# 案例专题考前冲刺

> 科目二（案例分析）按考频分五类：① **质量属性 + 架构风格**（拿分基本盘，目标 20 分）② 软件工程传统题型（结构化 DFD/E-R + UML）③ 数据库 / Redis ④⑤ 新兴技术（大模型 / 云原生 / 湖仓一体 / Web3）。超纲题年年有（软件 + 架构设计结合），第 ③④⑤ 类年年翻新。本文只留必背知识要点，题目从略。

## 一、质量属性 + 架构风格（第一类）

### 1.1 质量属性：开发期 6 + 运行期 7

| 期 | 属性 | 定义 / 设计策略（关键词） |
| ---- | -------- | -------------------------- |
| 开发期 | 易理性 | 设计被开发人员理解的难易程度；模块化、规范命名 |
| 开发期 | 扩展性 | 因新需求或需求变化而增加新功能的能力（灵活性）；抽象、插件、配置化 |
| 开发期 | 可重用性 | 重用软件系统或某一部分的难易程度；通用组件、设计模式 |
| 开发期 | 可测试性 | 对软件测试以证明满足需求规范的难易程度；接口隔离、依赖注入 |
| 开发期 | 可维护性 | 需要修改缺陷、增加功能、提高质量属性时，识别修改点并实施修改的难易程度；监控告警 |
| 开发期 | 可移植性 | 将软件系统从一个运行环境转移到另一个运行环境的难易程度；屏蔽 OS/硬件差异 |
| 运行期 | 性能 | 响应能力（响应时间、吞吐量）；优先级队列、增加计算资源、减少计算开销、并发、资源调度 |
| 运行期 | 安全性 | 阻止非授权使用 / 拒绝服务（保密性、完整性、不可抵赖性、可控性）；入侵检测、用户认证、授权、追踪审计 |
| 运行期 | 互操作性 | 与其他系统交换数据和相互调用服务的难易程度 |
| 运行期 | 可靠性 | 错误或意外使用下维持功能特性的能力（MTTF/MTBF/MTTR）；心跳、Ping/Echo、冗余、选举 |
| 运行期 | 可用性 | 正常运行时间比例（故障间隔时间 / 恢复速度）；心跳、Ping/Echo、冗余、选举 |
| 运行期 | 鲁棒性 | 非正常情况（非法操作、软硬件故障）下仍能正常运行，也称**健壮性 / 容错性** |
| 运行期 | 功能性 | 系统所能完成所期望的工作的能力（任务的总能力） |

**质量属性场景六要素**：刺激源、刺激、环境、制品、响应、响应度量（案例填空高频，如"敏感信息超长字节"→ 刺激源=用户、刺激=传输/存储时需加密、响应=加密算法、度量=16 字节）。

### 1.3 架构评估

- **ATAM（架构权衡分析法）**：让架构师明确如何权衡多个质量属性目标。参与者：评估小组、项目决策者、其他项目相关人。四个活动领域：场景和需求收集、体系结构视图和场景实现、属性模型构造和分析、评估。用**效用树**（质量属性 → 属性分类 → 属性场景）对场景分类和排优先级；头脑风暴出 3 类场景：**用例**（对系统典型的使用）、**增长**（覆盖对系统的修改）、**探测**（覆盖那些可能会对系统造成过渡的极限修改）。
- **SAAM**：以**可修改性**为核心的评估（考题出现少）。
- **ABAS**：领域知识库通过**基于属性的架构风格**维护。

## 二、软件工程传统题型（第二类）

- **结构化分析**：三大模型 = 功能模型（DFD）、行为模型（状态转换图 STD）、数据模型（E-R）。
- **数据流图**：四要素 = 外部实体、加工、数据存储、数据流；数据字典五条目 = 数据项、数据结构、数据流、数据存储、处理过程。
- **分层平衡原则**：父图与子图之间平衡（任一 SDF 子图的输入/输出数据流必须与父图中对应加工的输入/输出数据流保持一致）；若父图中某加工的一条数据流对应于子图中的几条数据流，而子图中组成这些数据流的数据项全体正好等于父图中的那条数据流，那么它们仍然平衡。
- **面向对象分析**：用例模型 = 识别参与者、合并需求获得用例、细化用例描述、调整用例模型；分析模型 = 定义概念类、识别类之间的关系、建立交互图。
- **UML 四关系**：依赖（语义依赖，一个事物的语义变化影响另一个）、关联（结构关系，组合和聚合都是部分与整体）、泛化（一般/特殊，父子类）、实现（接口与实现类之间的契约）。
- **14 种图速记**：用例图（参与者+用例边界）、类图/对象图（静态结构）、构件图/组合结构图（内部结构与端口）、顺序图/通信图/定时图/交互概览图（交互）、状态图/活动图（行为）、部署图/制品图（物理部署）、包图（逻辑分组）。

## 四、数据库与 Redis（第三类，超纲热点）

- **反规范化 5 法**：增加冗余列、增加派生列、重新组表、水平分割（按列值拆分到多张独立表）、垂直分割（主键与部分列放到一个表，主键与其余列放到另一个表，查询时减少 I/O 次数）。
- **Redis 定位**：Remote Dictionary Server，ANSI C 编写的 Key-Value 内存数据库；数据在内存中，MySQL 数据在磁盘中。
- **五大数据类型**：String（缓存、计数器）、List（消息队列、时间线）、Hash（对象存储）、Set（去重、共同好友）、Zset（排行榜）。
- **三种特殊类型**：Geo（地理位置定位，附近的人、距离计算）、HyperLogLog（基数统计，UV 统计）、Bitmaps（比特位映射，用户签到、在线状态）。
- **七类场景 → 用哪个结构（案例常问"用什么实现"）**：缓存 → **String/Hash**（击穿用 `SET NX` 互斥）｜排行榜 → **ZSet**（score 即分数）｜计数器 → **String**`INCR` / 多维度用 **Hash**`HINCRBY` / 去重计数用 **Set**`SCARD`｜消息队列 → **List**`BRPOP` / 延时用 **ZSet**（score=到期时间）/ 可靠消费用 **Stream**（`XREADGROUP`+`XACK`）｜分布式锁 → **String**`SET NX PX`+Lua（Redisson 内部用 **Hash** 存重入次数）｜社交 → **Set**（共同关注=`SINTER`、推荐=`SDIFF`）/ **ZSet**（粉丝榜）/ **List**（时间线）｜位运算 → **Bitmap**（签到，1bit/天）/ **HyperLogLog**（UV，误差约 0.81%）。完整表与命令见 [架构案例专题](架构案例专题.md) 6.8。
- **为什么快**：纯内存操作；B+ 树 / 合理的数据结构编码；单线程 IO 多路复用（避免上下文切换和锁竞争，6.0 起引入多线程提速）；5.0 曾实验 VM 机制（自建 VM 机，不经过系统函数处理，减少时间移动和请求）。
- **缓存三大问题**：穿透（查不存在的数据：布隆过滤器、缓存空值）；击穿（热点 key 过期瞬间高并发：热点数据永不过期、互斥锁）；雪崩（大量 key 同时过期 / Redis 宕机：过期时间加随机值、多级缓存、集群高可用、熔断限流）。
- **热 Key**：访问频率太高；解决 = 热点 key 分离到本地缓存、读写分离、增加副本。
- **过期 + 淘汰**：定期过期（每秒随机抽查，主动删除）+ 惰性过期（使用时检查，按需删除）+ 内存淘汰策略兜底；淘汰算法：volatile-lru / allkeys-lru / volatile-lfu / allkeys-lfu / volatile-random / allkeys-random / volatile-ttl / noeviction；一般生产建议 allkeys-lru，需严格保证数据不丢失用 noeviction。
- **分布式锁 Redisson**：加锁成功即启动看门狗线程，每隔 10 秒检查并延长 key 生存时间，解决"业务没执行完锁就过期"。
- **Redlock**：针对主从异步复制导致锁丢失的更高级算法。假定 5 个独立 master 节点：① 获取当前时间（毫秒）→ ② 按顺序向 5 个 master 请求加锁（设置连接和响应超时，超时时间远小于锁失效时间）→ ③ 用当前时间减去开始获取锁时间得到获取锁使用时间，**超过一半节点（N/2+1=3）加锁成功且使用时间小于锁有效期，才认定加锁成功** → ④ key 真正有效时间需减去获取锁所用时间 → ⑤ 失败则向所有 master 节点发解锁（防止有个别 master 加锁成功但没收到解锁）。
- **跳表**：链表 + 多级索引；平均查找 O(logN)、最坏 O(N)；支持顺序性操作、便于批量处理；组成 = zskiplist（表头、表尾、长度）+ zskiplistNode（节点）。
- **MySQL 与 Redis 双写一致性**：延时双删（实现简单，但短时间内仍可能不一致）；删除重试机制（降低二次删除失败，业务代码侵入多）；**读 binlog 异步删除缓存**（推荐：异步无侵入，保证最终一致）。
- **RDB vs AOF**：RDB = 定时生成内存数据二进制快照（dump.rdb），优点：恢复快、单文件容灾友好、BGSAVE 仅 fork 瞬间阻塞；缺点：两次备份间丢数据、fork 内存翻倍、最低 60 秒级持久化。AOF = 记录所有写操作命令，重放恢复，优点：always 模式零丢失、文本可读、可修复可重写；缺点：文件大、恢复慢、always 写性能下降 50%+。
- **cache-aside**：读——先读缓存，未命中读库并回写缓存；写——先写数据库，再更新 / 删缓存。
- **Redis 主从复制**：全量同步 = 请求同步 → 判断是否第一次 → 回退 master 数据版本信息 → 执行 bgsave → 清空本地数据加载 RDB → 执行 repl_backlog 中的命令；之后增量同步 = psync replid offset → 回复 continue → 获取 offset 后的数据。
- **防超卖三方案**（高频案例）：① 分布式锁控制超卖（扣减前先获取锁防止多节点同改，配 Lua 保证原子释放）；② Redis 原子操作 + 库存预扣（DECR ticket_stock，返回值 ≥0 成功，配 Lua 实现"限量每人一张"）；③ Redis 作乐观锁版本号缓存（WATCH 监听库存 key → MULTI → DECR → EXEC，key 被改则事务失败，失败重试至成功或上限）。
- **悲观锁 vs 乐观锁**：悲观锁 = 共享锁（读锁，多个事务可并发读，只允许一个事务持有该锁；加锁期间其他事务不能读也不能写，并发度最低、一致性最强，控制不当易死锁）；乐观锁 = 不加锁，数据表增加版本号字段（更新时检查版本号是否被改过，是则操作成功、否则重新加载），无阻塞、并发度高、不死锁，但冲突频繁时大量重试循环耗 CPU、需业务层处理重试。

## 五、新兴技术（第四、五类）

### 5.1 大模型

- **MaaS 三层**：模型平台层（底座通用模型，自然语言式交互 + 持续训练 / 领域化学习，对接算力）；模型服务层（API/SDK 编程式、Prompt 工程化管理平台、RAG 检索增强生成平台、智能体开发平台、智能化运营服务）；应用开发层（低代码/无代码 + 编程式扩展、微调、私有化部署、Agent 编排）。
- **MaaS 落地四个权衡**：统一接入与首 Token 优化是网关部署模式核心权衡；RAG 与长上下文是解决知识引入问题的两种架构方案（RAG：检索增强生成；长上下文：一次性把更多数据塞入提示词）；自建 Embedding 与云服务 Embedding 取决于使用频次和数据安全要求；单一模型与多模型决定系统可用性和供应依赖程度（多模型可避免单点故障，需智能路由引入更多供应商）。
- **RAG**：解决两个局限——模型知识截止于训练数据、不掌握企业未公开数据。两条链路通过向量数据库衔接：**离线**（文档解析 → 分段切片 → 向量化 → 入库）；**在线**（用户问题 → Embedding → 向量检索 TopK → 作为 Prompt → 生成）。检索策略：纯向量（语义相似，可能漏关键词）、混合检索（向量 + 关键词 BM25，结果重排）。Embedding 模型是关键决策：质量、推理速度、向量维度三者权衡。
- **Agent**：本质是让大模型像人类一样使用工具。**模型负责"思考"**（理解意图、制定计划、选工具），**工具负责"执行"**（查库、发邮件、调 API、执行代码）。四模块：记忆（对话历史与上下文）、规划（把复杂目标拆成子任务序列）、工具调用（Function Calling 把自然语言转为结构化工具调用）、行动与反思（判断是否达到目标，决定继续或结束）。
- **Function Calling 五步**：① 请求携带可用工具声明列表（名称、功能描述、JSON Schema 参数）→ ② 大模型判断需调用哪个工具，返回结构化 tool_calls → ③ 应用解析并实际执行工具 → ④ 执行结果作为新消息提交给大模型 → ⑤ 大模型生成最终自然语言回复。

### 5.2 云原生 AI 基础设施（四层）

- **总体四层**：基础设施层（GPU 等异构计算资源标准化接入与高效调度）、流量管理与调度层（灰度发布 / 金丝雀部署）、服务网格层（Serverless 事件驱动按需扩缩容）、观测监控层（指标采集与可视化）。
- **K8s GPU 管理**：Device Plugin 把 GPU 作为扩展资源上报集群；GPU Operator（驱动安装更新、容器运行时、设备插件上报资源、监控采集指标）；**MIG**（一张 A100/H100 切分为多个独立实例，各有计算核心/显存/缓存，细粒度共享降本）。
- **AI 工作负载调度**：通过 Pod 的 `nvidia.com/gpu` 声明申请；K8s 顺序调度会导致分布式训练多 Worker Pod 空转浪费，需队列管理、优先级控制、资源配置。**Volcano**（CNCF）：队列管理多租户隔离、任务优先级（在线推理优先于离线训练）、拓扑感知调度（Worker 调度到同一 RDMA 域降延迟）、资源预留防大作业饥饿。
- **服务网格 Istio**：把 AI 应用拆为多个微服务（预处理、模型推理、后处理、特征服务），Envoy Sidecar 代理流量；Istiod 控制平面负责服务发现、路由下发、安全管理。**虚拟服务**：灰度发布（95% 流量到 v1、5% 到 v2，看延迟/错误率逐步放量）；**目标规则**：负载均衡、连接池、熔断配置。**熔断**：防推理服务显存溢出/超时故障扩散、级联故障。
- **GPU 感知路由**：将 GPU 指标集成到服务网格——路由到 GPU 显存使用率最低的实例（避免 OOM）、一致性路由（同一用户请求总到同一实例，利用 GPU 缓存提速）。

### 5.3 湖仓一体

- **三阶段演进**：数据仓库（Schema-on-Write 写时模式，查询性能优、一致性高，但无法存非结构化数据、扩展成本高、不支持 ML）；数据湖（Schema-on-Read 读时模式，原始格式存储、成本低、支持 ML，但缺 ACID、查询差、易成"数据沼泽"）；**湖仓一体 Lakehouse**（对象存储之上提供 ACID、时间旅行、版本管理，保留湖的灵活性；一份数据支持 BI/数据科学/ML/实时多种负载）。
- **核心能力**：① **ACID + MVCC**：元数据层实现多版本并发控制，多读写并发互不干扰；每次写入生成新数据文件版本，提交前不可见，提交后元数据原子切换，保证一致性与隔离性。② **时间旅行**：每次 INSERT/UPDATE/DELETE 生成新快照并记录时间和版本号，可查任意历史时间点；用于审计合规、错误恢复、趋势分析、ML 特征工程（防数据泄露）。③ **Schema 演化**：加列/删列/重命名不需停机重建表，元数据层变更、存储文件不变，查询引擎按最新 Schema 解释数据。④ 数据治理：统计信息自动收集、小文件合并、分区管理、生命周期策略（过期数据自动清理或归档到低成本存储）。
- **平台六层**：数据源层（业务库、Kafka、日志、IoT、SaaS）→ 数据采集层（Flink CDC、Kafka/Flink 流式、Sqoop/DataX 批量）→ 湖存储层（HDFS/S3/OSS + Delta/Iceberg/Paimon，存贴源/明细/汇总）→ 计算引擎层（Spark 批与 ML、Flink 实时、Trino/Presto 交互查询）→ 数据服务层（BI 报表、数据科学、实时大屏、推荐系统）。
- **三大权衡**：实时性与数据质量（近实时入湖时效高但未经严格清洗；批量入湖质量高但时效差，风控/实时大屏选近实时，BI 报表可容忍小时级）；查询性能与存储成本（对象存储延迟高于本地 SSD，高频场景建物化视图/缓存，会增加存储成本）；Schema 灵活性与治理（核心数据模型规范化设计，探索性数据保留灵活性）。

### 5.4 Web3 与去中心化架构

- **四层结构**：区块链网络层（Layer0：Celestia/Polkadot；Layer1：Ethereum/Bitcoin/Solana；Layer2：Arbitrum/Optimism；按虚拟机分 EVM 系 Solidity 与非 EVM 系 Rust/Move；按功能分计算型与存储型 Filecoin/Arweave）→ 中间件层 → 应用层 → 访问层。
- **中间件层**：预言机 Oracle（区块链与外部数据桥梁，传资产价格/天气/IoT 读数，Chainlink 为龙头）；索引查询（The Graph 定制化监听链上数据并映射为自定义存储、Covalent 统一 API 服务）；去中心化存储（IPFS 内容寻址 + Filecoin/Arweave 激励层）；安全审计（CertiK/OpenZeppelin 代码审计、Immunefi Bug Bounty）。
- **RWA（真实世界资产）**：把实体资产数字化映射到链上形成通证，价值 = 碎片化 + 全球互通性带来更多流动性、降低融资成本。**三阶段**：链下确权（法律合规确权与价值评估）→ 链上映射（资产权益映射为代币）→ 链上治理（智能合约实现收益分配、质押清算自动化）。关键技术：可信数据上链（从认证 IoT 设备直采，运营数据与 IoT 数据互验，满足完整性/有效性/及时性）、身份认证体系（设备注册唯一"身份认证"标识，内置可信 SDK 于 MCU/模组/芯片，蚂蚁 Antchain Inside 方案已在充电桩、光伏、换电成熟应用）。
- **DePIN（去中心化物理基础设施）**：区块链 + 代币激励，社区共同建设维护物理基础设施，放弃层级化企业结构。**五大核心组件**：物理硬件（路由器/热点/服务器/GPU/太阳能板）、区块链与智能合约（管理交易、验证贡献、分配奖励）、代币激励（按网络参与程度获奖，形成自我强化循环）、运营者（投资维护设备获激励）、最终用户（付费用网完成生态闭环）。双边通证经济：供给端贡献硬件获代币与治理权；需求端付费，法币购买并销毁原生代币使价值回馈贡献者。典型项目：Helium（无线网络）、Filecoin（存储）、Render（GPU 算力）、IoTeX（物联网基础设施）。RWA 与 DePIN 协同：设备在链上以 NFT 形式表达，关联位置/类型/运行时间，NFT 可分割供多投资者按比例资助，每个物理设备都成为可交易 RWA 资产。

## 小结

- 第一类（质量属性 + 架构风格）是**拿分基本盘**：13 种架构风格 + 13 个质量属性 + 场景六要素必须条件反射级熟练。
- 第二类传统题型（DFD/E-R/UML）凭软件工程基本功即可稳拿。
- 第三类数据库超纲热点集中在 Redis：穿透/击穿/雪崩、Redisson/Redlock、RDB vs AOF、双写一致性、防超卖三方案。
- 第四、五类新兴技术靠"选词填图 90% + 半知半解 50%"策略得分：MaaS 分层与权衡、RAG 流程、Agent 四模块、云原生 AI 四层、湖仓一体三阶段与三权衡、Web3 四层、RWA 三阶段、DePIN 五组件。
