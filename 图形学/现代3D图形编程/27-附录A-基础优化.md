# 基础优化

优化这个题目太大了，仅用一个附录不可能充分覆盖。优化往往针对特定算法，而且通常要拿内存来交换。也就是说，你可以用占更多内存的方式让某样东西跑得更快。即便如此，也只有在做了恰当的性能分析、确知性能到底缺在哪里之后，才应该去做优化。

本附录转而讲解最基础的优化。这些优化不一定能提升任何特定程序的性能，但它们几乎不会有坏处，而且实现起来也相对容易。把它们看作你在做真正的优化之前应该先采用的默认标准做法。为了让叙述保持清晰，本书中的大部分代码并没有采用这些做法，所以其中许多对你来说会是新东西。

按我说的做，不要按我做的那样做。

## 顶点格式

尽可能让物体的顶点属性数组交错存放。显而易见，如果你需要频繁覆写某些属性，而其他属性保持静态，那你确实需要把这些数据分开。但除非你有某种特定需求，否则就应该交错存放顶点数据。

同样重要的是，尽量使用尽可能小的顶点数据。数据越小，GPU 缓存效率越高；每条缓存行能存放更多顶点属性。这意味着更少的直接内存访问，也意味着顶点着色器获取属性的性能提升。本书中的顶点数据几乎总是 32 位浮点数。只有在你确实需要那么高的精度时，才应该使用 32 位浮点数。

做到这一点的关键在于为属性使用归一化的整数值。再次提醒一下它的工作方式，下面是 `glVertexAttribPointer` 的定义：

```cpp
glVertexAttribPointer(void);
```

如果 `type` 是整数类型，比如 `GL_UNSIGNED_BYTE`，那么把 `normalized` 设为 `GL_TRUE` 就表示 OpenGL 会把这个整数值解释为归一化的值。它会自动把整数 255 转成 1.0，依此类推。反之如果归一化标志为 false，它就会把整数直接转成浮点数：255 变成 255.0，等等。有符号的值同样可以归一化；带归一化的 `GL_BYTE` 会把 127 映射到 1.0，-128 映射到 -1.0，等等。

**颜色**

颜色值通常存储为 4 个无符号归一化字节。这比使用 4 个 32 位浮点数小得多，而精度的损失几乎总是可以忽略。要传入 4 个无符号归一化字节，使用：

```cpp
glVertexAttribPointer(#, 4, GL_UNSIGNED_BYTE, GL_TRUE, ...);
```

最妙的是，这一切都是免费的；它不消耗任何实际性能。不过要注意，32 位整数无法被归一化。

有时颜色值需要比 8 位更高、但又低于 16 位的精度。如果一个颜色处于线性 RGB 色彩空间中，往往值得给它高于 8 位的精度。如果该颜色的 alpha 可以忽略或根本不存在，那么可以使用一种特殊的 `type`。这个类型是 `GL_UNSIGNED_INT_2_10_10_10_REV`。它接受 32 位无符号归一化整数，并从每个整数中取出该属性的四个分量。这个类型只能配合归一化使用：

```cpp
glVertexAttribPointer(#, 4, GL_UNSIGNED_INT_2_10_10_10_REV, GL_TRUE, ...);
```

每个整数中最高有效的 2 位是 Alpha，接下来的 10 位是 Blue，然后是 Green，最后是 Red。请注意这里是反序的。它等价于 C 中的这个位域结构：

```cpp
struct RGB10_A2
{
  unsigned int alpha    : 2;
  unsigned int blue     : 10;
  unsigned int green    : 10;
  unsigned int red      : 10;
};
```

**法线**

另一个精度并非首要关键的属性是法线。如果法线是归一化的——它总是应当归一化——那么各坐标始终落在 [-1, 1] 区间内。所以这里适合使用有符号归一化整数。8 位精度有时已经够用，但 10 位精度会有所改善。16 位精度 `GL_SHORT` 可能 overkill 了，所以请坚持使用 `GL_INT_2_10_10_10_REV`（上面那个格式的有符号版本）。由于这个格式提供 4 个值，你需要把 4 作为该属性的大小，但在着色器中仍然可以用 `vec3` 作为法线的输入变量。

**纹理坐标**

二维纹理坐标通常不需要 32 位精度。8 位和 10 位精度往往不够，但 16 位无符号归一化整数通常已经足够。如果纹理坐标超出 [0, 1] 范围，那么归一化就不够用了。这些情况下，32 位浮点数之外还有一种选择：16 位浮点数。

处理 16 位浮点数最难的地方在于 C/C++ 对它的支持很差。它没有原生的 16 位浮点类型，几乎所有其他类型都有。就连 10 位格式也可以像上面那样用结构体中的位选择器拼出来。而从 32 位浮点数生成 16 位浮点数需要格外小心，同时还需要理解浮点值的原理。

这正是 GLM 数学库派上用场的地方。它提供了 `glm::thalf`，一种表示 16 位浮点值的类型。它带有重载运算符，因此可以像普通 `float` 一样使用。GLM 还分别提供了用于向量和矩阵的 `glm::hvec` 与 `glm::hmat` 类型。

**位置**

一般来说，位置是最不容易在没有代价的情况下得到优化的属性。16 位浮点数可以用，但它们被限制在大约 [-6550.4, 6550.4] 的范围内。它们也缺少某些精度，而根据模型空间中物体的大小和细节程度，这些精度可能是必需的。

如果 16 位浮点数不够用，可以使用某种形式的压缩。过程如下：

1. 加载网格数据时，找出网格在模型空间中的包围体。做法是分别找出 X、Y、Z 三个方向上的最大值和最小值。这代表模型空间中一个包含所有顶点的矩形。这个矩形由两个 3D 向量定义：最大向量（包含 X、Y、Z 的最大值）和最小向量。它们被命名为 `max` 和 `min`。
2. 计算该区域的中心点：

```cpp
glm::vec3 center = (max + min) / 2.0f;
```

3. 计算该区域尺寸（宽、高、深）的一半：

```cpp
glm::vec3 halfSize = (max - min) / 2.0f;
```

4. 对网格中的每个位置，用它减去中心点、再除以一半尺寸，算出一个归一化的版本。如下：

```cpp
glm::vec3 newPosition = (position - center) / halfSize;
```

5. 对每个新位置，乘以 32767，把它转换成有符号归一化整数：

```cpp
unsigned short normX = (unsigned short)(newPosition.x * 32767.0f);
unsigned short normY = (unsigned short)(newPosition.y * 32767.0f);
unsigned short normZ = (unsigned short)(newPosition.z * 32767.0f);
```

  这三个坐标随后就作为新的位置数据存进缓冲对象。
6. 把 `center` 和 `halfSize` 变量随网格数据一起保存。在为该网格计算从模型空间到相机空间的矩阵时，在最前面再加上最后一个矩阵。这个矩阵会执行我们计算归一化数值时那个操作的逆操作：

```cpp
matrixStack.Translate(center);
matrixStack.Scale(halfSize);
```

  这个最后的矩阵*不应该*应用到法线矩阵上。请在应用上面最后一步*之前*算出法线矩阵。所以，如果你此前没有为法线使用单独的矩阵（也就是说，你的模型到相机矩阵中没有非均匀缩放），现在就需要用一个了。所以这可能会让你的数据变大，或者让你的着色器跑得稍慢一点。

**对齐**

还有一条你始终应该遵守的规则：确保所有属性都从 4 字节边界开始。这对小于 4 字节的属性同样成立，比如由 8 位数值组成的 3 分量向量。虽然 OpenGL 允许你使用任意对齐方式，但硬件可能无法正常工作。所以，如果你把 3D 位置数据做成 16 位浮点数或 16 位有符号归一化整数，你仍然会从每个位置浪费掉 2 个字节。你可能需要考虑把位置值做成 4 分量值，并在 W 分量里放点有用的东西。

## 纹理

你可以用多种技术来提升纹理访问的性能。

### 图像格式

数据越小，取入着色器的速度就越快。和顶点格式一样，尽量使用你能凑合的最小格式。和顶点格式一样，你能凑合的边界往往由你想在纹理中存储什么来决定。

**法线**

包含法线的纹理可以使用 `GL_RGB10_A2_SNORM`，它是我们给属性法线用的 10 位有符号归一化格式在纹理层面的等价物。不过，如果这些法线是用于切线空间法线贴图的，还可以做得更精确。由于切线空间法线的 Z 坐标总是为正，而且法线是归一化的，实际的 Z 值可以由另外两个值算出。所以你只需要存储 2 个值；`GL_RG16_SNORM` 就足以满足需求。要算出第三个值这样做：

```glsl
vec2 norm2d = texture(tangentBumpTex, texCoord).xy;
vec3 tanSpaceNormal = vec3(norm2d, sqrt(1.0 - dot(norm2d, norm2d)));
```

显然这会消耗一些性能，所以问题在于你实际需要多少精度。好的一面是，使用这种方法意味着你不必再对从纹理中取回的切线空间法线做归一化。

`GL_RG16_SNORM` 格式还可以通过纹理压缩变得更小。`GL_COMPRESSED_SIGNED_RG_RGTC1` 压缩纹理格式是一种双通道有符号整数格式。它每像素只占 8 位。

**浮点强度**

浮点纹理有两种不走寻常路的格式，二者都有重要用途。`GL_R11F_G11F_B10F` 格式可能是用于 HDR 渲染目标的好格式。顾名思义，它只占 32 位。缺点是相比 `GL_RGB16F` 精度损失相对较大（而且完全失去了目标 alpha）。两者能存储的数量级大致相同，但更小的格式会损失一些精度。这可能影响也可能不影响场景的整体视觉质量。测一下哪个更好应该相当简单。

`GL_RGB9_E5` 格式用于输入用的浮点纹理。如果你有一张表示 HDR 情况下光强度的纹理，这个格式会相当顺手。它的工作方式是每个 RGB 颜色获得 9 位数值，但它们共享同一个指数。这与浮点数的原理有关，但归结起来就是：这些数值的量级必须彼此比较接近。它们不必那么接近；仍有一定余地。相对于较大值过小的数值会变成零。视具体量级而定，这往往是可以接受的取舍。

这个格式适合那些由离线工具生成的纹理。你无法把渲染结果写入这种格式的纹理。

**颜色**

存储被钳制在 [0, 1] 的颜色，可以按需用 `GL_RGBA8` 或 `GL_SRGB8_ALPHA8` 获得不错的精度。不过，也有压缩纹理格式可用。如果压缩瑕疵不太明显，S3TC 格式是不错的选择。S3TC 格式也有 sRGB 版本。

S3TC 各格式之间的差别在于你需要多少 alpha。可选项如下：

- **GL_COMPRESSED_RGB_S3TC_DXT1_EXT**：无 alpha。
- **GL_COMPRESSED_RGBA_S3TC_DXT1_EXT**：二值 alpha。每个纹素要么为零要么为一。alpha 为零的纹素，其 RGB 颜色也会是零。
- **GL_COMPRESSED_RGBA_S3TC_DXT3_EXT**：每像素 4 位 alpha。
- **GL_COMPRESSED_RGBA_S3TC_DXT5_EXT**：alpha 在一个 S3TC 块中压缩，与 RG 纹理压缩很相似。

如果一张图像需要有变化的 alpha，主要差别在于 DXT3 与 DXT5 之间。DXT5 有可能得到更好的结果，但如果 alpha 用 S3TC 算法压缩得不好，结果会比 DXT3 差不少。

### 经常使用 mipmap

当纹理被映射到那些在纹素空间中比在窗口空间中更大的区域时，mipmap 能提升性能。也就是说，当发生纹理缩小时，mipmap 能提升性能。mipmap 之所以能提升性能，是因为它让纹理访问的位置保持彼此邻近。纹理硬件是针对访问纹理局部区域而优化的，所以改善纹理数据的局部性有助于性能。

这有多重要取决于纹理被映射到表面的方式。使用显式纹理坐标的静态映射，或者基于表面属性做线性计算的映射，都能利用 mipmap 改善纹理访问的局部性。对于更不寻常的映射，或者纯粹用作查找表的数据，mipmap 可能对局部性毫无帮助。

归根结底，当相关纹理表示的是某个表面特征、因而直接映射到该表面时，mipmap 更有可能提升性能。所以漫反射纹理、法线贴图、高光贴图以及其他表面特征，都很可能从使用 mipmap 中获得一些性能收益。投影光就不太可能从中获益，因为这取决于它所投影到的几何体。

## 物体优化

这些优化都与物体这个概念有关。就本次讨论而言，一个物体是网格、程序、uniform 数据以及一组纹理的组合，用来渲染世界中某个特定的东西。

### 物体剔除

一个虚拟世界由许多物体组成。我们绘制的物体越多，渲染耗时越长。

一项主要的优化，同时也是非常简单的一项：只渲染必须渲染的东西。绘制一个在世界中实际上看不见的物体毫无意义。因此，这里的任务是对每个物体检测它是否可见；如果不可见，就不渲染它。这个过程称为可见性剔除或物体剔除。

作为第一轮筛选，我们可以说：不在视锥之内的物体不可见。出于显而易见的原因，这称为视锥剔除。判定一个物体是否在屏幕之外通常是一项 CPU 任务。每个物体都必须用一个简单的体积来表示，比如一个球体或一个相机空间的包围盒。之所以用这些物体，是因为它们相对容易与视锥做测试；如果它们落在视锥内，那么对应的物体就被视为可见。

当然，这只能把场景缩减到相机前方的物体。被其他物体完全遮挡的物体仍然会被渲染。有许多技术可以检测物体是否遮挡了其他物体的视线。Portal、BSP 以及各种其他技术，都会预处理某些静态地形以确定可见性集合。这样就可以知道：当相机位于世界的某个区域时，位于某些其他区域的物体即使在视锥之内也不可见。

更细粒度的解决方案涉及一项称为遮挡查询的硬件特性。它的做法是渲染一个物体，然后询问该物体实际被光栅化了多少个片元。如果连一个片元都通过了深度测试（假定所有可能的遮挡表面都已渲染），那么这个物体就是可见的，必须渲染。

通常更倾向于渲染简单的测试物体，这样只要测试物体的任何部分可见，真实物体就一定可见。绘制一个测试物体要比绘制一个带有专用蒙皮顶点着色器的复杂层次模型快得多。写掩码（用 `glColorMask` 和 `glDepthMask` 设置）用来阻止测试物体的片元着色器输出被写入帧缓冲。因此，测试物体只是针对深度缓冲做测试，而不会被真正渲染。

OpenGL 中的遮挡查询是带状态的对象。它们用 `glGenQueries` 函数创建。要开始为遮挡查询渲染一个测试物体，需要把 `glGenQueries` 生成的对象连同 `GL_SAMPLES_PASSED` 模式一起传给 `glBeginQuery` 函数。`glBeginQuery` 与相应的 `glEndQuery` 之间的所有渲染命令都属于这个测试物体。如果该物体的所有片元都被丢弃了（通过深度缓冲或其他方式），那么查询失败。如果连一个片元都被渲染了，那么查询通过。

这可以配合一个称为条件渲染的概念使用。它的意思就如字面所说：有条件地渲染一个物体。它允许一系列由 `glBeginConditionalRender`/`glEndConditionalRender` 函数括起来的渲染命令，根据遮挡查询对象的状态来决定这些渲染命令是否执行。如果遮挡查询通过，那么这些渲染命令就会被执行；如果没有通过，就不会执行。

当然，条件渲染可能造成管线停顿；OpenGL 仍然要求操作按顺序执行，条件操作也不例外。所以如果一个条件渲染正在等待它的遮挡查询完成，所有后续操作都会被拖住。为避免这一点，你可以在开始条件渲染时指定 `GL_QUERY_NO_WAIT`。这样如果查询在这次条件渲染准备好被渲染之前还没完成，OpenGL 就会直接渲染。为了让这个机制收益最大化，最好把条件对象安排在远晚于其依赖的测试对象之后再渲染。

### 模型 LOD

当一个模型距离很远时，它不需要看起来那么细致，因为大多数细节都会因为分辨率不足而丢失。因此，人们可以用更精细的模型替换较粗糙的模型。这通常被称为细节层次（Level of Detail，LOD）。

当然在现代渲染中，"细节"不只是网格中多边形数量的意思。它往往还包括用哪个着色器、用哪些纹理等等。所以网格有 LOD，着色器也有。纹理则有 mipmap 这套内建的 LOD 机制。但常常是这样的：低 LOD 的着色器（远处使用的那些）不需要像近处 LOD 着色器那样多的纹理。对远处的模型，你或许用逐顶点光照就应付得过去，而近处的模型则需要逐片元光照。

这在视觉上的难点在于如何处理 LOD 层级之间的过渡。如果你把切换点放得离相机太近，用户就会看出跳变；如果放得太远，你又会失去在远处渲染低细节网格所带来的大部分性能收益。找到一个合适的折中点是关键。

### 状态切换

OpenGL 有三类函数：真正执行渲染的函数、从 OpenGL 获取信息的函数，以及修改 OpenGL 中某些存储信息的函数。绝大多数 OpenGL 函数属于第三类。OpenGL 的这些信息统称为"状态"，无谓地改变状态代价高昂。

因此，这条优化规则是：尽可能减少状态切换的次数。对简单场景来说，这可能微不足道。但在一个复杂的数据驱动环境中，这会极其复杂。

基本的思路是把所有需要渲染的物体（剔除不可见物体并完成各项 LOD 工作之后）收集成一张列表，然后按它们共享的状态排序。例如，使用同一个程序的物体共享着色器程序状态。这样做之后，如果你按状态顺序渲染物体，就把 OpenGL 状态切换的次数降到了最低。

最需要作为排序依据的三类状态，是变化最频繁的三类：程序（及其关联的 uniform）、纹理，以及 VAO 状态。全局状态，比如背面剔除、混合等，代价较低，因为它们变化没那么频繁。一般来说，所有网格使用的剔除参数、视口设置、深度比较状态等等都是一样的。

减少顶点数组状态切换通常不只是排序就够了，还需要改变网格数据的存储方式。本书通常给每个网格自己的 VAO，代表它自己独立的状态。这当然非常方便，但如果 CPU 是瓶颈，它反而会损害性能。

为此，可以尝试把顶点数据格式相同的网格归到同一组缓冲对象和 VAO 中。这样就可以用若干条不同的 `glDraw*`命令渲染若干个物体，而它们全都使用同一份 VAO 状态。用索引数据渲染时，`glDrawElementsBaseVertex` 对这个用途非常有用。绑定 VAO 的次数越少越好。

关于 uniform 状态切换对性能有多大危害，以及在程序内 uniform 与基于缓冲的 uniform 之间切换的性能差异，能参考的信息要少一些。

请注意，处理混合时状态排序帮不上忙，因为混合的正确性要求基于深度排序。因此必须避开这一点。

另外还有一些棘手的状态可能造成损害，具体取决于硬件。例如，一旦你清空深度缓冲并开始向它渲染，最好就不要改变深度测试的方向。这涉及到深度缓冲的某些特定硬件优化。

## 寻找瓶颈

在优化渲染方面，你手中最有用的工具，就是搞清楚你的渲染为什么慢。

GPU 是按管线来设计的。管线中的每个阶段在功能上都与其他阶段独立。顶点着色器可以在计算若干个顶点，同时裁剪和光栅化在处理另外一些三角形，而片元着色器在处理由其他三角形生成的片元。

然而，如果光栅化器正忙，顶点着色器生成的顶点就无法传递给光栅化器。同理，如果所有片元着色器都被占用，光栅化器也无法生成更多片元。因此，GPU 的整体性能只能等于管线中最慢一步的性能。

这意味着，要真正让 GPU 变快，你必须找到管线中那个最慢的特定阶段。这个步骤被称为寻找**瓶颈**。在你知道瓶颈是什么之前，你所能做的最多只是猜测为什么东西比你以为的慢。而仅仅凭猜测就大幅改动代码，大概不是你该做的事。至少在你对相关的 GPU 有了大量经验之前不是。

还应当注意，瓶颈在单帧的整个渲染过程中并不一致。帧的某些部分可能是受 CPU 限制的，另一些可能是受片元着色器限制的。因此，先尝试找出很可能存在同样问题的渲染片段，然后再去找瓶颈。

### 测量性能

大多数人谈论性能时，最常见的性能指标是每秒帧数（FPS）。这个指标在跟外行交流时有用，但图形程序员不会把 FPS 当作标准性能度量。它是总体目标，但在测量一段渲染代码的实际性能时，更有用的度量就是时间。这通常以毫秒（ms）来衡量。

如果你想维持 60fps，那意味着你有 16.67 毫秒可以用来完成全部渲染任务。

有一件事会让性能度量变得复杂：GPU 既是管线式的，又是异步的。运行常规代码时，你调用一个函数，通常可以确信它返回时该函数所做的动作都已完成。而当你发出一个渲染调用（任何 `glDraw*` 函数）时，不仅渲染很可能在它返回时还没完成，甚至极有可能渲染根本还没*开始*。即便是做一次缓冲区交换也无法保证 GPU 已经结束工作，因为 GPU 可以等到稍后才真正执行缓冲区交换。

如果你确实想给 GPU 计时，就必须强制 GPU 完成它的工作。在 OpenGL 中，你可以调用一个名字起得很妙的函数 `glFinish`。它会在 GPU 完成工作之后的某个时刻返回。注意，它并不保证返回时就紧跟在 GPU 完成之后，只是在 GPU 完成了所有命令之后的某个时刻返回。所以，在调用 finish 之前给 GPU 一点足够的工作量是个好主意，这样可以尽量缩小你测得的时间与 GPU 实际所用时间之间的差距。

你还需要关闭垂直同步，也就是 vsync。图形芯片在某个时刻能够交换前后帧缓冲，并保证不会让显示图像的一半来自一个缓冲、另一半来自另一个缓冲。后一种情况称为**画面撕裂**，启用 vsync 可以避免它。但你并不关心撕裂；你想知道的是性能。所以你需要关闭任何形式的 vsync。

Vsync 由窗口系统相关的扩展 `GLX_EXT_swap_control` 和 `WGL_EXT_swap_control` 控制。两者做的事情相同，API 也相似。`wgl/glxSwapInterval` 函数接受一个整数，告诉你两次交换之间要等待多少个 vsync。如果传 0，那么它会立即交换。

### 可能的瓶颈

一段渲染代码可能存在若干种潜在瓶颈。我们会逐一列出这些瓶颈以及判定某处是否为瓶颈的方法。你应该按下面给出的顺序来测试它们。

#### 片元处理

这大概是最容易找到的。你的片元处理量完全取决于各个三角形被光栅化出的片元数量。因此，只要提高分辨率就行。如果你把分辨率提高 2 倍像素数（宽度或高度翻倍），而渲染时间也翻倍了，那么你就受片元处理限制。

注意，提高分辨率会让渲染时间上升。你真正关心的是它是否随渲染出的片元数量线性上升。如果片元数增加到 2 倍而渲染时间只上升 1.2 倍，那么这段代码就不完全是受片元处理限制。

#### 顶点处理

如果你并不受片元处理限制，那么很有可能你是受顶点处理限制的。在排除片元处理之后，只要关掉所有片元处理即可。如果这没有显著提升你的性能（一般来说总会有点变化），那么你就是受顶点处理限制。

要关闭片元处理，只需 `glEnable`(`GL_RASTERIZER_DISCARD`)。这会导致所有片元被丢弃。显然，什么都不会被渲染，但光栅化之前的所有步骤仍会执行。因此，你测得的性能时间就只反映顶点处理。

#### CPU

CPU 瓶颈意味着 GPU 处于饥饿状态：它消耗数据的速度超过了 CPU 提供数据的速度。你其实不会直接去测试 CPU 瓶颈，而是通过排除法把它找出来。如果其他环节都不是瓶颈，那么 CPU 显然没有给 GPU 足够的东西做。

### 无法修复的瓶颈

完全有可能某个瓶颈你修不了。也许你的渲染器中就是有一处顶点处理密集的代码无法避免。也许在某个渲染区域你确实需要那么多片元处理。

如果存在某个无法优化掉的瓶颈，那就转而利用它：提高管线中其他阶段的复杂度。如果你有一个修不好的 CPU 瓶颈，那就渲染更精细的模型。如果你有一个顶点着色器瓶颈，就通过增加一些片元着色器复杂度来改进光照。诸如此类。只要注意别把复杂度推到让瓶颈转移、反而更慢的程度就行。

## 顶点格式

存储在缓冲对象中的顶点属性可以有出人意料的多种格式。本部分教程通常使用 32 位浮点数据，但那远非最佳情况。

这里说的**顶点格式**，具体是指传给 `glVertexAttribPointer` 调用的那一组数值，它们描述了每个属性在缓冲对象中如何对齐。

### 属性格式

每个属性都应该占用尽可能少的空间。这是出于性能考虑，同时也节省内存。对缓冲对象来说，这两者通常是一致的。你在内存中存储的数据越少，它到达顶点着色器的速度就越快。

属性也可以像纹理一样用归一化整数格式存储。这对颜色和纹理坐标最为有用。例如，要让一个属性存储为 4 个无符号归一化字节，可以使用：

```cpp
glVertexAttribPointer(index, 4, GLubyte, GLtrue, 0, offset);
```

如果你想把一个法线存为归一化的有符号短整数，可以使用：

```cpp
glVertexAttribPointer(index, 3, GLushort, GLtrue, 0, offset);
```

另外还有几种专门的格式。`GL_HALF_FLOAT` 可用于 16 位浮点类型。当你需要 [-1, 1] 之外的值、但又不需要完整的

非归一化整数同样可以使用。它们在 GLSL 中直接映射为浮点值，所以一个非归一化的 16 会映射到 GLSL 值 16.0。

所有这些格式最好的一点是，使用它们在性能上*毫无*代价。它们都会被静默转换成浮点值供顶点着色器使用，没有任何性能损失。

### 交错属性

属性并不都必须来自同一个缓冲对象；多个属性可以来自多个缓冲对象。然而，只要可能，就应当避免这种做法。此外，同一缓冲中的属性只要可能就应当彼此交错存放。

考虑 C++ 中的一个结构体数组：

```cpp
struct Vertex
{
  float position[3];
  GLubyte color[4];
  GLushort texCoord[2];
}

Vertex vertArray[20];
```

`color` 在 `Vertex` 结构体中的字节偏移是 12。也就是说，从 `Vertex` 结构体的开头算起，`color` 变量从第 12 字节开始。`texCoord` 变量从第 16 字节开始。

如果我们在 `vertArray` 与一个缓冲对象之间做 memcpy，并希望设置属性从这份数据中取值，那么可以利用步长和偏移把位置摆正确：

```cpp
glVertexAttribPointer(0, 3, GL_FLOAT, GLfalse, 20, 0);
glVertexAttribPointer(1, 3, GL_UNSIGNED_BYTE, GL_TRUE, 20, 12);
glVertexAttribPointer(3, 3, GL_UNSIGNED_SHORT, GL_TRUE, 20, 16);
```

第五个参数是步长。步长是从该属性的一个实例开头到下一个实例开头的字节数。这里的步长被设为 `sizeof`(`Vertex`)。C++ 规定结构体的大小就表示数组中不同实例之间的字节偏移。所以这就是我们的步长。

各个偏移表示第一个元素在缓冲对象中的位置。它们与结构体中的偏移一致。如果我们把这份数据加载到缓冲对象起始位置之后的某个地址，就需要把这些值加上上传数据的起始位置。

决定数据如何这样打包时有一些陷阱。首先，把每个属性都放在 4 字节对齐上是个好主意。这可能意味着要在结构体中引入显式的填充（空隙）。如果不对齐到 4 字节，某些硬件会出现严重的性能下降。

其次，把任何交错顶点数据的大小限制为 32 字节的整数倍是个好主意。违反这一条没有违反 4 字节对齐规则那么严重，但如果交错顶点数据的总大小是 48 字节之类的，性能有时会不够理想。或者像我们例子中的 20 字节。

### 打包建议

如果你需要的就是最小的顶点数据大小，可以考虑这些打包技巧。

颜色一般不需要超过 3 到 4 字节。每个分量一个字节。

纹理坐标，特别是那些被钳制在 [0, 1] 范围内的，几乎从不需要超过 16 位精度。所以使用无符号短整数。

法线应尽可能存储为有符号的 2_10_10_10 格式。法线通常不需要那么高的精度，尤其是你反正要对它们做归一化。这个格式正是为法线设计的，所以请使用它。

位置是最难处理的，因为需求变化太大。如果你愿意修改顶点着色器并投入一些工作，那么通常可以用 16 位有符号归一化短整数。

这里的关键是一份特殊的缩放/平移矩阵。在离线工具中准备数据时，你取出模型的浮点位置，并确定模型在三个轴向上的最大范围。这形成一个包围模型的包围盒。盒子的中心就是你新模型的中心，你施加一次平移把点移到该中心。然后你施加一次非均匀缩放，把点从它们的范围区间变换到有符号归一化值的 [-1, 1] 区间。你把用到的偏移和缩放作为网格数据的一部分保存起来（不存进缓冲对象）。

到了渲染模型的时候，你只需把变换反过来。你构建一个缩放/平移矩阵，撤销把它们送进有符号归一化区间时所做的操作。注意这个矩阵不应该应用到法线上，因为法线并没有以这种方式压缩过。对这个变换来说，完整的矩阵乘法甚至都是浪费；一次缩放加平移用简单的向量乘加就能完成。

## 同步

GPU 的性能在很大程度上来自这一点：一旦你告诉它要做什么，它就去做自己的事，不再需要进一步干预。作为程序员，你并不在意某一帧是否还没完成。你唯一关心的是用户能在这一帧就绪时看到它。

用户可以做某些事情，让这种完美的异步活动戛然而止。这些事情被称为同步事件。

OpenGL 的定义允许异步行为：你发出的命令不必在函数结束时完成（大多数情况下）。不过 OpenGL 是这样定义的：如果存在异步行为，用户*不能*察觉它。也就是说，如果你调用 glDrawArrays，这条命令的效果应当仅仅基于 OpenGL 的当前状态。这意味着，如果 glDrawArrays 命令在更晚的时候才执行，OpenGL 实现必须采取一切必要手段，防止后续的状态变化影响结果。

因此，如果你调用 glDrawArrays 从某个缓冲对象读取数据，紧接着又对这个缓冲对象调用 glBufferSubData，那么 OpenGL 实现可能不得不在 glBufferSubData 调用中暂停 CPU，直到 glDrawArrays 至少完成了顶点处理。不过，实现也可能只是把你试图传输的数据复制到它自己分配的一块内存中，等 glDrawArrays 完成后再上传到缓冲对象。你无法确定会发生哪一种。

同步事件通常包括修改数据对象。也就是说，改变缓冲对象或纹理的内容。一般来说，改变对象的简单状态，比如某个 VAO 提供哪些属性或纹理参数，并不会引起同步问题。改变 OpenGL 全局状态同样不会引起同步问题。

有一些方法允许你修改数据对象，同时仍让 GPU 保持异步。但对它们的任何讨论都远远超出了本书的范围。只要记住：正在使用中的数据对象大概不应该被修改其数据。
