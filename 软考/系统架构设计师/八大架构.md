## 1. 信息系统架构设计

**TOGAF**（开放的企业架构框架标准）——为方法、标准、方法论和企业架构专业人员提供一致性保障。

- **四个目标**：确保关键利益相关方对使用相同语言、避免被"锁定"到专有解决方案、节省时间和资金、实现可观的 ROI。
- **核心思想（四个）**：模块化架构、内容框架、扩展指南、架构风格。
- **关键是 ADM**（架构开发方法）：按架构领域开发顺序排列成环形的多个阶段构成。
- **ADM 三个级别的迭代**：基于 ADM 整体的迭代、多个开发阶段间的迭代、一个阶段内部的迭代。

**ADM 全生命周期十阶段** ⭑

| 阶段 | 内容 |
| ---- | ---- |
| 预备阶段 | 为实施企业架构项目做好准备，包括定义组织机构、特定架构框架、架构原则等 |
| 需求管理 | 完成需求的识别、保管和交付，相关 ADM 阶段按优先级顺序对需求进行处理 |
| A 架构愿景 | 设置 TOGAF 项目的范围、约束和期望 |
| B 业务架构 | 开发业务架构 |
| C 信息系统架构 | 分为**应用架构**和**数据架构**两个子阶段 |
| D 技术架构 | 开发技术架构 |
| E 机会及解决方案 | 进行实施和迁移规划，确定各阶段交付物 |
| F 迁移规划 | 制定详细实施和迁移计划 |
| G 实施治理 | 监督项目实施 |
| H 架构变更管理 | 监控变更，确保架构响应企业需求 |

**信息系统生命周期五阶段** ⭑

> 规划 → 分析 → 设计 → 实施 → 运行维护

- **关键区分**：**系统分析回答"做什么"**（逻辑模型），**系统设计回答"怎么做"**（物理模型）。这是最常考的辨析点。
- 运行维护阶段：系统投入运行后需**经常进行维护和评价**，记录运行情况，评价系统的工作质量和经济效益。

## 2. 层次式架构设计

软件体系**层次式结构是最通用的架构**（也叫 N 层架构模式），一般分为**表现层（展示层）/ 中间层（业务层）/ 数据访问层（持久层）/ 数据层**。

### 2.1 表现层

- **UIP 框架**：提供了扩展框架，用于简化用户界面与商业逻辑代码的分离。
  - **UIC（User Interface Components）**：用户**看得见**、与之交互的组件，负责获取数据并返回结果。
  - **UIPC（User Interface Process Components）**：**用户看不见**，协调用户界面各部分，配合后台活动（导航、工作流控制、状态和视图管理）。
- **表现层动态生成设计**：基于 XML，实现界面配置（静态）、界面动态生成、界面定制（动态）。构成：数据获取类 + DOM API + 界面配置模块 + 数据库 + XML 配置文件。

### 2.2 中间层

- **组件设计**：业务逻辑组件分为**接口**（定义业务逻辑组件）和**实现**两类 → **面向接口编程**，为更好解耦。
- **工作流设计**：业务流的全部或部分自动化，包含**6 个基本模块**——过程定义工具、工作流 API、工作流引擎、客户端应用、调用应用、管理监控工具。
- **五种接口** ⭑：① 过程定义导入/导出接口（转换格式和 API）② 客户端应用程序接口 ③ 应用程序调用接口 ④ 工作流机协作接口（定义相关标准，不同厂商产品间任务项传递）⑤ 管理和监控接口。
- **实体设计**：业务逻辑层实体提供对业务数据的状态编程访问；如 **XML 的 DataSet**（以数据为中心的模型到更面向对象的表示）。
- **业务框架**：采用**容器**形式（IoC/DI），降低业务层和相邻各层的耦合。三层结构：
  - **Domain Model**：领域层业务对象，仅包含业务属性。
  - **Service**：应用过程的服务实现。
  - **Control**：服务控制器，服务之间的纽带。

### 2.3 数据访问层

**五种数据访问模式** ⭑

| 模式 | 说明 |
| ---- | ---- |
| ① 在线访问 | 占用一个数据库连接，读数据不间断地与后台数据源交互 |
| ② **DAO**（Data Access Object） | 标准 J2EE 设计模式，把底层数据访问与高层业务逻辑分离 |
| ③ **DTO**（Data Transfer Object） | 经典 EJB 设计模式，数据容器，用于跨越进程/网络边界传输数据；**本身不含业务逻辑** |
| ④ 离线数据模式 | **以数据为中心**，从数据源获取后按预定义结构存放，成为应用中心，与后台数据源断开 |
| ⑤ **ORM** | 对象/关系映射，在对象与关系数据库之间转换 |

- **工厂模式**：先定义抽象 `DataAccess`，再由具体类实现（SQL Server / Oracle / JDBC），用抽象工厂实现数据库切换。
- **事务处理**：JDBC 中 `auto-commit` 默认开启；须先 `commit()` 或 `rollback()` 才能将多条 SQL 组成一个事务；最后一次 `commit()` 之后的 SQL 在下次 `commit()` 时才提交。
- **连接对象管理**：静态的**连接池**（系统初始化时分配好，不能随意关闭）→ 解决资源频繁分配、释放问题。
  - 请求数据库连接时：若池有空闲连接则分配；若无空闲连接，找最合适的连接给客户；客户释放时按是否被复用做不同处理，未被使用则放回连接池。

### 2.4 数据架构规划与设计

- **XML 与数据库融合**：XML 文档分两类——
  - **以数据为中心的文档**：结构规则、同构、嵌套层次少、混合内容少 → 用于**传递信息、产品介绍、e-mail**。
  - **以文档为中心的文档**：结构不规则、异构、混合内容多、元素顺序有关系 → 用于**存储 Web 数据**。
- **XML 两种存储方式**：基于**文件**的存储（无法获取 XML 结构信息，查询定位难、管理难）、**数据库**存储（数据融合，管理结构化和半结构化、并发控制、一致性、管理方便）。

### 2.5 物联网层次架构 ⭑

| 层 | 作用 | 类比人体 |
| -- | ---- | -------- |
| **感知层** | 识别物体、采集信息（二维码、RFID、摄像头、GPS、传感器、M2M 终端）→ 解决物理世界数据获取 | 皮肤和五官 |
| **网络层** | 传递和处理信息（通信网与互联网融合、网络管理中心、信息中心和智能处理中心） | 神经中枢和大脑 |
| **应用层** | 与行业需求结合实现广泛智能化，提供特定服务 → 解决信息处理和人机交互 | 社会分工 |

## 3. 云原生架构设计

- **内涵**：基于云原生技术的一组**架构原则和设计模式的集合**，把**非业务代码部分最大化剥离**，让云设施接管弹性、韧性、安全、可观测性、灰度等非功能特性。
- **代码分三部分**：业务代码、三方软件、处理非功能特性的代码。
- **特点**：代码结构发生巨大变化；非功能性特性大量委托给云原生解决；高度自动化的软件交付。

### 3.1 七大原则 ⭑（必背）

| 原则 | 要点 |
| ---- | ---- |
| **服务化** | 拆分为微服务/小服务架构，按不同生命周期分别迭代 |
| **弹性** | 部署规模随业务量自动伸缩，无须事先容量规划 |
| **可观测** | 通过日志、链路跟踪、度量，让调用耗时/返回值/参数清晰可见 |
| **韧性** | 依赖的软硬件组件异常时的抵御能力 |
| **所有过程自动化** | 标准化交付过程 + 在标准化基础上自动化（IaC、GitOps、OAM、Operator） |
| **零信任** | 默认不信任网络内外部任何人/设备/系统，以身份为中心重构访问控制 |
| **架构持续演进** | 架构本身必须是一个具备持续演进能力的架构 |

### 3.2 主要架构模式

服务化架构（微服务/小服务）、Mesh 化架构、Serverless、存储计算分离、分布式事务、事件驱动架构（EDA）。

> 常见误答：部分教材/考点版本把**「可观测架构」（Logging / Tracing / Metrics）**也单列为一种模式，共 **7 种**；讲义只列 6 种。答题时按题目给定的教材版本写，**别把数目写死**。

### 3.3 相关技术

- **容器**：标准化的软件单元，把应用及其所有依赖项打包，不受运行环境限制，在不同计算环境间快速、可靠运行。
- **Kubernetes（K8s）**：容器编排的事实标准。核心能力——资源调度、应用部署与管理、自动修复、服务发现与负载均衡、弹性伸缩、声明式 API、可扩展性架构、可移植性。
- **微服务四条设计约束** ⭑：
  1. **个体约束**：功能在业务领域划分上相互独立，低耦合、单一职责。
  2. **横向关系**：通过服务发现和可交互性处理服务之间的横向关系。
  3. **纵向约束**：数据存储隔离（**DSS**），数据访问通过服务提供的 API 进行。
  4. **全局约束**：全自动化，支持蓝绿、金丝雀等不同发布策略。
- **微服务框架**：Apache **Dubbo**（阿里，高性能 RPC，智能负载均衡、自动服务注册发现）、Spring Cloud、Eclipse MicroProfile、**Tars**（腾讯）、SOFAStack（蚂蚁）、**DAPR**（微软，可移植、无服务器、事件驱动运行时）。
- **Serverless 四特征**：全托管的计算服务、通用性、自动弹性伸缩、按量计费；**FaaS 是最具代表性的产品形态**。关注点：**计算资源弹性调度、负载均衡和流控、安全性**。
- **服务网格 Service Mesh**：把服务间的连接、安全、流量控制和可观测等通用功能**下沉为平台基础设施**。架构分 **Data Plane（Proxy）** 和 **Control Plane**（Istio：Pilot / Citadel / Galley）；由控制平面下发**服务发现、熔断、限流**等策略。

## 4. 面向服务的架构设计（SOA）

### 4.1 SOA 与微服务对比 ⭑（高频表）

| 维度 | SOA 架构 | 微服务架构 |
| ---- | -------- | ---------- |
| 服务粒度 | 拆分为多个独立的功能模块 | 更精细，以独立进程方式存在 |
| 架构特点 | **集中式**的技术架构 | **去中心化**的分布式架构 |
| 服务总线 | 以 **ESB** 链接各个子系统 | 去掉了 ESB 企业服务总线 |
| 耦合程度 | 模块间松耦合、但应用服务间相互依赖 | 降低了耦合度，互相之间无影响 |
| 接口方式 | 通过调用接口进行交互 | 更通用（如 HTTP RESTful），无关语言、平台 |
| 数据库 | 集中式数据管理 | 不同微服务采用不同数据库技术，数据源唯一、服务独立 |
| 部署方式 | 相互依赖导致部署复杂 | 分布式去中心化部署，极易扩展和维护 |
| 响应速度 | 通过 ESB 交互，响应速度较慢 | 去掉 ESB 后，响应速度提升 |
| 系统复杂性 | 服务间依赖导致复杂性较高 | 降低了系统复杂性 |
| 适用场景 | 有效整合应用系统的各项业务功能 | 在互联网业务场景下更适合 |
| 演进关系 | 面向服务的架构、组件模型 | SOA 架构的进一步优化 |

### 4.2 主要协议和规范

- **UDDI**：统一描述、发现和集成协议，在互联网上相互作用并共享信息的注册体系。
- **WSDL**：Web 服务描述语言，基于 XML，描述三个基本属性——**服务做什么、如何访问服务、服务位于何处**。
- **SOAP**：基于 XML 的简单协议，包括 **4 部分**——① 信封（描述消息内容、谁发送、谁接收）② 编码规则 ③ RPC 表示 ④ 绑定（底层协议交换信息）。

### 4.3 设计原则（8 条）

① 无状态（避免服务请求者依赖服务提供者的状态）② 单一实例 ③ 明确定义的接口 ④ 自包含和模块化 ⑤ 粗粒度（消息量较大，但交互频度低）⑥ 服务之间的松耦合性 ⑦ 重用能力 ⑧ 互操作性、兼容性和策略声明。

### 4.4 设计模式

- **服务注册表模式**：服务注册、服务注册服务、服务请求者三部分。
- **企业服务总线 ESB 模式**：中间件技术实现的、支持异构环境中的服务以及基于消息和事件驱动模式的交互，具有适当服务质量和管理。
  - 交互过程：先由**服务请求者**发起一次交互，产生服务请求消息 → ESB 根据请求消息中的服务名/接口名查找目标组件 → 将消息转发至目标组件 → 将结果逆传回请求者。**不是点对点的直接交互，而是由事件驱动的消息交互模式**。
  - **ESB 六大核心功能** ⭑：① 位置透明的路由和寻址服务 ② 提供服务的注册和管理 ③ 支持多种消息传递范型（请求/响应、发布/订阅等）④ 支持多种可广泛使用的传输协议 ⑤ 支持多种数据格式及相互转换 ⑥ 提供日志和监控功能。
- **微服务模式**：不再强调庞大的 ESB，把 SOA 思想进入单个业务系统内部，实现真正的组件化。
- **常见服务设计模式** ⭑：① **聚合型微服务**（数据信息加工处理后再发布）② **链式微服务**（客户端请求 → 经过合并处理的响应，形成一条调用链）③ **数据共享微服务**（多个微服务共享缓存或数据库）④ **异步消息传递微服务**（消息队列，异步通信）。
- **微服务架构问题与挑战**：分布式布局带来的复杂性；各微服务含不同数据库，增加测试复杂性与数据一致性风险；大规模应用中监控、管理、分发、扩容困难。

## 5. 嵌入式系统架构设计

### 5.1 软件架构原理与特征

- **两种架构模式**：**层次化架构**（高层抽象与低层具体概念间存在依赖关系；分层构成一个主要元素和接口；**封闭型**——一层对象只能调用下一层；**开放型**——可调用同一层或更低任意一层）、**递归架构**（把非常复杂的系统进行分解，自顶向下：从系统层级开始标识结构对象；自底向上：从底层开始逐步抽象）。
- **ES 组成**：硬件相关的底层驱动、系统软件、设备驱动接口、通信协议、图形界面、标准化浏览器。
- **嵌入式操作系统特点**：可裁剪性、可移植性、强实时性、强稳定性、弱交互性、硬件适配性、固化代码、操作简单方便、较强的硬件适应性。
- **体系结构四种**：整件结构、层次结构、客户/服务器结构、面向对象结构。
- **内核**：管理系统的各种资源，连接应用程序和硬件。分**宏内核（单片）**和**微内核**。

### 5.2 实时调度算法 ⭑（选择题常考）

| 算法 | 中文 | 优先级规则 |
| ---- | ---- | ---------- |
| **EDF** | 最早截止时间优先 | 根据任务的**开始截止时间**确定优先级，越早越高 |
| **LLF** | 最低松弛度优先 | 根据任务**紧急（松弛）程度**确定，越紧急越高。松弛度 = 必须完成时间 − 本身执行时间 − 当前时间；**越富裕越松弛** |
| **RMS** | 单调速率调度 | **静态**优先级调度；**周期越短，优先级越高** |

- **任务间关系**：相互独立、竞争、同步、通信。
- **任务间通信方式**：共享内存、信号量、消息队列、Socket 和远程调用、Signals（信号，用于异步处理，是中断机制的一种模拟）。
- **竞争**：任务间争夺资源；**同步**：任务之间存在先后关系。

### 5.3 嵌入式数据库 ⭑（三类）

| 类型 | 要点 |
| ---- | ---- |
| **内存式数据库 MMDB** | 实时性、移动性、伸缩性；**主拷贝常驻内存**，活动事务只与实时内存数据库的内存数据交互 |
| **基于文件的数据库 FDB** | 以文件方式存储，按一定格式储存在磁盘中；典型产品 **SQLite**。特点：不需要网络配置和管理，不需要通过数据库访问服务器，减少网络访问消耗、简化管理 |
| **基于网络的数据库 NDB** | 基于手机 4G/5G 移动通信；把嵌入式设备作为远程数据库的客户端。三部分：**客户端、通信协议、远程服务器** |

### 5.4 设计方法 DARTS ⭑

- **RTSA（实时结构化分析法）**：用 **DTD** 表示。步骤：① 用实时结构化分析法开发系统阶段（SCD 和 STD）② 将系统划分为多个并发任务 ③ 任务接口定义（分析数据流/控制流）④ 设计每个任务（一个任务代表一个程序模块）⑤ 设计过程的结果（任务规范 + 任务分解）。
- **优点**：强调把系统分解成并发任务并提供确认标准；提供详细的接口和任务间接口指南；强调**任务结构图（STD）**的重要性；提供从 RTSA 阶段到实时设计的转换。
- **不足**：用结构化方法把任务创建成程序模块，而非完全用 **HIM 封装数据存储**；若 RTSA 阶段没做好，创建任务非常困难。

## 6. 通信系统架构设计

### 6.1 网络拓扑架构

| 场景 | 可选架构 |
| ---- | -------- |
| **局域网** | 单核心架构、双核心架构、环形架构、层次型架构 |
| **广域网** | 单核心、双核心、环形、**半/全冗余**、**对等子域**、**层次子域** |

- 通用规律：**单核心**结构简单、投资节约，但**单点故障致命**；**双核心**可冗余、可靠性高，但投资高；**环形**具备自愈保护、节省光纤，但投资高、易成环路；**层次型（层次子域）**扩展性好、分层排障便于维护，但路由/冗余设计难度高。

### 6.2 网络构建和设计方法

- **网络需求分析**：网络构建及开发过程的**起始环节**，明确客户真实诉求，围绕业务需求、用户需求、应用需求、计算机平台需求和网络需求，最终形成**网络需求规格说明书**。
- **网络技术遴选及设计**：局域网（生成树协议 STP、虚拟局域网 VLAN、无线城域网、线路冗余、交换设备功能）；广域网（远程接入技术、广域网互联技术）。
- **地址规划模型三条原则**：① 使用结构化层次化的子网地址模型（层次化规划）② 通过中心授权机构管理地址 ③ 编址授权下发 ④ 为终端用户设备指派动态地址（移动性用户）⑤ 私有地址合理使用（NAT）。
- **路由协议选择**：协议类型（距离矢量 / 链路状态）、度量值、顺序、层次化与非层次化、内部与外部、分类与无类、静态路由指定。
- **层次化网络模型设计**：**核心层、汇聚层、接入层** ⭑。
- **网络高可用设计方法**：提高网络可靠性、缩短网络恢复时间。
- **网络安全** ⭑：防火墙、VPN（虚拟专用网）、访问控制技术、网络安全隔离、网络安全协议（SSL / SET / HTTPS）、网络安全审计。
- **绿色网络设计原则**：**标准化、集成化、虚拟化、智能化**。

## 7. 安全架构设计

### 7.1 安全威胁

- **按对象分类**：物理安全、通信链路安全、网络安全、操作系统安全、应用系统安全、管理系统安全。
- **常见威胁（14+）**：信息泄露、破坏信息完整性、拒绝服务、非法使用（非授权访问）、窃听、业务流分析、假冒、旁路控制、授权侵犯、**特洛伊木马**、**陷阱门（后门）**、抵赖、**重放**、计算机病毒、人员渎职、媒体废弃物、物理侵入、窃取、业务欺骗。

### 7.2 安全架构的构成

安全架构是架构建面向安全性方向的一种细分，包括**三部分** ⭑：
1. **产品安全架构**：构建产品安全质量属性的主要组成部分及它们的关系，目标是**不依赖外部防护系统**的前提下从源头打造自身安全。
2. **安全技术体系架构**：构建通用的安全技术基础设施（安全基础设施、安全工具和技术、安全组件与支持系统）。
3. **审计架构**：独立的审计部门或所能提供的风险发现能力。

### 7.3 安全模型 ⭑（必背）

| 模型 | 关注点 | 核心规则 |
| ---- | ------ | -------- |
| **HRU** | 基础模型 | 访问控制矩阵 + 操作 |
| **Bell-LaPadula（BLP）** | **机密性** | **不上读、不下写**（低级别主体不能读高级别客体，高级别主体不能写低级别客体） |
| **Biba** | **完整性** | **不下读、不上写**；三条规则：星完整性规则（低完整性主体不能写高完整性客体）、简单完整性规则（高完整性主体不能从低完整性客体读取）、调用属性规则（低不能从高调用） |
| **Clark-Wilson** | **商业数据完整性** | 三元素 Subject / Program / Object；**权限分离**；要求**审计能力**；CDI（受完整性保护客体）/ UDI（不受保护客体）、IVP（完整性验证过程）/ TP（转换过程） |
| **Chinese Wall**（Brew and Nash） | **防利益冲突** | 主体访问过的信息与公司数据集一致 → **墙内可访问**；前提是主体未对属于其他公司数据集进行过访问。适用于金融、咨询等存在利益冲突的行业 |

> 常见误答：BLP 与 Biba 的读/写方向**恰好相反**，别背反。上下指的是**安全级别 / 完整性级别**，不是架构图里的楼层。关注点也常被混淆——BLP 管**机密性**，Biba 与 Clark-Wilson 管**完整性**。

### 7.4 WPDRRC 模型 ⭑

- **六个环节**（有时序性和动态性）：**预警 Warning、保护 Protect、检测 Detect、响应 Respond、恢复 Restore、反击 Counterattack**。
- **三个要素**：**人员（核心）、策略（桥梁）、技术（保证）**。

### 7.5 系统架构脆弱性分析 ⭑（案例高频，能按架构逐条说）

| 架构 | 脆弱性表现 |
| ---- | ---------- |
| **分层架构** | ① **层间脆弱性**：底层出错会导致整个程序无法运行 ② **层间通信脆弱性**：层间须引入通信机制，操作延层传递会造成**性能下降** |
| **C/S 架构** | ① 客户端软件脆弱性（需装客户端，面临被分析、数据被截取）② 网络开放性脆弱性（客户端在客户端存储用户名、密码，带来安全隐患）③ 网络协议脆弱性（多为二层结构/客户端直接读服务端数据；不安全的数据包共享，易受攻击） |
| **B/S 架构** | 系统**使用 HTTP 协议**，比 C/S 更易被病毒入侵（HTTPS 有所提升，但仍弱于 C/S） |
| **事件驱动架构** | ① 组件脆弱性（削弱对系统的控制力）② 组件间数据交换脆弱性 ③ 组件间逻辑关系脆弱性 ④ 事件驱动**容易进入死循环** ⑤ 高并发易导致数据不正确、丢失 ⑥ 固定流程脆弱性（可响应流程固定，操作不当易引发安全问题） |
| **MVC 架构** | ① 复杂性带来脆弱性（视图与控制器分离，增加系统复杂性、产生过多更新操作，降低性能）② 视图与控制器间紧密连接（无控制器时视图作用有限，反之亦然）③ 视图对模型低效率访问（需多次调用模型操作） |
| **微内核架构** | ① 难以进行良好的整体优化 ② 微内核系统的**进程间通信开销**比单一内核大得多 ③ **通信损失率高**（通信与执行效率的损失） |
| **微服务架构** | ① 需处理分布式系统的复杂性 ② 需设计服务之间的通信机制（传递速度慢或不可用会造成局部实效）③ 服务管理复杂（生产环境需管理多个服务实例，需全局统筹） |

## 8. 大数据架构设计

### 8.1 Lambda 架构

- **设计目的**：提供满足大数据系统关键特性的架构，包括高容错、低延迟、可扩展。整合**离线计算与实时计算**，融合不可变性、读写分离和复杂性隔离原则，用于**同时处理离线和实时数据**。
- **应用场景**：机器学习、物联网、流处理。
- **三层** ⭑

| 层 | 说明 |
| -- | ---- |
| **批处理层 Batch Layer** | 存储数据集（全量），在数据集上**预先计算**查询函数，并构建查询所对应的 View 供查询 |
| **加速层 Speed Layer** | 只处理**最近的增量数据流**，为效率在接收新数据后不断更新 **Real-time View**；流处理层的数据可能不准确、不全面 |
| **服务层 Serving Layer** | 用于**合并** Batch View 和 Realtime View 中的结果数据集到最终数据集，用于响应应用层的查询请求 |

- **技术栈**：Hadoop（HDFS 存储主数据）、Spark / Storm（速度层）、HBase / Cassandra（服务层）、Hive（创建可查询的视图）。
- **优点**：容错性好、查询灵活度高、易伸缩、易扩展。
- **缺点**：全场景覆盖带来编码开销；针对具体场景重新离线训练收益不大；重新部署和迁移成本高。
- **与事件溯源（Event Sourcing）**：三个核心观点——① 整个系统以事件为驱动，所有业务都由事件驱动完成 ② 事件是核心，系统以事件为基础，事件要保存在某种存储上 ③ 业务数据只是事件产生的视图，不一定保存到数据库中。
- **与 CQRS**：CQRS 分离**读操作（查询）**和**写操作（修改）**，将能改变数据模型状态的命令和对模型状态的查询操作实现分离。

### 8.2 Kappa 架构

- **原理**：在 Lambda 基础上优化，**删除了 Batch Layer**，将数据通道用**消息队列**进行替代，依旧以**流处理**为主；数据在**数据湖**里追加存储，当需要离线分析或再次计算时，将数据湖中数据再次经过消息队列重播一次即可。
- **与 Lambda 的关系**：Kappa **不是 Lambda 的替代架构，而是其简化版本**——放弃了批处理的支持，更擅长**业务本身增量数据写入**场景的分析需求；Lambda **支持批处理**，更适合对**历史数据**分析查询。

**Lambda vs Kappa 对比与选型** ⭑

| 对比内容 | Lambda 架构 | Kappa 架构 |
| -------- | ----------- | ---------- |
| 复杂度与开发维护成本 | 需要维护两套系统（引擎），复杂度高、成本高 | 只需要维护一套系统，复杂度低、成本低 |
| 计算开销 | 需要一直运行批处理和实时计算，计算开销大 | 必要时才进行全量计算，开销相对较小 |
| 实时性 | 满足实时性 | 满足实时性 |
| 历史数据处理能力 | **批量全量处理、吞吐量大、历史数据处理能力强** | 流式全量处理、吞吐量相对较低、历史数据处理能力相对低 |

- **选型四因素**：业务需求与技术需求（Hadoop/Spark/Storm → Lambda；Flink → Kappa）、复杂度、开发维护成本、历史数据处理能力。
- **Kappa 缺点**：① 消息中间件缓存的数据量和回溯数据有性能瓶颈 ② 实时处理时因数据流先后顺序问题，可能导致数据丢失 ③ 抛弃离线数据处理模块，放弃了离线计算更稳定可靠的特点；双系统维护成本高、两套代码带来后期运维困难。
- **Kappa+**：流式计算框架直接读 HDFS 数据仓库数据，实现**实时计算和历史数据 backfill**。
