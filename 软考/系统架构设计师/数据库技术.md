## 一、三级模式与两级映像 ⭑

| 模式 | 别名 | 对应数据库对象 | 特点 |
| ---- | ---- | -------------- | ---- |
| **外模式** | 用户模式、子模式 | **视图（View）** | 用户能看到并使用的那部分数据；**一个数据库可有多个外模式** |
| **模式** | 概念模式、逻辑模式 | **基本表（Table）** | 全体数据的逻辑结构与特征；**一个数据库只有一个模式** |
| **内模式** | 存储模式、物理模式 | **存储文件（File）** | 数据的物理存储结构与存取方式；**只有一个** |

**两级映像 = 数据独立性的来源**：

| 映像 | 位置 | 保证的独立性 | 含义 |
| ---- | ---- | ------------ | ---- |
| **外模式 / 模式** | 视图 ↔ 基本表 | **逻辑独立性** | 基本表改了，只需改映像，**视图与应用程序不用改** |
| **模式 / 内模式** | 基本表 ↔ 存储文件 | **物理独立性** | 存储方式改了，只需改映像，**模式与应用程序不用改** |

> 常见误答：把「模式」当成用户模式。**模式 = 全体数据的公共视图 = 基本表**；**外模式才是用户视图**。题目问"表示用户使用的部分数据"选**外模式**，"描述记录间联系/操作/完整性/安全性要求"选**概念模式**。

## 二、数据库设计六阶段 ⭑

| 阶段 | 干什么 | 产出物 |
| ---- | ------ | ------ |
| ① **需求分析** | 分析数据存储要求，获得**信息、处理、系统**三方面要求 | **数据流图（DFD）、数据字典、需求说明书** |
| ② **概念结构设计** | 设计 **E-R 图**（实体-联系图），自底向上逐层分 E-R 图再合并 | **E-R 模型**（概念结构模型） |
| ③ **逻辑结构设计** | 把 E-R 图转换成**关系模式**（表结构） | **关系模式 + 视图 + 完整性约束** |
| ④ **物理设计** | 确定**数据分布、存储结构、访问方式** | 存储结构与访问方式说明 |
| ⑤ **数据库实施** | 建库、编写调试应用程序、组织数据入库、试运行 | 具体数据库实例 |
| ⑥ **运行与维护** | 系统评价、调整与修改 | — |

> ⚠️ 关系模式（"表结构"）是在**逻辑结构设计**阶段产生的，不是概念设计（出 E-R 图）、也不是物理设计。

**E-R 图合并的三类冲突**（合并分 E-R 图时）：

| 冲突 | 含义 |
| ---- | ---- |
| **属性冲突** | 同一属性存在于不同的分 E-R 图 |
| **命名冲突** | 同名不同义，或同义不同名 |
| **结构冲突** | 同一实体在不同分 E-R 图中：属性不同，或**一个图里是实体、另一个图里是属性** |

## 三、E-R 模型

| 元素 | 图形 | 说明 |
| ---- | ---- | ---- |
| **实体** | 长方形 | 客观存在且可相互区别的事物 |
| **属性** | 椭圆 | 实体的特性；分为简单/复合、单值/多值、NULL、派生属性 |
| **联系** | 菱形 | 实体内部及实体之间的联系，两端要写联系类型 |
| **码（key）** | — | 唯一标识实体的属性集 |

- **强实体 vs 弱实体**：弱实体**依赖于强实体存在**（如"课程"与"学生"）。
- **实体集**：具有相同类型和共享相同属性的实体集合。
- **联系类型**：1:1、1:N、M:N。
- **递归实体**：「一个实体实例与**同一实体类型**的其他实例存在联系」——如员工与上级。

### E-R 模型 → 关系模型的三条转换规则 ⭑

| 联系类型 | 转换方式 |
| -------- | -------- |
| **1:1** | 联系可放到**任意一端**实体中作为一个属性（须保证 1:1 两端关联），也可单独作为一个关系模式 |
| **1:N** | 联系可单独作为一个关系模式，也可**在 N 端加入 1 端实体的主键**（更常用） |
| **M:N** | 联系**必须单独**作为一个关系模式，其主键是 **M 端与 N 端主键的联合** |

> ⚠️ 口诀：**M:N 必须单独建表**（否则无法表达多对多）；1:1 / 1:N 可以"并"进实体里。

## 四、函数依赖与码 ⭑

- **函数依赖**：给定 X 能唯一确定 Y，称 X 确定 Y（记 X→Y）。
- **部分函数依赖**：A 可确定 C，(A,B) 也可确定 C——`(A,B)` 中**一部分**就能确定 C。
- **传递函数依赖**：当 A 与 B **不等价**时，A→B、B→C，则 A 传递确定 C；若 A、B 等价则不存在传递。

| 概念 | 定义 |
| ---- | ---- |
| **超键** | 能唯一标识元组的属性集 |
| **候选键** | **超键中去掉冗余属性**后剩下的属性 |
| **主键** | **任选一个候选键**即为主键 |
| **外键** | 其他表的主键 |
| **主属性** | **候选键内**的属性；其余为非主属性 |

## 五、范式（1NF → 4NF）⭑

| 范式 | 条件 | 消除的"坏"依赖 |
| ---- | ---- | -------------- |
| **1NF** | 关系中的**每一个分量必须不可再分**（无重复列/多值列） | — |
| **2NF** | 满足 1NF，且**每个非主属性完全函数依赖**于任何候选键 | 消除非主属性对码的**部分函数依赖** |
| **3NF** | 满足 1NF，且表中不存在非主属性对码的**传递依赖** | 消除非主属性对码的**传递函数依赖** |
| **BCNF** | 在 3NF 基础上，**每个依赖的左边决定因素都必然包含候选键** | 消除**主属性**对码的部分和传递函数依赖 |
| **4NF** | 限制属性间不允许有非平凡且非函数依赖的**多值依赖** | 消除非平凡且非函数依赖的**多值依赖** |

**用讲的例子串一遍**（学生表：学号、学生姓名、系名、系主任、课程号、成绩）：
- 原表：一个"课程号"列里塞多个值 → **违反 1NF**（先拆成不可分）。
- 拆成 (学号,课程号)→成绩：但 学号→姓名、系名→系主任，**非主属性部分依赖/传递依赖** → 不满足 2NF / 3NF。
- 继续拆：学生(学号,姓名,系名)、系(系名,系主任)、选课(学号,课程号,成绩) → **每张表都属于 3NF**。

> ⚠️ 一句判别技巧：**候选键只有一个属性时，不可能存在部分依赖**（因为不存在"复合码的一部分"）；**BCNF 比 3NF 严**，区别在于是否把"主属性对码的依赖"也算进去。

## 六、关系代数 ⭑

**五种基本运算 + 五种符号**（其余运算可由它们合成）：

| 运算 | 符号 | 含义 |
| ---- | ---- | ---- |
| **并** | ∪ | R∪S：两个关系需**同模式**，由两者所有元组构成 |
| **差** | − | R−S：属于 R 但不属于 S 的元组。**不满足交换律** |
| **笛卡尔积** | × | R×S：属性列数为两者之和，记录数为 **\|R\|×\|S\|** ⭑ |
| **投影** | π | **按列**取（垂直分割），可写列号顺序，**会自动去重** |
| **选择** | σ | **按条件取行**（水平分割） |

**常用扩展运算**：交 ∩、连接 ⋈、除 ÷、重命名 ρ。

**连接对比**（易混）：

| 类型 | 特点 |
| ---- | ---- |
| **等值连接** | 按条件拼接，**保留重复属性列** |
| **自然连接** | 显示全部属性列，但**相同属性列只显示一次**，且只显示两个关系模式中属性**相同且值相同**的记录 |
| **左外连接** | 自然连接时，把 **R** 中舍弃的元组也放到新关系中 |
| **右外连接** | 自然连接时，把 **S** 中舍弃的元组也放到新关系中 |
| **完全外连接** | R 和 S 中舍弃的元组都保留 |

> 常见误答：把"投影"当成按行取。**选择 σ 取行、投影 π 取列**；且**交 ∩ 不是基本运算**（可由差导出：R∩S = R − (R−S)），**除 ÷ 也不是基本运算**。

## 八、并发控制与事务 ⭑

**事务 ACID 四特性**：

| 特性 | 对应操作 | 含义 |
| ---- | -------- | ---- |
| **原子性** | 操作 | 要么全做，要么全不做 |
| **一致性** | 数据 | 事务发生后数据一致（如转账不会"A 扣了 B 没收"） |
| **隔离性** | 执行 | 任一事务的更新操作在成功提交前，对其他事务不可见 |
| **持续性** | 改变 | 事务操作的结果是持续性的 |

**并发控制要解决的三个问题**：

| 问题 | 含义 |
| ---- | ---- |
| **丢失更新** | 事务 1 修改并写回，事务 2 也修改并写回，**后者覆盖了前者的更新** |
| **不可重复读** | 事务 2 两次读 A，中间事务 1 修改并写回 A，**两次读值不一致** |
| **读脏数据** | 事务 1 修改 A 后，事务 2 读到 A，**随后事务 1 回滚**，事务 2 读到的是无效数据 |

**封锁（两阶段提交中的锁）** ⭑：

| 锁 | 别名 | 权限 |
| -- | ---- | ---- |
| **共享锁 S** | 读锁 | 事务**只能读、不能写**；其他事务可再加 S 锁，**但不能加 X 锁** |
| **排他锁 X** | 写锁 | 事务**既可读也可写**；其他事务**不能再加任何锁** |

> 常见误答：以为拿到共享锁就能改数据。**共享锁 = 只读**；**排他锁 = 读写独占**。（2025-11 真题：事务 T 获得对 D 的共享锁，则 T 对 D **可读不可写**。）

## 十、案例分析：高并发（乐观锁 / 悲观锁 / Redis）⭑

> 这是近年**几乎每场都出现**的超纲热点（讲义的 2605 案例）。核心是把"防止超卖"这件事讲清楚。

**锁的两种分类**：

| 分类 | 名称 | 核心特点 |
| ---- | ---- | -------- |
| **悲观锁** | **共享锁**（读锁） | 允许多事务并发读；**不允许**加排他锁的写操作；会**阻塞写** |
| | **排他锁**（写锁） | 只允许一个事务持有；期间其他事务**不能读也不能写**；并发度最低、一致性最强；控制不当易**死锁** |

**乐观锁 vs 悲观锁**：

| 维度 | 乐观锁 | 悲观锁 |
| ---- | ------ | ------ |
| 实现方式 | 表加**版本号字段**，更新时带原版本号 + 1；影响行数为 1 成功、为 0 说明被改过则重试 | 数据库加锁（共享/排他） |
| 优点 | 无阻塞、读操作不加锁、系统并发度高 | 实现简单、数据库原生支持、**一致性最强** |
| 缺点 | 冲突频繁时大量重试、消耗 CPU、业务层要实现重试 | 存在线程阻塞、并发差、加锁释放有额外开销、**易死锁且死锁后恢复成本高** |
| 适用 | **读多写少、冲突概率低** | **写多读少、冲突高** |

**三种基于 Redis 的高并发控制场景**（防超卖）：

| 场景 | 实现思路 |
| ---- | -------- |
| **场景一** 分布式锁控制超卖 | 扣库存前先**获取锁**，防止多节点同时改同一资源；处理完释放锁（**配合 Lua 脚本保证原子释放**） |
| **场景二** Redis 原子操作 + 库存预扣 | 库存放 Redis，用 **DECR 扣减**；返回值 ≥ 0 成功，否则库存不足；**可配 Lua 实现复杂条件扣减**（如限每人一张） |
| **场景三** Redis 作乐观锁版本号缓存 | **WATCH 监听库存 key** → **MULTI 开事务** → 执行 DECR 等 → **EXEC**；期间 key 被改则事务失败，**循环重试**至成功或达上限 |

**答题表述模板**（案例题常问"请设计一种乐观锁实现方式 + 对比优缺点"）：先说锁的分类（共享/排他）→ 再讲乐观锁用版本号（CAS）避免阻塞 → 对比两者适用场景 → 最后落到 Redis 三种具体方案。
