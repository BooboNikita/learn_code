# Gamma 与纹理

在上一个教程中，我们第一次使用了图片纹理。那是一个简单、平坦的场景；现在我们要引入光照。但在此之前，我们需要先讨论一下纹理中到底存放的是什么。

## sRGB 颜色空间

使用纹理时最需要牢记的一件事，就是「这张纹理里的数据意味着什么？」这个问题的答案。在第一个纹理教程中，我们用过许多含义各异的纹理。我们有：

- 一张一维纹理，表示某个特定光泽度下镜面反射的高斯模型。
- 一张二维纹理，表示镜面反射的高斯模型，其中 S 坐标表示法向量与半角向量之间的夹角，T 坐标是表面的光泽度。
- 一张二维纹理，为表面上的每个位置指定一个镜面光泽度。

知道一张纹理存的是什么数据、它的纹理坐标又意味着什么，是至关重要的。缺少这份知识，就无法有效地使用这些纹理。

前面我们讨论过，在线性颜色空间中处理颜色对于光照和渲染中获得准确的色彩重现有多么重要。Gamma 校正是施加在输出颜色上的，把线性 RGB 取值映射到显示器所期望的 Gamma 校正后的 RGB 取值。

当时我们说过，我们所有的光照计算都假定顶点的颜色是线性 RGB 取值。这意味着模型的创建者，也就是把颜色放进网格中的人，必须确保被相加的颜色确实是线性 RGB 颜色。如果建模者没有做到这一点，如果建模者使用的颜色处于某个非线性 RGB 颜色空间中，那么网格最终呈现的颜色就会与他期望的相差甚远。

纹理也是一样，只不过问题严重得多。而这有一个非常重要的原因。请加载 `Gamma Ramp` 教程。

*Gamma Ramp*

这只是两个贴了纹理的矩形。上面那个不使用着色器的 Gamma 校正渲染，下面那个使用 Gamma 校正渲染。这些纹理尺寸为 320x64，并且就是按这个尺寸渲染的。

纹理中有五个灰度色块。每个色块比它左边那个更亮，亮度以 25% 递增。所以左边第二个色块是最大亮度的 25%，中间那个色块是 50%，依此类推。这意味着左边第二个色块应当显得只有中间那个的一半亮，而中间那个应当只有最右边那个的一半亮。

Gamma 校正的存在，是为了让线性取值在非线性显示器上看起来恰当地线性。它纠正的是显示器的非线性。根据我们已知的一切，下面那个矩形，也就是做了 Gamma 校正、把线性取值转换后加以显示的矩形，应该看起来是对的。上面那个矩形应该看起来是错的。

然而，我们看到的恰恰相反。下面那个矩形中各个色块的相对亮度不对，上面那个却没问题。这是为什么？

因为，虽然纹理取值的表观亮度以 25% 递增，该纹理使用的颜色取值却没有。这张纹理不是简单地在第一个块里放 0.0、第二个块里放 0.25 之类做出来的。它是用图像编辑程序制作的。颜色的选取依据是它们的*表观*相对亮度，而不是简单地给取值加上 0.25。

这意味着这些颜色取值*已经*做过 Gamma 校正了。它们不可能处于线性颜色空间中，因为创建图像的人是根据颜色的外观来选取颜色的。既然颜色的外观受显示器非线性的影响，那么纹理美术实际上选取的是 Gamma 校正之后的颜色取值。简单地说，纹理中的颜色已经处于一个非线性颜色空间中。

由于上面那个矩形不做 Gamma 校正，它只是把 Gamma 校正之前的颜色取值直接传给显示器，一切就这样自然地发生了。下面那个矩形则相当于做了两次 Gamma 校正。

当我们把纹理直接绘制到屏幕上时，这些都没问题。但如果该纹理中的颜色本应表示光照方程中某个表面的漫反射反射率，那么就有了一个大麻烦。从纹理中取回的颜色取值是非线性的，而我们所有的光照方程都*需要*输入取值是线性的。

我们本可以手动对纹理取值做 Gamma 反校正，无论是在加载时还是在着色器中。但那既没必要又浪费。相反，我们只要把实情告诉 OpenGL：这张纹理不在线性颜色空间中。

你所遇到的几乎每一个图像编辑程序，从无所不能的 Photoshop 到简陋的 Paint，都是在非线性颜色空间中显示颜色的。但它们用的并不是任意一种非线性颜色空间；它们都选定了一个叫作 **sRGB 颜色空间**的特定颜色空间。所以，当美术人员选取例如某种绿色调时，他们是从 sRGB 颜色空间中选取的，而它是非线性的。

sRGB 颜色空间用得有多普遍？它内建于每一个 JPEG 中，几乎所有视频压缩格式和工具都在使用它，几乎每一个图像编辑程序都假定它存在。一般来说，如果你从来源不明的渠道拿到一张图像，完全有理由假定其中的 RGB 取值是 sRGB 的，除非你有特别的理由认为不是。

sRGB 颜色空间是 Gamma 2.2 的一种近似。它并不精确等于 2.2，但已经足够接近，以至于你可以把 sRGB 图像直接显示到屏幕上而不做 Gamma 校正。这正是我们对上面那个矩形所做的事。

由于 sRGB 颜色空间无处不在，如今 sRGB 解码逻辑已经直接内建在 GPU 中。OpenGL 自然也支持它。这是通过特殊的图像格式来实现的。

**示例：sRGB 图像格式**

```cpp
std::auto_ptr<glimg::ImageSet> pImageSet(glimg::loaders::stb::LoadFromFile(filename.c_str()));

glimg::SingleImage image = pImageSet->GetImage(0, 0, 0);
glimg::Dimensions dims = image.GetDimensions();

glimg::OpenGLPixelTransferParams pxTrans = glimg::GetUploadFormatType(pImageSet->GetFormat(), 0);

glBindTexture(GL_TEXTURE_2D, g_textures[0]);

glTexImage2D(GL_TEXTURE_2D, 0, GL_RGB8, dims.width, dims.height, 0,
    pxTrans.format, pxTrans.type, image.GetImageData());
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_BASE_LEVEL, 0);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAX_LEVEL, pImageSet->GetMipmapCount() - 1);
        
glBindTexture(GL_TEXTURE_2D, g_textures[1]);
glTexImage2D(GL_TEXTURE_2D, 0, GL_SRGB8, dims.width, dims.height, 0,
    pxTrans.format, pxTrans.type, image.GetImageData());
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_BASE_LEVEL, 0);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAX_LEVEL, pImageSet->GetMipmapCount() - 1);

glBindTexture(GL_TEXTURE_2D, 0);
```

这段代码把同一份纹理数据加载了两次，但使用了不同的纹理格式。第一张使用 `GL_RGB8` 格式，第二张使用 `GL_SRGB8`。后者把这张纹理的颜色数据标识为处于 sRGB 颜色空间中。

要看看这对渲染效果有什么影响，你可以在两张纹理之间切换。<kbd>1</kbd> 键把上面那张纹理在线性 RGB（从现在起我们称之为 **lRGB**）与 sRGB 之间切换，<kbd>2</kbd> 键对下面那张做同样的事。

*Gamma Ramp with sRGB Images*

上下两张都使用 sRGB 版本时，我们能看到下面那个做了 Gamma 校正的矩形是对的。

当一张纹理使用某种 sRGB 格式时，对它的纹理访问函数会有所不同。当它们取回一个纹素时，OpenGL 会自动把颜色从 sRGB 颜色空间线性化。这正是我们想要的。而最妙的是，线性化的代价可以忽略不计。因此我们完全没必要去摆弄数据或者用别的方式手动线性化。OpenGL 会替我们做。

注意着色器并没有改变。它仍然使用普通的 `sampler2D`，用一个二维纹理坐标和 `texture` 函数去访问它，等等。着色器不必知道、也不必关心图像数据是在 sRGB 颜色空间还是线性颜色空间中。它只要调用 `texture` 函数，并期待它返回 lRGB 颜色取值即可。

### 像素定位

关于本教程中的渲染，有一件值得关注的有趣事情。它不仅使用了正交投影（不同于我们自教程 4 以来大多数教程的做法），还对正交投影做了一些特殊的处理。在透视投影出现之前的那些教程里，正交投影基本算是默认的。我们直接用裁剪空间中的顶点作图。而由于那些顶点的 W 是 1，裁剪空间就等同于 NDC 空间，因此我们就得到了一个正交投影。

我们经常会希望用窗口空间的像素坐标来绘制某些对象。这常用于绘制文字，但也可以用来完全按照纹理中的原样显示图像，就像我们这里做的一样。由于顶点着色器必须输出裁剪空间取值，关键在于构造出一个能把窗口空间坐标变换到裁剪空间的矩阵。OpenGL 会在内部完成转换回窗口空间的过程。

这通过 `reshape` 函数完成，和我们大多数投影矩阵函数一样。这个计算其实相当简单。

**示例：窗口到裁剪空间的矩阵计算**

```cpp
glutil::MatrixStack persMatrix;
persMatrix.Translate(-1.0f, 1.0f, 0.0f);
persMatrix.Scale(2.0f / w, -2.0f / h, 1.0f);
```

目标是把窗口空间坐标变换到裁剪空间；由于 W 分量保持为 1.0，裁剪空间等同于 NDC 空间。窗口空间坐标的 X 范围是 [0, w)，Y 范围是 [0, h)。NDC 空间的 X 与 Y 范围是 [-1, 1]。

第一步是把我们的 X 与 Y 两个范围从 [0, w/h) 缩放到 [0, 2]。下一步是施加一个简单的偏移，把它移到 [-1, 1] 范围。别忘了，变换应用到矩阵栈上的顺序与它们被书写的顺序是相反的。

不过有一件事需要注意。NDC 空间的 +X 向右、+Y 向上。OpenGL 的窗口空间与此一致；窗口空间的原点在左下角。这本身很好，但很多人习惯的是左上角原点、+Y 向下的坐标系。

在本教程中，我们使用左上角原点的窗口空间。这就是 Y 缩放被取负、Y 偏移为正的原因（若采用左下角原点，则希望偏移为负）。

**注意**

> 取负 Y 缩放会翻转所渲染物体的绕序。这通常无关紧要；大多数时候你在窗口空间中工作时，并不依赖背面剔除来剔掉某些三角形。在本教程中，我们甚至没有启用背面剔除。而且很多时候，当你用像素级精确的坐标进行渲染时，背面剔除本身就无关紧要，应当禁用。

### 顶点格式

在此之前的所有教程中，我们的顶点数据都是浮点值数组。第一次，情况不再如此。由于我们工作在像素坐标中，我们希望用整数像素坐标来指定顶点位置。这就是那两个矩形的顶点数据：

```cpp
const GLushort vertexData[] = {
     90, 80,    0,     0,
     90, 16,    0,     65535,
    410, 80,    65535, 0,
    410, 16,    65535, 65535,
    
     90, 176,   0,     0,
     90, 112,   0,     65535,
    410, 176,   65535, 0,
    410, 112,   65535, 65535,
};
```

我们的顶点数据有两个属性：位置和纹理坐标。我们的位置是二维的，纹理坐标也是二维的。这些属性是交错排列的，位置在前。所以上面前两列是位置，后两列是纹理坐标。

我们的数据不是浮点数，而是由 `GLushort` 组成，也就是 2 字节的整数。OpenGL 如何解释它们由 `glVertexAttribPointer` 的参数指定。它可以用两种方式解释它们（严格说来是三种，但这里我们不用第三种）：

**示例：顶点格式**

```cpp
glBindVertexArray(g_vao);
glBindBuffer(GL_ARRAY_BUFFER, g_dataBufferObject);
glEnableVertexAttribArray(0);
glVertexAttribPointer(0, 2, GL_UNSIGNED_SHORT, GL_FALSE, 8, (void*)0);
glEnableVertexAttribArray(5);
glVertexAttribPointer(5, 2, GL_UNSIGNED_SHORT, GL_TRUE, 8, (void*)4);

glBindVertexArray(0);
glBindBuffer(GL_ARRAY_BUFFER, 0);
```

属性 0 是我们的位置。我们看到类型不是 `GL_FLOAT` 而是 `GL_UNSIGNED_SHORT`。这与我们所用的 C++ 类型一致。但 GLSL 着色器接收该属性时用的是浮点 `vec2`，而不是整数二维向量（在 GLSL 中那会是 `ivec2`）。OpenGL 如何调和这一点？

这取决于第四个参数，它定义这个整数值是否被归一化。如果设为 `GL_FALSE`，那么它就是未归一化的。因此，它会像标准的 C/C++ 类型转换那样被转换成浮点数。整数取值 90 被转换成浮点取值 90.0f。而这正是我们想要的。

对位置来说这正是我们想要的；但纹理坐标就是另一回事了。归一化的纹理坐标应当取值于 [0, 1]（除非我们想用某种形式的环绕）。要做到这一点，整数纹理坐标通常会——嗯——被归一化。把 `GL_TRUE` 传给第四个参数（只有第三个参数是整数类型时才有效），就是告诉 OpenGL 在把整数值转换成浮点数时对它进行归一化。

这种归一化的作用与纹素取值的归一化完全相同。由于 `GLushort` 的最大值是 65535，该值被映射到 1.0f，而最小值 0 被映射到 0.0f。所以这不过是一种稍微考究的写法，把纹理坐标设成 1 和 0。

注意所有这些转换在性能上是*免费*的。事实上，把顶点属性尽可能紧凑地压缩，往往是一种有用的性能优化。这在内存和渲染性能两方面都更划算，因为从内存中读取的数据越少，耗时就越少。

把归一化的 short 与 32 位浮点数、归一化无符号字节（对颜色很有用）等混用在同一份顶点数据里，OpenGL 完全没有问题（不过不能用在同一个*属性*内部）。上面的数组本可以对纹理坐标使用 `GLubyte`，但那样就很难把它作为 C 风格数组直接写进代码里了。在真实应用中，人们通常不会从 C 风格数组获取网格，而是从文件中获取。

## sRGB 与 mipmap

光照函数需要 lRGB 取值，其主要原因是它们要执行线性运算。因此它们在非线性颜色上会给出不准确的结果。这并不局限于光照函数；*所有*对颜色的线性运算都需要 lRGB 取值才能得到合理的结果。

在纹素取值上执行的一个重要线性运算是过滤。无论是放大还是缩小，非最近邻的过滤都要做某种线性算术。由于这一切都由 OpenGL 处理，问题是这样的：如果一张纹理是 sRGB 格式，OpenGL 的纹理过滤是在把纹素取值转换成 lRGB *之前*进行，还是之后？

答案相当简单：过滤在线性化之后进行。所以它做的是正确的事。

**注意**

> 事情没那么简单。OpenGL 规范在技术上把这一点留作未定义。不过，如果你的硬件能够不作修改地运行这些教程（即你的硬件支持 OpenGL 3.3），那么它很可能会做正确的事。只有在 3.0 之前的硬件上这才是个问题。

一个更大的问题是：你是否为纹理正确地生成了 mipmap？上一个教程中 mipmap 生成被一笔带过了，因为工具通常会替你做。一般来说，mipmap 生成涉及对颜色做某种形式的线性运算。要让这个过程对 sRGB 纹理产生正确的结果，它需要先把 sRGB 颜色取值线性化，在其上执行过滤，然后再转换回 sRGB 以便存储。

除非你正在编写纹理处理工具，否则这个问题的答案就是直接问你的纹理工具本身。多数可免费获取的纹理工具完全没有意识到非线性颜色空间的存在。你可以根据创建 mipmap 时给出的选项来判断哪些工具意识到了这一点。如果你能为纹理指定一个 Gamma，或者有某种设置可以指定纹理的颜色是 sRGB，那么这个工具就能做正确的事。如果没有这样的选项，它就不能。对于 sRGB 纹理，你应当使用 Gamma 2.2，这正是 sRGB 所近似的值。

**注意**

> GIMP 的 DDS 插件是一个不错的免费工具，而且它了解线性颜色空间。NVIDIA 的命令行纹理工具同样是免费的，也做到了这一点。

要看看这会如何影响渲染，请加载 `Gamma Checkers` 工程。

*Gamma Checkers*

它的工作方式与前面那些过滤教程一样。<kbd>1</kbd> 和 <kbd>2</kbd> 键分别选择线性 mipmap 过滤和各向异性过滤（使用可能的最大的各向异性）。

我们能看到它看起来与上一次见到的有些不同。远处的灰色区域比当时暗得多。这是因为我们正在使用 sRGB 颜色空间的纹理。虽然 sRGB 中的白色与黑色是一样的（分别是 1.0 和 0.0），但它们 50% 的混合值（0.5）却不是。sRGB 纹理假定 0.5 这个颜色就是 sRGB 的 0.5，因此它变得比我们预期的更暗。

一开始，我们渲染时不做任何 Gamma 校正。要切换 Gamma 校正，按 <kbd>a</kbd> 键。这会恢复到我们此前看到的样子。

不过，我们所用的纹理其实是不正确的。如前所述，0.5 并不是黑色与白色 50% 混合时对应的 sRGB 颜色。在 sRGB 颜色空间中，那个颜色大约是 0.73。这张纹理之所以是错的，是因为它的 mipmap 不是在正确的颜色空间中生成的。

要切换到 mipmap 生成正确的纹理，请按 <kbd>g</kbd> 键。

*Gamma Correct with Gamma Mipmaps*

这看起来仍然与上一个教程不同。这自然地告诉我们，此前不做 Gamma 校正其实是个问题，因为这个版本看起来好得多。灰色与棋盘格混合得好多了，因为灰色现在正确地处在白色与黑色之间的正中。这里要记住的要点是：确保管线中每个阶段都是线性的，这总是很重要。这其中就包括 mipmap 的生成。

## sRGB 与屏幕

至此我们已经看到如何用 sRGB 纹理存储 Gamma 校正后的图像，使得它们在被着色器取回时自动完成线性化。由于 sRGB 颜色空间非常接近 Gamma 2.2 的近似，如果我们能用一张 sRGB 图像作为渲染目标，我们就会自动获得 Gamma 校正，而不必把它写进着色器。但这需要两件事：能够指定屏幕图像是 sRGB 的，以及能够声明我们输出的是线性取值，并希望它们在存储时被转换成 sRGB 颜色空间。

OpenGL 自然两者都提供。要看看它们如何工作，请加载最后一个工程 `Gamma Landscape`。它展示了带纹理的地形，配有昼夜循环和几个来回移动的光源。

*Gamma Landscape*

它使用标准的鼠标控制来移动视角。和之前一样，<kbd>1</kbd> 和 <kbd>2</kbd> 键分别选择线性 mipmap 过滤和各向异性过滤。主要特性是不依赖着色器的 Gamma 校正。它默认启用，可以按 <kbd>空格键</kbd> 切换。

**sRGB 屏幕图像**

设置这个的过程有点让人困惑，但对我们的教程来说最终相当简单。OpenGL 规范规定了如何使用 OpenGL 渲染系统，但它并不规定如何*创建* OpenGL 渲染系统。那是交给平台相关的 API 完成的。因此，虽然使用 OpenGL 的代码是平台无关的，但这段代码最终依赖平台相关的初始化代码来创建 OpenGL 上下文。

这些教程依赖 FreeGLUT 来建立 OpenGL 上下文并管理平台相关的 API。`framework.cpp` 文件负责完成初始化设置工作，精确地告诉 FreeGLUT 我们希望如何设置屏幕图像。为了让不同的教程都能调整我们设置 FreeGLUT 屏幕图像的方式，框架会调用 `defaults` 函数。

**示例：Gamma Landscape 的 defaults 函数**

```cpp
unsigned int defaults(unsigned int displayMode, int &width, int &height)
{
    return displayMode | GLUT_SRGB;
}
```

`displayMode` 参数是一个位域，其中包含框架设置好的标准 FreeGLUT 显示模式标志。这个函数必须返回该位域，而此前所有教程都是原样返回它的。这里，我们修改它以包含 `GLUT_SRGB` 标志。该标志告诉 FreeGLUT，我们希望屏幕图像处于 sRGB 颜色空间中。

**从线性到 sRGB 的转换**

仅此还不够。我们还必须告诉 OpenGL：我们的着色器将写入线性颜色空间的取值，并且这些取值在写入屏幕之前应当被转换成 sRGB。这只需一条简单的 `glEnable` 命令：

**示例：启用 sRGB 转换**

```cpp
if(g_useGammaDisplay)
    glEnable(GL_FRAMEBUFFER_SRGB);
else
    glDisable(GL_FRAMEBUFFER_SRGB);
```

这样做的必要性并不完全显而易见，尤其是因为我们在读取纹理时无法手动关闭 sRGB 到线性的转换。当我们绘制直接处于 sRGB 颜色空间的东西时，能够为屏幕渲染禁用线性到 sRGB 的转换是很有用的。例如，让界面的某些部分直接用 sRGB 颜色空间绘制，而实际被渲染的场景使用颜色转换，这往往很有用。

注意这种颜色转换在性能上与纹理读取一样免费。所以你不必害怕在合理范围内频繁地使用它。

有了这种自动的 Gamma 校正，就比手动 Gamma 校正更好，因为它覆盖了所有写入屏幕的内容。在之前的教程里，我们必须手动对清除色以及某些用于渲染实心物体的其他颜色做 Gamma 校正。现在，我们只需启用转换，一切就都受到了影响。

确保从纹理创建、经过光照、一直到屏幕的整条管线都是线性的这个过程，通常称为 **Gamma 校正纹理**。这个名字有点误称，因为「纹理」并不是必要条件；自从教程 12 引入这个概念起，我们一直就是 Gamma 校正的（教程 15 除外，在那里我们讨论了过滤）。不过，纹理是保持管线线性这一目标的主要潜在失分点，因为磁盘上的许多图像格式根本没有办法说明图像数据是 sRGB 还是线性的。所以这个名字还是有一定道理的。

## 本章小结

在本教程中，你学到了以下内容：

- 任何时候都要记住，纹理中存储的数据究竟意味着什么，这一点很重要。
- 多数时候，当纹理表示真实颜色时，这些颜色处于 sRGB 颜色空间中。必须选择合适的图像格式。
- 过滤这类线性运算必须在线性取值上进行。OpenGL 对 sRGB 纹理的所有操作都会这么做。
- 同样，mipmap 的生成是一种线性运算，必须先把 sRGB 转换成 lRGB，做过滤，然后再转换回来。由于 OpenGL（通常）不生成 mipmap，因此确保 mipmap 被正确生成是图像创建者的责任。
- 光照运算需要线性取值。
- 帧缓冲也可以处于 sRGB 颜色空间中。OpenGL 在这样做时同样要求进行专门的启用，从而允许渲染中的一部分采用 sRGB 编码而其他部分不采用。

### 值得关注的 OpenGL 函数

- **glEnable/glDisable(GL_FRAMEBUFFER_SRGB)**：启用/禁用从线性到 sRGB 的转换。启用时，片元着色器写入 sRGB 图像的颜色被假定为线性的，因此它们会被转换成 sRGB 颜色空间。禁用时，片元着色器写入的颜色被假定已经处于 sRGB 颜色空间中，会按给定的值原样写入。

## 术语表

- **sRGB 颜色空间**：一种非线性的 RGB 颜色空间，近似 Gamma 2.2。*绝大多数*图像编辑程序和操作系统默认都在 sRGB 颜色空间中工作。因此，你遇到的绝大多数图像都处于 sRGB 颜色空间。

  OpenGL 能够直接处理 sRGB 纹理和屏幕图像。对 sRGB 纹理的访问会返回 lRGB 取值，而对 sRGB 屏幕图像的写入可以从线性转换成 sRGB 取值，前提是使用了正确的启用。
- **Gamma 校正纹理**：确保所有纹理、图像以及其他颜色的来源和去处（例如顶点属性）要么已经处于 lRGB，要么按需要与线性颜色空间相互转换的过程。sRGB 格式的纹理是其中一部分，渲染到 sRGB 屏幕图像（或者手动做 Gamma 校正）也是其中一部分。这些做法提供了自动校正。手动校正可能需要施加到顶点颜色属性上，而为了正确插值，这一校正需要在插值之前施加。
