## 一、考情定位

- 论文的「软件架构设计」「基于架构的软件开发方法」两块与本篇重合度最高——**一份素材能同时覆盖案例与论文**。

> 近几季试题一题型：质量属性填空 + 场景六要素（2025-11）；质量属性判断 + 解释器风格图（2025-05）；质量属性与功能性判断 + ping/echo 与心跳（2024-11）；微服务优缺点 + 效用树 + 六要素（2024-05）；Lambda 与 Kappa（2023-11）。

## 二、架构风格

### 2.1 五大类 13 种总览 ⭑

| 大类 | 子类 | 关键词 / 场景 |
| ---- | ---- | ------------- |
| **数据流风格** | 批处理风格 | 整体；**离线数据分析和大规模数据处理**，交互性不好 |
| | 管道-过滤器风格 | 流式；可**实时数据处理和流式计算** |
| **调用/返回风格** | 主程序/子程序风格 | 主程序直接调用子程序 |
| | 面向对象风格 | **显式调用**对象的方法，须知道其标识和名称 |
| | 层次结构风格 | 分层，调用下层 |
| | 客户端/服务器风格 | 基于**资源不对等**实现共享 |
| **数据共享风格**（以数据为中心） | 仓库（数据库）风格 | **业务功能驱动**相应进程执行 |
| | 黑板风格 | **中央数据结构的当前状态触发**相应进程执行，共享知识库、协同处理 |
| | 超文本风格 | 网状链接，互联网领域 |
| **虚拟机风格** | 解释器风格 | 灵活可自定义，**逐行解释源代码**，效率低 |
| | 基于规则的系统风格 | 灵活可自定义，**基于事先定义的规则和条件**，效率低 |
| **独立构件风格** | 进程通信风格 | **显式**进程间通信，面向分布式系统 |
| | 事件系统风格 | **隐式调用**、解耦，构件放弃了对计算的控制权 |

### 2.2 构件与连接件（只留常考）

- **管道-过滤器**：构件 = **过滤器**；连接件 = **数据流传输管道**。
- **批处理**：构件 = **独立的应用程序**；连接件 = 某种类型的**媒介**（定义数据流图、表达拓扑）。
- **仓库**：构件 = **中央数据结构**（说明当前数据状态）+ 一组**对中央数据操作的独立构件**；连接件 = **仓库与独立构件之间的交互**。
- **黑板**：**知识源 + 黑板（共享数据）**，知识源通过直接存取读写黑板。
- **解释器四部分** ⭑：解释引擎、存储区（被解释的代码）、解释引擎当前工作状态、源代码被解释执行的进度。
- **基于规则的系统**：规则集、规则解释器、规则/数据选择器、工作内存。
- **事件驱动**：事件源 → 事件 → 事件管理器 → 分发/通知 → 事件处理器。

### 2.3 易错点 ⭑

> **仓库 vs 黑板**：都属"以数据为中心"，差别在**触发方式**——仓库由**业务功能的输入事务流**驱动；黑板由**中央数据结构的当前状态**触发，且由多个**知识源**协同求解。

> **解释器 vs 基于规则**：同属**虚拟机风格**，共同特点是"**灵活、可自定义，但效率低**"。解释器逐行解释源码；基于规则的系统按预先定义的规则和条件推理。

> **事件驱动 vs 进程通信**：同属**独立构件风格**。进程通信是**显式**的进程间通信（面向分布式）；事件驱动是**隐式调用**，构件解耦、放弃了对计算的控制权。

> **常见误答**：管道-过滤器**可以**并行执行（各过滤器彼此独立），所以"不能并行执行"恰恰是**它不成立**的脆弱性描述。

## 三、架构复用

- **机会复用**：开发**过程中**发现可复用资产就复用（事后）。
- **系统复用**：开发**之前**就规划好哪些需要复用（事前）。
- **三阶段**：① 构造/获取可复用资产 → ② 管理这些资产（构件库）→ ③ 选择可复用部分，开发应用系统。

## 四、DSSA（特定领域软件架构）

- **定义**：专用于**一类特定领域**、为该领域**一组应用**提供**领域模型 + 参考需求 + 参考架构**的软件构件集合。
- **垂直域**：一个特定领域内的**通用软件架构**（完整架构）；**水平域**：**多个不同领域之间的相同部分**（如购物和教育都有收费系统）。
- **三个基本活动** ⭑（背这个链条）：

| 活动 | 产出 |
| ---- | ---- |
| **领域分析** | 获得**领域模型**（领域需求） |
| **领域设计** | 获得 **DSSA**（领域需求的解决方案，是**高层次设计**，不是单个系统的表示） |
| **领域实现** | 依据领域模型和 DSSA **开发和组织可重用信息** |

- **四种角色**：领域专家（提供需求、**复审**）、领域分析人员（知识获取 → 领域模型）、领域设计人员（开发 DSSA）、领域实现人员（开发构件）。
- **五阶段** ⭑：定义领域范围 → 定义领域特定的元素 → 定义领域特定的设计和实现需求约束 → 定义领域模型和架构 → 产生/搜集可复用的产品单元。
- 整个过程是**并发的、递归的、反复的、螺旋型**的（类似螺旋模型）。

## 五、ABSD 与基于架构的软件开发

### 5.1 ABSD（基于架构的软件设计）

- 由**业务、质量和功能需求的组合**驱动；采用**视角和视图**描述架构。
- **用例**描述功能需求，**质量属性场景**描述质量（非功能）需求。
- 设计起点早：**项目总体功能框架明确**即可开始，即**需求获取和分析还没完成就开始设计**。
- **三个基础** ⭑：① **功能的分解**（用已有的基于模块的内聚和耦合技术）② **通过选择架构风格来实现质量和业务需求** ③ **软件模板的使用**。
- 方法特征：**自顶向下、递归细化**——顶层分解为若干**概念子系统** + 软件模板；第 2 层再把概念子系统分解为**概念构件** + 附加软件模板。

### 5.2 基于架构的软件开发六步 ⭑

| 步骤 | 关键点 |
| ---- | ------ |
| **① 架构需求** | 需求来源：**系统的质量目标、系统的商业目标、系统开发人员的商业目标**；重在标识构件 |
| **② 架构设计** | 把需求阶段标识的构件**映射成构件**，分析构件间的相互作用 |
| **③ 架构文档化** | 产出**两种文档**：**架构（体系结构）规格说明**、**测试架构需求的质量设计说明书** |
| **④ 架构复审** | 由**外部人员**参加（独立于开发组织，如用户代表、领域专家）；**复审不过则返回架构设计阶段** |
| **⑤ 架构实现** | 实现构件 → 构件组装成系统 → 系统测试 |
| **⑥ 架构演化** | 按需求**增删构件**，使架构可复用 |

- **标识构件流程**：需求获取 → 生成类图 → 对类分组 → 把类打包成构件 → 需求评审。
- **架构演化流程**：需求变化请求 → 架构演化计划 → 构件变动 → 更新构件的相互作用 → 构件组装与测试 → 技术评审 → 演化后的架构。

## 六、质量属性

> 本讲的**第一得分点**，案例题几乎每季必考。注意存在**两套并行的分类**，考试时按题干要求作答。

### 6.1 开发期 6 项 / 运行期 7 项

- **开发期**（关注开发阶段）：易理解性、可扩展性（灵活性）、可重用性、可测试性、可维护性、可移植性。
- **运行期**（关注运行阶段）：性能、安全性、可伸缩性、互操作性、可靠性、可用性、鲁棒性（健壮性 / 容错性）。

### 6.2 8 个核心质量属性与设计策略 ⭑

| # | 质量属性 | 含义 | 设计策略 |
| - | -------- | ---- | -------- |
| 1 | **性能** | 系统的响应能力（响应时间、吞吐量） | 优先级队列、增加计算资源、减少计算开销、引入并发机制、采用资源调度 |
| 2 | **可靠性** | 在**应用或系统错误面前**维持功能特性的能力（MTTF/MTBF/MTTR） | **心跳、Ping/Echo、冗余、选举** |
| 3 | **可用性** | 系统能够**正常运行的时间比例** | **心跳、Ping/Echo、冗余、选举** |
| 4 | **安全性** | 向合法用户提供服务的同时**阻止非授权使用**（保密性/完整性/不可抵赖性/可控性） | 入侵检测、用户认证、用户授权、追踪审计 |
| 5 | **可修改性** | **快速、以较高性价比**变更系统的能力，靠**考察变更代价**衡量 | 接口-实现分离、抽象、信息隐藏 |
| 6 | **功能性** | 完成**所期望的工作**的能力，需多个构件协作 | — |
| 7 | **可变性** | 架构经扩充或变更成为**新架构**的能力 | — |
| 8 | **互操作性** | 与其他系统相互作用，需为**外部可视的功能特性和数据结构**提供软件入口 | — |

> 可靠性 与 可用性 的设计策略**完全相同**（心跳、Ping/Echo、冗余、选举），这是最容易混的一处。

### 6.3 质量属性场景六要素 ⭑

**刺激源（Source）、刺激（Stimulus）、环境（Environment）、制品（Artifact）、响应（Response）、响应度量（Measurement）**。

> **易答错点**：六要素里的"环境"要答**系统设计时 / 编译时 / 构建时 / 运行时**这类**时机**，而不是"高并发环境"这类场景描述。

## 七、架构评估

### 7.1 SAAM（基于场景的架构分析方法）

- **最早**形成文档并得到广泛应用的软件架构分析方法。
- 主要质量属性是**可修改性**；基本特点是**把任何形式的质量属性都具体化为场景**。
- 3 个主要方面：**功能、结构、分配**；输入：问题描述、需求声明、架构描述。
- **5 步**：场景开发 → 架构描述 → 单个场景评估 → 场景交互 → 总体评估。
- 用于架构的**最后版本，但早于详细设计**。

### 7.2 ATAM（架构权衡分析法）

- 让架构师明确**如何权衡多个质量目标**。
- **4 个活动领域**：场景和需求收集 → 体系结构视图和场景实现 → 属性模型构造和分析 → 折中。
- 针对**性能、可用性、安全性、可修改性**，在系统开发**之前**评价与折中。
- 工具：**效用树**——树根 → 质量属性 → 属性分类 → 质量属性场景（叶子节点）。
- 头脑风暴设计 3 类场景：**用例场景**（系统典型使用）、**增长场景**（对系统的修改）、**探测场景**（可能造成过载的**极端修改**）。
- 领域知识库通过**基于属性的架构风格（ABAS）**维护。

### 7.3 SAAM vs ATAM ⭑

| 维度 | SAAM | ATAM |
| ---- | ---- | ---- |
| 定位 | **最早**形成文档、广泛应用的架构分析方法 | 架构**权衡**分析方法，评估多质量目标 |
| 主要质量属性 | **可修改性** | **性能、可用性、安全性、可修改性** |
| 主要手段 | 把质量属性统一具体化为场景 | 效用树 + 场景（用例/增长/探测）分类分级 |
| 主要活动 | 场景开发、架构描述、单个场景评估、场景交互、总体评估（**5 步**） | 场景和需求收集、视图与场景实现、属性模型构造与分析、折中（**4 域**） |
| 使用阶段 | 架构的最后版本，**早于详细设计** | 系统开发**之前** |
