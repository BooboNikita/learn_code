## 1. 常量指针和指针常量有何区别？

**考察点**：`const` 与 `*` 的相对位置，即顶层 / 底层 const。

**要点**：

- **指针常量**：`int* const p` —— 指针**本身**是常量，`p` 不能改指，但 `*p` 可改。`const` 在 `*` **右边**。
- **常量指针**（指向常量的指针）：`const int* p` —— 指向的内容不可改，但 `p` 可改指别处。`const` 在 `*` **左边**。
- 记忆法：**从右往左读**，`int* const p` → "p is a const pointer to int"；`const int* p` → "p is a pointer to const int"。
- 性质归类：`int* const` 是**顶层 const**（Top-level，对象本身不可改），`const int*` 是**底层 const**（Low-level，指向对象不可改）。
- 拷贝规则差异：**顶层 const 在拷贝时被忽略**（`int* const` 可以赋给 `int*`）；**底层 const 不能被忽略**（`const int*` 赋给 `int*` 编译报错，需要 `const_cast`）。

```cpp
int a = 1, b = 2;

int* const p1 = &a;      // 指针常量：p1 不能改，*p1 = 10 可以
const int* p2 = &a;      // 常量指针：*p2 不能改，p2 = &b 可以
const int* const p3 = &a; // 两者都是（指向常量的常量指针）

// p1 = &b;   // 错误：p1 是常量
// *p2 = 10;  // 错误：指向的是常量
```

```cpp
char* const cp = buf;        // 顶层 const
const char* pc = buf;        // 底层 const
char* p = cp;                // OK：顶层 const 被忽略
// char* q = pc;             // 错误：不能丢弃底层 const
```

> 面试追问「函数参数里 `const T* const&` 是什么」：引用是底层 const（引用本身天然不可改绑），`T* const` 才涉及顶层 const —— 这种写法主要作用是防止误改指针。

## 2. 引用和指针如何选择？

**考察点**：语义表达能力（可空性、可改绑性、所有权）与性能。

**要点**：

- **引用不能为空**，必须绑定到已有对象且**不能改绑**；**指针可空、可改指、可做算术。**
- 因此选择规则可按"语义"判断：

| 场景 | 选择 | 原因 |
| ---- | ---- | ---- |
| 参数可能"不存在" | 指针 / `std::optional` | 引用无法表达空 |
| 参数一定存在，且不想拷贝 | `const T&` | 语义清晰、无拷贝 |
| 需要修改调用方对象 | `T&` | 无空值检查负担 |
| 需要改绑、需要遍历数组 | 指针 | 引用不可改绑、不能做算术 |
| 表达"拥有资源" | 智能指针 | 明确所有权与生命周期 |
| 表达"借用、不拥有" | 引用 或 `T*` | Core Guidelines：裸指针只用于"非拥有" |
| 拷贝构造/赋值、`operator<<` 等 | **必须引用** | 值传递会无限递归 / 要求链式调用 |
| 容器元素、返回"可能没有" | 指针 / `optional` | 容器要可拷贝或可移动 |

- **性能**：引用通常按指针实现但**没有额外语义开销**，且编译期可优化；大小语义上与被引用对象一致（`sizeof(T&) == sizeof(T)`）。
- **安全性**：引用无"空引用"风险，但不能解决悬垂（返回局部变量的引用同样致命）。
- 工程约定（C++ Core Guidelines）：**函数签名中裸指针表示"非拥有的可空对象"，引用表示"非拥有的非空对象"，智能指针表示所有权。**

```cpp
void render(const Widget& w);        // 必须传对象，不拷贝
void render(const Widget* w);        // 可能没有，需判空
bool find(const std::vector<int>& v, int x, int& out);   // 输出参数用引用
std::unique_ptr<Widget> create();     // 所有权移交用智能指针
```

**追问：为什么引用做函数参数没有拷贝？** 因为引用只是别名，传递的是地址，不产生对象副本；值传递则会调用拷贝构造。

## 3. `nullptr` 和 `NULL` 有何区别？

**考察点**：C++11 引入 `nullptr` 的动机 —— 类型安全与重载决议。

**要点**：

- `NULL` 是宏，通常是 `0`（C++ 中定义为 `0`，C 中可为 `(void*)0`）；它的类型是**整型**，不是指针类型。
- `nullptr` 是 C++11 的关键字字面量，类型为 `std::nullptr_t`，**可隐式转换为任意指针类型和指向成员的指针类型**，但**不能转换为整数**（除 `bool`）。
- 三处关键差异：

**① 重载决议**

```cpp
void f(int);
void f(char*);

f(NULL);      // 调用 f(int)  —— 意图通常是 f(char*)，语义错误！
f(nullptr);   // 调用 f(char*)，明确
```

**② 模板类型推导**

```cpp
template <typename T> void g(T);
g(NULL);      // T 推导为 int（有些实现为 long），不是指针
g(nullptr);   // T 推导为 std::nullptr_t
```

**③ 可读性与类型安全**：`nullptr` 明确表达"空指针"，代码审查时不会与数字 `0` 混淆。

| 维度 | `NULL` | `nullptr` |
| ---- | ------ | --------- |
| 本质 | 宏，整型常量 `0` | 关键字，`std::nullptr_t` |
| 类型 | `int` / `long` | `std::nullptr_t` |
| 能否隐式转指针 | 能（经由字面量 0） | 能 |
| 能否隐式转整数 | 能 | **不能**（除 `bool` 上下文） |
| 重载/模板行为 | 走整型版本，易错 | 走指针版本，符合直觉 |

> 结论：C++11 起**一律用 `nullptr`**；代码里出现 `if (p == NULL)` 属于遗留风格。顺带：`if (p)` 与 `if (p != nullptr)` 等价，但前者可读性差，不推荐。

## 4. RAII 的核心机制是什么？

**考察点**：C++ 资源管理的基石。

**要点**：

- **RAII = Resource Acquisition Is Initialization（资源获取即初始化）**：把资源的生命周期**绑定到栈对象的生命周期**上 —— 构造函数获取资源，析构函数释放资源。
- 依赖的语言机制是 **C++ 的确定性析构**：栈对象在以下所有路径离开作用域时都会自动析构：
  - 正常执行到作用域末尾
  - `return`
  - `break` / `continue` / `goto` 跳出
  - **异常抛出导致的栈展开（stack unwinding）**
- 因此 RAII 天然**异常安全**，不需要写 `finally`（C++ 也没有 `finally`）。

```cpp
class FileGuard {
public:
    explicit FileGuard(const char* path) : fp_(std::fopen(path, "r")) {
        if (!fp_) throw std::runtime_error("open failed");
    }
    ~FileGuard() { if (fp_) std::fclose(fp_); }   // 无论如何都会执行

    FileGuard(const FileGuard&) = delete;          // 资源不可拷贝
    FileGuard& operator=(const FileGuard&) = delete;
    FileGuard(FileGuard&& o) noexcept : fp_(o.fp_) { o.fp_ = nullptr; }

    std::FILE* get() const { return fp_; }
private:
    std::FILE* fp_;
};

void use() {
    FileGuard f("a.txt");      // 构造即获取
    risky();                   // 抛异常也不泄漏，析构照常执行
}                              // 作用域结束自动 fclose
```

- **标准库中的 RAII 范例**：`std::unique_ptr`/`shared_ptr`（内存）、`std::lock_guard`/`unique_lock`（互斥量）、`std::fstream`（文件）、`std::vector`/`std::string`（动态内存）。
- **设计要点**：
  - 资源在构造中获取，失败就抛异常（不要"半初始化"对象）。
  - 拷贝语义：要么禁止拷贝，要么实现引用计数/移动（现代做法：**移动语义 + 零法则**）。
  - 析构函数应 **`noexcept`**：抛异常会导致 `std::terminate`（尤其在栈展开期间）。

**RAII 失效的边界**（面试加分项）：

- `longjmp`（跳过析构）、`std::exit`/`abort`、未捕获异常触发 `terminate`、信号处理函数内跳出、`operator new` 失败且资源未包裹。
- 结论：RAII 只能覆盖"正常栈展开路径"，所以不推荐在 C++ 里混用 `setjmp/longjmp`。

## 5. `new`/`delete` 与 `malloc`/`free` 有何区别？

**考察点**：运算符 vs 库函数、构造/析构的介入。

**要点**：

| 维度 | `new` / `delete` | `malloc` / `free` |
| ---- | ---------------- | ----------------- |
| 本质 | **运算符**（`operator new` 可重载） | **标准库函数**（`<cstdlib>`） |
| 是否调用构造/析构 | **是**：`new` 先分配再构造，`delete` 先析构再释放 | 否，只操作裸内存 |
| 返回类型 | 具体类型指针，无需强转 | `void*`，**须强转** |
| 大小 | 编译器自动推导 `sizeof(T)` | 手工 `sizeof(T) * n` |
| 失败行为 | 抛 `std::bad_alloc`（`nothrow` 版本返回 `nullptr`） | 返回 `NULL` |
| 数组 | `new[]` / `delete[]` 配套（记录元素个数） | `malloc` 只管字节数 |
| 定制 | 可在**类内重载** `operator new`（对象池、内存追踪） | 只能全局替换 |
| 底层实现 | `operator new` 内部通常调用 `malloc`（libstdc++ 中是 `malloc`） | 调用分配器（`brk`/`mmap`） |

**要点补充**：

- **绝不能混用**：`new` 配 `free`、`malloc` 配 `delete` 都是未定义行为 —— 前者不调用析构函数，后者可能因缺少分配器元数据（cookie）而崩溃。
- `new[]` 为什么必须配 `delete[]`：对**有非平凡析构函数**的类型，分配器会额外记录元素个数（通常放在返回地址前 8 字节的 cookie），`delete[]` 靠它循环调用 N 次析构；用 `delete` 只会析构一个。
- `new` 的完整过程：`operator new(sizeof(T))` 拿内存 → 调用构造函数；编译器在异常时会自动 `operator delete` 回滚。`delete p`：调用析构 → `operator delete(p)`。
- **placement new** 只构造不分配：`new (buf) T(...)`，需**手动** `p->~T()`，再自行管理内存（容器/内存池的基础）。

```cpp
// 分配失败处理
int* p = new (std::nothrow) int[100];   // 不抛异常，返回 nullptr
if (!p) { /* 处理 */ }
delete[] p;

A* a = new A(1);      // 分配 + 构造
delete a;             // 析构 + 释放

void* raw = ::operator new(sizeof(A));     // 只分配，等价于 malloc
A* b = new (raw) A(2);                     // placement new 构造
b->~A();
::operator delete(raw);
```

> 追问「`operator new` 和 `new` 表达式的关系」：`new` 表达式 = 调用 `operator new` 分配 + 调用构造函数，前者可以被重载/替换，后者由编译器生成。

## 6. 栈和堆有何区别？

**考察点**：两种存储区的管理与使用差异。

| 维度 | 栈（Stack） | 堆（Heap） |
| ---- | ----------- | ---------- |
| 管理者 | **编译器**自动（函数调用约定） | **程序员**（裸指针）或 RAII/智能指针 |
| 分配时机 | 编译期确定大小与偏移 | 运行期动态 |
| 分配/释放速度 | 极快（移动栈指针，O(1)） | 较慢（分配器查找空闲块 + 可能系统调用） |
| 空间大小 | 小且固定（Linux 默认 8 MB/线程，`ulimit -s`） | 大（受进程虚拟地址空间与物理内存限制） |
| 增长方向 | 高地址 → 低地址（向下增长） | 低地址 → 高地址 |
| 碎片 | 无 | 有（内部/外部碎片） |
| 生命周期 | 作用域结束自动回收 | 直到显式释放（或进程退出） |
| 线程关系 | **每线程私有**（故线程数受栈大小限制） | **进程内共享**（需同步） |
| 常见内容 | 局部变量、函数参数、返回地址、寄存器保存区 | `new`/`malloc` 的对象、容器底层数组 |
| 典型故障 | 栈溢出（递归过深、超大局部数组） | 内存泄漏、碎片、OOM |

**要点补充**：

- 栈的"分配"本质是**函数序言里的一条指令**（如 `sub rsp, 0x20`），不涉及任何数据结构查找；堆的分配要走分配器逻辑（空闲链表/分级缓存）。
- "栈快"不只因为指针加减，还因为**局部性好**：栈上数据集中在热缓存，堆对象分散且每次访问可能 cache miss。
- 栈溢出实例：`void f() { char buf[10 * 1024 * 1024]; }` 直接爆栈；递归无终止条件同理。
- 现代 C++ 实践：优先用栈对象（+ RAII）而非裸 `new`，把"堆分配"限定在真正需要动态生命周期的场合。

```cpp
void f() {
    int a[100];                       // 栈：函数返回自动回收
    int* p = new int[100];            // 堆：必须 delete[]
    std::vector<int> v(100);          // 数据在堆，句柄在栈，析构自动释放
    delete[] p;
}
```

## 7. 栈和堆的内存分配方式有何不同？

**考察点**：从"编译器生成的指令"到"分配器实现"的层次差异。

**一、栈的分配方式**

- 由**编译器**在函数序言/尾声生成指令：调整栈指针（`sub rsp, N` / `add rsp, N`）+ 用 rbp/rsp 相对寻址访问局部变量；部分变量直接放在寄存器里（寄存器分配）。
- 特点：**O(1)、无碎片、无锁、无系统调用**（除非触发栈扩展导致缺页异常由内核补页）。
- 每次函数调用创建**栈帧**：返回地址、保存的寄存器、参数、局部变量；参数传递还可能走寄存器（System V AMD64 用 6 个整型寄存器）。

**二、堆的分配方式**

1. **分配算法（glibc malloc 为例）**：
   - 维护 **chunk 链表**（fastbins / smallbins / largebins / unsorted bin），采用**首次适应 + 分割 + 合并（coalescing）**策略。
   - 小分配走 bins 复用，大分配可能走 `mmap`。
2. **系统调用层面**：
   - `brk`/`sbrk`：抬高进程 data 段末尾（program break）来扩展堆，适合**小分配**；释放不归还内核（仍留在堆里复用）。
   - `mmap`：**大分配**（默认阈值约 128 KB，`M_MMAP_THRESHOLD`）用匿名映射，`free` 时 `munmap` 直接归还内核。
3. **工程级分配器**（tcmalloc / jemalloc / mimalloc）：**多级缓存** —— thread cache（无锁）→ central cache → page heap，按 size class 分级，降低锁竞争与碎片。
4. 每个已分配块前有**元数据头**（size、in-use 标志、prev_size 等），所以实际占用 > 请求字节数 → 这是"内部碎片"的来源；块间空隙形成"外部碎片"。

```cpp
void* p = malloc(24);   // 实际占用 ≥ 24 + 头部(8~16) + 对齐，通常 32 字节
free(p);
```

**三、对比结论**

| 维度 | 栈 | 堆 |
| ---- | -- | -- |
| 分配动作 | 修改栈指针寄存器 | 查空闲链表/分级缓存 + 可能 `brk`/`mmap` |
| 释放动作 | 恢复栈指针 | 归还 bins / 延迟合并 / `munmap` |
| 元数据 | 无（编译期确定偏移） | 每块有头部 + 分配器全局结构 |
| 并发 | 线程私有，无竞争 | 共享，需锁/线程缓存 |
| 碎片 | 无 | 内部 + 外部碎片 |

> 一句话总结：**栈分配是"移动指针"，堆分配是"分配器管理 + 可能系统调用"。**

## 8. 全局、局部、静态局部对象何时初始化和销毁？

**考察点**：三种存储期（静态 / 自动 / 静态局部的动态初始化时机）。

| 对象 | 存储期 | 初始化时机 | 销毁时机 |
| ---- | ------ | ---------- | -------- |
| 全局 / 命名空间作用域对象 | 静态存储期 | 静态初始化（常量初始化/零初始化）在**编译期或程序加载时**；动态初始化在 **`main` 之前** | **`main` 返回后**，按初始化**逆序**销毁 |
| 局部（自动）对象 | 自动存储期 | **执行到定义语句时**初始化 | **离开作用域时**立即析构（含异常栈展开） |
| 静态局部对象 | 静态存储期 | **首次执行到该定义**时初始化（懒加载，只一次） | `main` 返回后（与全局对象一起，逆序销毁） |

**要点补充**：

- **"静态初始化顺序问题"（SIOF, Static Initialization Order Fiasco）**：不同编译单元（.cpp）中全局对象的**动态初始化顺序未定义**。若 A 的构造函数使用 B 的全局对象，而 B 尚未构造 → 使用未初始化对象（UB）。

```cpp
// a.cpp
extern std::vector<int> g_data;      // b.cpp 中定义
int g_first = g_data.size();         // 危险：g_data 可能还没构造

// b.cpp
std::vector<int> g_data{1, 2, 3};
```

**改用函数内静态局部变量（Meyers Singleton）即可根治**——C++11 起保证其初始化是线程安全的：

```cpp
std::vector<int>& data() {
    static std::vector<int> d{1, 2, 3};   // 首次调用时构造
    return d;                             // 之后就只返回引用
}
int g_first = data().size();              // 安全：调用时才构造
```

- **C++11 起线程安全保证**：静态局部变量的初始化编译器会生成守卫变量（`__cxa_guard_acquire/release`，对应 `std::call_once` 式的语义），多线程同时到达时只有一个线程执行初始化，其余阻塞等待。
- 局部对象的初始化点就是**定义语句执行时**（不是函数入口），所以 `goto`/`if` 跳过定义则不会构造；`switch` 中 `case` 标签跨越初始化也会报错，需加 `{}`。
- 析构顺序：**先构造的后析构**（栈式逆序）；静态对象跨越线程结束时，若其他线程还在使用，可能出现"静态对象析构后仍被访问"（故 `main` 返回后应确保线程已 join）。
- 静态对象若从未使用（TU 未链接/未初始化）可能不构造 —— 但静态局部变量一定是"用到才构造"。

```cpp
struct Logger {
    Logger()  { std::cout << "init\n"; }
    ~Logger() { std::cout << "destroy\n"; }
};

Logger g;                       // 输出 init（在 main 前）

void f() {
    static Logger s;            // 第一次调用 f 时输出 init
    Logger l;                   // 每次调用都 init/destroy
}                               // l 在这里 destroy

int main() { f(); f(); }        // g 在 main 返回后 destroy，s 紧随其后（逆序）
```

## 9. 类成员初始化顺序由什么决定？

**考察点**：初始化列表顺序 ≠ 实际初始化顺序。

**要点**：

- 成员的实际初始化顺序**由成员在类中的声明顺序决定**，与**初始化列表的书写顺序无关**。
- 完整顺序：
  1. **虚基类**子对象（按继承的深度优先、从左到右）
  2. **基类**子对象（按继承列表的声明顺序）
  3. **成员变量**（按在类中声明顺序）
  4. 构造函数体执行
- 因此初始化列表写反会导致"用未初始化的成员去初始化另一个成员" → 得到未定义值（不是 UB，但值不确定），编译期加 `-Wreorder` 会给警告。

```cpp
class Bad {
    int b_;      // 声明顺序：b_ 在前
    int a_;
public:
    Bad(int v) : a_(v), b_(a_ + 1) {}   // 危险！实际先初始化 b_，此时 a_ 还没初始化
    // 实际执行：b_ = a_(未初始化) + 1; 然后 a_ = v;
};
```

- 正确写法：**初始化列表顺序与声明顺序保持一致**，并给每个成员显式初始化。
- 现代做法（零法则友好）：**在声明处给默认成员初始化器（NSDMI）**，只在需要时才用初始化列表覆盖：

```cpp
class Good {
    int b_ = 0;
    int a_ = 0;
public:
    Good(int v) : a_(v), b_(a_ + 1) {}   // 顺序与声明一致（a_ 声明在前）
};
```

- **必须在初始化列表中初始化**（否则编译错误或无法达成语义）的成员：
  - `const` 成员（只能初始化，不能赋值）
  - **引用成员**（必须绑定且不可改绑）
  - **无默认构造函数的类类型成员**（如 `std::mutex`、`std::atomic`、自定义类型）
  - 基类子对象（需调用带参基类构造）
- 析构顺序恰好相反：成员逆序析构 → 基类 → 虚基类。
- 面试常考的连锁结论：因为基类先于派生类构造，"**在基类构造中调用虚函数不会多态**"；也因为成员按声明顺序构造，**初始化列表的顺序优化不了任何东西**，只是文档作用。

## 10. 构造中途抛异常，已构造成员如何释放？

**考察点**：部分构造对象的析构规则 + 栈展开。

**要点**：

- 规则：**构造函数抛出异常时，该对象的析构函数不会被调用**（因为对象从未"完整构造"），但**已经构造完成的基类子对象和成员子对象会按逆序自动析构**。
- 机制就是**栈展开**：编译器为构造函数生成异常表（.eh_frame），异常抛出时逐个回滚已完成的构造步骤。

```cpp
struct Member {
    Member(const char* n) : name(n) { std::cout << "ctor " << name << "\n"; }
    ~Member()                        { std::cout << "dtor " << name << "\n"; }
    const char* name;
};

struct Base { ~Base() { std::cout << "~Base\n"; } };

struct Foo : Base {
    Member m1{"m1"};
    Member m2{"m2"};
    Member m3{"m3"};
    Foo() {
        std::cout << "body\n";
        throw std::runtime_error("boom");
    }
    ~Foo() { std::cout << "~Foo\n"; }   // 不会执行
};

int main() {
    try { Foo f; } catch (const std::exception& e) { std::cout << "caught\n"; }
}
```

输出：

```text
ctor m1
ctor m2
ctor m3
body
dtor m3        // 成员逆序析构
dtor m2
dtor m1
~Base          // 最后析构基类
caught
```

注意 `~Foo` **没有出现** —— 完整对象未构造成功，Foo 的析构不参与。

**工程含义与常见陷阱**：

1. **裸资源会泄漏**：如果构造函数里 `p_ = new int[100];` 之后又抛异常，`p_` 尚未被任何 RAII 接管 → 泄漏。**解决：成员一律用智能指针/容器等 RAII 类型**，已构造成员的析构就自动兜底了。
2. **多步构造的资源回滚**：若确实要管理两个裸资源，用 `std::unique_ptr` 成员或"先构造成员再交换"的写法：

```cpp
class Two {
    std::unique_ptr<A> a_;
    std::unique_ptr<B> b_;
public:
    Two() : a_(std::make_unique<A>()), b_(std::make_unique<B>()) {}
    // b_ 构造失败 → a_ 自动析构释放，无泄漏
};
```

3. **函数 try-block**（constructor function-try-block）：可捕获成员初始化列表抛出的异常：

```cpp
Foo() try : m_(risky()) {
    // ...
} catch (const std::exception& e) {
    // 注意：这里成员已被析构，不能再访问成员或使用 this
    throw;    // 通常需要重新抛出，否则对象处于"半死"状态
}
```

4. **派生类构造中抛出**：基类子对象已构造 → 基类析构会执行；派生类的成员按完成顺序逆序析构。

**面试加分结论**：

- "已构造的成员不用手动释放，编译器保证逆序析构。"
- "但**这块内存会被释放**（`operator delete` 由 `new` 表达式在异常时调用），泄漏的只是构造函数里**没有交给 RAII 管理的裸资源**。"
- "所以两条铁律：**成员用 RAII 类型；析构函数保持 `noexcept`**（在栈展开期间抛异常会直接 `std::terminate`）。"
