## 二、案例改版后的新趋势

1. **传统常考题分题型必须掌握**——虽然看趋势后续再考可能性变小，但仍是重点，**目标 20 分**。
2. **重点是对超纲技术考题**——超纲题不局限于软件工程，而是**"软件 + 架构设计"的结合**，讲义会着重讲解，**目标 15 分**。
3. **超纲题考的不是知识，是能力**——给一个项目背景 + 一张架构图（或让你从备选词里选），让你完成架构设计填空。**背景和架构图来源于硕士论文或新技术新框架**。
4. **应对方法：培养举一反三**——不要妄想会出教材里的架构原型，而是**通过学习已有的架构图，掌握架构设计精髓**，从而能应对比陌生架构图的设计填空。
5. **光听没有用**——历年架构题里超纲的架构图填空题很多，**必须自己动手做超纲题**才有效。

## 三、解题技巧（现场应试纪律）⭑

| # | 技巧 |
| - | ---- |
| 1 | **第一题必做**，不用犹豫，先做完第一题 |
| 2 | 后面四选一：**快速浏览所有题目的"问题"**，看描述能不能看懂，再选 |
| 3 | **问题与题目描述相结合**——尤其系统分析与设计问题、新技术问题，**答案一般都在题目描述里**，从描述中提炼答案 |
| 4 | **以最简洁的语言写**，一般题目有最大字数要求，不能超过 |
| 5 | 遇到新知识点**不要慌，稳住心态** |
| 6 | **列条目回答**——把自认为对的都写上，**多写不扣分，少写一定扣分** |
| 7 | 分析题目的**倾向性**，顺势答题 |
| 8 | 机考后无完整真题流出，命题会**根据回忆知识点出题**——所以本讲的真题回忆就是最接近真题的东西 |

> **常见误答**：把时间全花在想"这题我不会"上。**正确做法是先把第一题（传统架构）做完**——那是白给的 20 分，超纲题放到最后，有时间再啃。

## 四、软件架构设计（第一类 · 拿分基本盘）

> 质量属性与架构风格的完整版见 [系统架构设计](系统架构设计.md)，此处只留案例速查。

### 4.1 质量属性：开发期 6 + 运行期 7 ⭑

| 期 | 属性 | 定义要点 | 设计策略关键词 |
| -- | ---- | -------- | ------------ |
| 开发期 | **易理性** | 设计被开发人员理解的难易程度 | 模块化、规范命名 |
| 开发期 | **可扩展性** | 增加新功能 / 适应需求变化的能力（灵活性） | 抽象、插件、配置化 |
| 开发期 | **可重用性** | 重用系统或某一部分的难易程度 | 通用组件、设计模式 |
| 开发期 | **可测试性** | 以测试证明满足需求规范的难易程度 | 接口隔离、依赖注入 |
| 开发期 | **可维护性** | 识别并实施修改的难易程度 | 监控告警 |
| 开发期 | **可移植性** | 转移到另一运行环境的难易程度 | 屏蔽 OS / 硬件差异 |
| 运行期 | **性能** | 及时提供响应的能力（响应时间、吞吐量） | 优先级队列、增加计算资源、减少计算开销、并发、资源调度 |
| 运行期 | **安全性** | 阻止非授权使用、拒绝服务 | 入侵检测、用户认证、用户授权、追踪审计 |
| 运行期 | **可伸缩性** | 应对负载变化的能力 | 可伸缩性 / 弹性 |
| 运行期 | **互操作性** | 与其他系统交换数据与相互调用的难易程度 | — |
| 运行期 | **可靠性** | 错误或意外使用下维持功能的能力 | 心跳、Ping/Echo、冗余、选举 |
| 运行期 | **可用性** | 正常运行的时间比例 | 心跳、Ping/Echo、冗余、选举 |
| 运行期 | **鲁棒性** | 非正常情况（非法操作、软硬件故障）下仍能正常运行 = **健壮性 / 容错性** | — |
| 运行期 | **功能性** | 系统所能完成所期望工作的能力 | — |

**质量属性场景六要素** ⭑：刺激源、刺激（人/计算系统/任何其他刺激器）、环境、制品、响应、响应度量。

| 场景要素 | 说明 |
| ---- | ---- |
| 刺激源 | 某个**生成刺激**的实体（人、计算机系统或任何其他刺激器） |
| 刺激 | 该刺激是**当前刺激**（系统的一种事件），如**需要处理某个业务逻辑的请求** |
| 环境 | 刺激发生在**某些条件**下（正常操作、峰值负载、故障） |
| 制品 | 某个制品被刺激（整个系统或系统的一部分） |
| 响应 | 刺激**发生后**所采取的行动（维护或修改系统） |
| 响应度量 | 响应发生时，应**能够以某种方式对其进行度量**，以对需求进行测试（故障间隔时间、恢复时间） |

### 4.2 架构风格：构件与连接件速查

| 架构风格 | 常见关键字及例子 | 简介 |
| ---- | ---- | ---- |
| 数据流-批处理 | **传统编译器**，每个阶段产生一个中间文件 | 一个接一个，**以整体为单位** |
| 数据流-管道-过滤器 | 编译器下**一个阶段的输入**，是上一个阶段的输出 | 一个接一个，**前一个输出是后一个输入** |
| 调用/返回-主程序-子程序 | | **显示调用**，主程序直接调用子程序 |
| 调用/返回-面向对象 | 对象是构件，通过对象调用封装的方法和属性 | 对象是**抽象数据类型的实例** |
| 调用/返回-层次结构 | | 分层，最多影响其上下两层（**通常只能影响相邻**） |
| 调用/返回-客户/服务器 | 两层 C/S；三层 C/S：表示层、功能层、数据层 | — |
| 独立构件-进程通信 | 进程间通信的消息传递，同步或异步 | 消息是**命名**的 |
| 独立构件-事件驱动-隐式调用 | 事件触发动作，如**程序方法的语法高亮、语法错误提示** | **不直接调用**，通过**事件**驱动 |
| 虚拟机-解释器 | 自定义流程，按流程执行规则 | 解释引擎、存储区、数据结构 |
| 虚拟机-规则系统 | 灵活组合**规则集**、选择器、工作内存 | DSS 和人工智能、专家系统 |
| 数据中心-仓库 | 现成**数据仓库的集成开发环境** | 中央共享数据，独立处理单元 |
| 数据中心-黑板 | **知识源与黑板、逻辑推理** | 黑板、黑板、单元、知识源 |
| 闭环控制风格 | **汽车巡航定速**、空调温度调节 | 发出控制命令并不断调整 |

### 4.3 下午案例分析最常考的 7 种风格对比 ⭑

| 架构风格 | 主要特点 | 主要优点 | 主要缺点 | 适合领域 |
| ---- | ---- | ---- | ---- | ---- |
| **管道-过滤器** | 过滤器相对独立 | 功能模块复用；维护性和可扩展性较好；具有独立性；模块独立执行 | 不适于交互性强（对存在关系数据流必须进行协调） | 系统可划分为清晰的模块；**有清晰的数据流** |
| **面向对象** | 力争实现问题空间和软件系统结构的一致性 | 高度模块化；实现封装、易维护、易扩充；易扩充性 | 增加了对象与类之间的间接性 | 多种领域 |
| **事件驱动** | 系统由若干子系统或构件组成；每个构件有独立处理机制和多个事件处理器；每个构件常有一个事件处理器 | 适合分布式系统；**解耦**；异步、并发的处理能力 | 构件之间存在**复杂的逻辑关系** | 一个系统可从外部对象获得数据 |
| **分层风格** | 不同的构件形成层次结构（可替换）；多层次相互独立 | 支持系统设计过程中不同层的抽象；**可扩展性**；支持复杂系统 | 不同层之间耦合、**依赖关系难管理** | 适合功能层次明确的系统 |
| **数据共享风格** | 采用多个构件共享数据存储；中央数据存储与独立构件 | 便于数据共享；数据存取效率高，以数据为中心 | 交互复杂、**数据一致性**问题 | 适合专家系统等**以数据为中心**的求解 |
| **解释器风格** | 系统核心是虚拟机 | 可以用多种操作来解释一个句子；灵活应对 | 适合特定领域 | 适于模式匹配系统与语言编译器 |
| **闭环控制风格** | 通过不断的测量被控对象，认识和掌握被控对象；将控制理论引入系统结构设计 | 把控制理论引入软件系统结构中 | 系统一定在有目的的作用下运行 | 存在有**目标、信息处理和反馈控制过程**的系统 |

> **常见误答**：把"管道-过滤器"和"批处理"混为一谈。**批处理 = 整体为单位**（每个阶段产生一个中间文件），**管道-过滤器 = 前一个的输出就是后一个的输入**，且管道-过滤器**可以并行**执行不同过滤器。

## 五、系统开发基础（第二类）⭑

### 5.1 结构化分析三大模型 + 数据字典

| 模型 | 图形 | 作用 |
| ---- | ---- | ---- |
| **功能模型** | **数据流图（DFD）** | 描述系统的**功能分解** |
| **行为模型** | **状态转换图** | 描述系统**状态变化** |
| **数据模型** | **E-R 图** | 描述**数据对象及其关系** |

**数据流图四要素**：数据流、加工（处理）、数据存储、外部实体。
**数据字典五项**：数据项、数据结构、数据流、数据存储、处理。

**平衡原则**（高频考点）：

1. **父图与子图的平衡**——任何一张**子图的输入数据流总数 = 父图某条输入数据流**，输出同理。
2. 如果某个加工的**输入数据流全部来自该子图**，而**输出数据流全部输出到该子图**，那么它是**整体的一张子图**。

### 5.2 UML 六种关系

| 关系 | 符号 | 说明 |
| ---- | ---- | ---- |
| 关联 | 实线 | 对象之间某种语义上的**联系** |
| 依赖 | 虚线 + 箭头 | 一个元素**改变**定义会影响另一个 |
| 泛化 | 实线 + 空心三角 | 特殊类与一般类之间的**一般化关系** |
| 聚合 | 空心菱形 | 整体与部分，**部分可独立存在** |
| 组合 | 实心菱形 | 整体与部分，**部分不可独立存在** |
| 实现 | 虚线 + 空心三角 | 接口与实现类 |

**UML 图（案例重点记 4 种）** ⭑：**用例图**、**类图**、**活动图**、**状态图**。交互图（顺序图 / 协作图）也是常客。

### 5.3 面向对象分析模型

- **用例模型** → 参与者和用例（识别参与者 → 识别用例 → 合并与抽象用例）
- **分析模型** → 数据模型（类与对象、关联、泛化、依赖）、行为模型（用例实现、顺序图、状态图、类图、协作图、活动图）

### 5.4 顺序图片段 8 种 ⭑

| 片段 | 语义 |
| ---- | ---- |
| **alt** | 条件分支，多个互斥的片段 |
| **opt** | 可选行为，只有一个条件 |
| **loop** | 循环执行 |
| **break** | 中断行为，跳出循环 |
| **par** | 并行执行，多个消息同时发出 |
| **critical** | 临界区，确保原子性 |
| **neg** | 不应发生的行为 |
| **ref** | 引用其他顺序图 |

### 5.5 顺序图 vs 协作图

- 顺序图：**强调消息发生的先后顺序**，用**生命线**表示对象。
- 协作图：**强调对象之间的协作关系**（通信图），用**关联角色**表示。
- 二者可以互相转换，**表达的是同一信息**。

## 六、数据库系统（第三类 · Redis 是必考）⭑

### 6.1 三类数据库定义

| 类型 | 定义 | 关键点 |
| ---- | ---- | ---- |
| **关系型数据库** | 建立**在关系模型基础上的数据库**，借助集合代数等数学概念和方法来处理数据 | 实体及联系用**二维表**表示 |
| **NoSQL** | **非关系型**数据库，特点是**解决大规模数据集合的存储问题** | 为**解决大规模数据集合**而生，尤其**海量数据、高并发** |
| **内存数据库** | 将**数据整体存储在内存中**，提高性能 | — |

### 6.2 关系型 vs NoSQL（9 维）⭑

| 维度 | 关系型 | NoSQL |
| ---- | ---- | ---- |
| 并发支持 | 支持并发，效率低 | **并发性高** |
| 存储与查询 | 关系表方式存储，SQL 查询 | 海量数据存储，查询效率高 |
| 扩展方式 | 向上扩展 | **向外扩展** |
| 索引方式 | B 树、哈希等 | **键值索引** |
| 应用领域 | 面向通用 | 特定领域 |
| 数据类型 | 实时一致性 | **弱一致性** |
| 事务 | 高事务 | 弱事务 |
| 数据量 | 有限数据 | **海量数据** |
| 水平扩展 | 弱 | **强** |
| 数据容量 | 有限 | **海量** |

### 6.3 缓存技术：Memcached vs Redis

| 项 | Memcached | Redis |
| ---- | ---- | ---- |
| 本质 | 高性能**分布式内存对象缓存系统**，用于动态 Web 应用以减轻数据库负载 | 开源的**使用 ANSI C 语言编写**、支持网络、可**基于内存亦可持久化**的日志型、**Key-Value** 数据库，并提供多种语言 API |
| 存储内容 | 在内存里维护一个统一的**巨大 hash 表**，可用存储**各种格式**数据（图片、视频、文件、数据库检索结果） | — |
| 底层 | — | **K-V 内存数据库** |
| 数据结构 | 仅 key-value | 字符串、哈希、**列表**、**集合**、**有序集合**五种基本 + 三种特殊 |

**Redis 与 Memcached 的 5 点差异** ⭑：

1. Redis 与 Memcached **都是把数据存在内存中、都是内存数据库**，都支持 **key-value** 数据结构；Memcached 还可用于缓存其他东西（图片、视频等），Redis 还支持 **list、set、hash** 等结构。
2. **Redis 并不是所有数据都一直存储在内存中**——这是和 Memcached 最大的区别。**当物理内存用完后**，Redis 可以将一些**很少被访问的 value 交换到磁盘**。
3. Redis 在很多方面**比 Memcached 优秀**：不仅限于**持久化**方面，Redis 还可以对数据进行**复杂数据类型**的存储。
4. Redis 可以**将数据持久化到磁盘**（RDB / AOF），而 Memcached **只是简单的 key-value 缓存**。
5. Redis 还有很多**更丰富的数据结构**（list、set、hash、zset），可以应用在**更多场景**。

### 6.4 Redis 数据结构与五大特性

- **五种基本类型**：String、List、Set、Sorted Set、Hash
- **三种特殊类型**：**Geo**（地理位置）、**HyperLogLog**（基数统计）、**Bitmaps**（位图，底层是 String，可当数组用）
- **五大特性**：① **基于内存存储** ② **高效的数据结构**（B+ 树） ③ **合理的数据编码** ④ **单线程** ⑤ **原子性**

> 常见误答：把"Redis 是单线程"理解成"Redis 只有一个线程"。**Redis 6.0 引入的是 I/O 多线程**（网络读写与协议解析并行），**命令执行始终是单线程**；Redis 7.0 进一步优化（I/O 线程默认启用、支持部分命令并行）。见第十一节。

### 6.5 缓存三大问题（必考）⭑

| 问题 | 现象 | 原因 | 解法 |
| ---- | ---- | ---- | ---- |
| **缓存穿透** | 查一个**根本不存在**的数据，缓存和数据库都没有 | 恶意攻击用大量不存在的 key 反复查询 | ① **布隆过滤器**（不存在则直接返回）② **缓存空值**（设较短过期时间）③ **实时监控 + 淘汰** |
| **缓存击穿** | 一个**热点 key** 过期，大量请求同时打到数据库 | 热点数据大多设置过期时间，过期瞬间大量并发 | ① 热点数据**永不过期 + 后台更新** ② **互斥锁**，保证只有一个线程重建缓存 |
| **缓存雪崩** | **大量 key 同时过期**或 Redis 宕机，大量请求打到数据库 | ① 大量数据同时过期 ② 缓存服务宕机 | ① **过期时间加随机值**打散 ② **Redis 集群 / 高可用**（哨兵、Cluster）③ 熔断降级 |

**缓存雪崩的两类成因与对策**：

- **缓存击崩**（同一热点）：缓存中数据**大批量**到达过期时间，而查询数量巨大 → 缓存失效，数据库压力过大甚至 down 机。**缓存击穿则是热点 key 过期**——只有大量并发请求打到数据库。
- **缓存雪崩一般有两种情况**：大量数据**同时过期**、**Redis 服务宕机**。

### 6.6 热 Key 问题 ⭑

- **什么是热 Key**：访问频率高的 key（如秒杀、热点新闻）。
- **产生原因**：① 用户消费数据大于生产数据（如秒杀）② **请求分片不均**（固定 Hash 落到一台服务器）。
- **解决方案**：① **Redis 集群打散**（增加分片副本，均匀流量）② **将热点 key 分散到不同服务器中**（可用 Redis 的 setnx 实现）③ **使用二级缓存**（即 JVM 本地缓存，减少 Redis 读请求）。

### 6.7 过期策略与内存淘汰策略

**三种过期策略**：**定时过期**（对每个 key 设置定时器，到期删除）→ 缺点是 CPU 压力大；**惰性过期**（访问时检查，过期则删除）→ 缺点是可能永不删除；**定期过期**（每隔一段时间扫描并删除过期 key）→ 折中。

**内存淘汰策略**（Redis 内存满时选谁淘汰）⭑：

| 策略 | 说明 |
| ---- | ---- |
| **volatile-lru** | 设置了过期时间的 key 中**最近最少使用**淘汰 |
| **allkeys-lru** | **所有 key** 中最近最少使用淘汰 |
| **volatile-lfu** | 4.0 新增：过期 key 中**最不经常使用**淘汰 |
| **allkeys-lfu** | 4.0 新增：所有 key 中最不经常使用淘汰 |
| **volatile-random** | 过期 key 中**随机**淘汰 |
| **allkeys-random** | 所有 key 中随机淘汰 |
| **volatile-ttl** | 过期 key 中**剩余过期时间最短**淘汰 |
| **noeviction** | **默认策略**：内存不足时**新写入操作报错** |

> **常见误答**：讲义原文把 volatile-lru 的触发条件写作"内存不足"，更准确的说法是"**内存不足以容纳新写入的数据**（需在 maxmemory 内写入）时触发淘汰"。

| 场景 | 说明 |
| ---- | ---- |
| **缓存** | 降低数据库压力、缓解访问热点；天然有**热点数据、**低数据库压力等优点 |
| **排行榜** | zset 数据结构（score 实时排序） |
| **计数器** | 累加操作、批量统计 |

| **位运算** | 签到、统计：Bitcount、Bitmap |

### 6.9 持久化：RDB vs AOF ⭑

| 维度 | **RDB**（Redis Database） | **AOF**（Append Only File） |
| ---- | ---- | ---- |
| 原理 | **定时生成内存数据快照**，保存为 `dump.rdb` 文件 | 记录所有**写操作命令**（文本格式），通过**重放命令**恢复数据 |
| 优点 | 高性能、**二进制压缩存储**（适合大文件）、恢复速度快（比 AOF 快 ≥10 倍） | 数据完整性高；文件体积较大；恢复速度慢（需逐条重放） |
| 缺点 | **没法做到实时持久化**（两次 RDB 之间可能丢失数据）；新版本有损坏格式问题 | 恢复慢；**写文件与 RDB 兼容性问题** |
| 触发 | `save` / `bgsave`；`shutdown` 时会执行 | `always`（每条命令）/ `everysec`（每秒）/ `no`（默认不开启） |
| 数据丢失 | 两次 RDB 之间 | 最多丢 1 秒（everysec） |

> **常见误答**：讲义"每 5 分钟备份一次"的表述易被记成 AOF 的行为——**RDB 是"定时快照"**（讲义给的例子是每 5 分钟），**AOF 是"追加写命令"**。

### 6.10 高可用：主从 / 哨兵 / Cluster ⭑

| 模式 | 机制 | 关键点 |
| ---- | ---- | ---- |
| **主从复制** | 全量复制 + 增量复制 | `replicaof`；从节点只读；**主从切换会丢数据**（异步复制） |
| **哨兵（Sentinel）** | 监控主从节点，主节点故障时自动选新主 | 三个作用：**发送命令等待回复**、**判断主节点是否下线**、**自动切换主节点**；客观下线 = 超时；主观下线 = 多个哨兵一致认为下线 |
| **Cluster** | 数据分片，**16384 个槽位** | **Hash Slot 插槽算法**（不是一致性 Hash）；客户端按**槽位路由**；节点间用 **Gossip** 协议；故障判定：**主观下线 → 客观下线**；扩缩容需**迁移槽位** |

**主从复制的两个阶段**（案例填空高频）：

- **第一阶段**：① 请求数据同步 ② 判断是否需要同步 → **全量复制** ③ 数据同步 → **部分复制**（判断主从是否一致）
- **第二阶段**：① 发送 repl_backlog 缓冲 ② 判断是否需要同步 → 加载缓冲区 → **offset 同步**

### 6.11 分布式锁（超纲高频）⭑

**三种锁的对比**：

| 锁 | 范围 | 特点 |
| ---- | ---- | ---- |
| **线程锁** | 方法 / 代码块 | 同一 JVM 内有效；因为线程锁实现本质上依赖共享内存状态，**显示 lock 是共享某个变量（state）** |
| **进程锁** | 进程间 | 进程有独立性，无法访问其他进程资源，用 **synchronized** 等线程锁无法实现 |
| **分布式锁** | 多进程 / 多机 | 当多个进程**不在同一系统**中时 |

**Redis 分布式锁实现（基于 Redisson）**：

1. **加锁**：`setnx`（虚拟机的 `setnx` → 相当于 `set key value NX`）；再加 **`pexpire` 设置超时时间**（`set key value NX PX`）。
2. **虚拟机与宿主机对共享资源加锁**——保证**同一时间只有一个虚拟机**能操作共享资源。
3. **解锁**：必须**执行 `DEL` 释放锁**，否则其他线程永远拿不到锁 → 实际是**Lua 脚本**保证原子性（`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end`）。
4. **续期（看门狗）**：线程 1 持锁但业务未执行完 → **锁过期被释放，线程 2 拿到锁 → 线程 1 再操作就出错**。**Redisson 用 watch dog 看门狗**（后台线程每 10 秒检查一次）自动续期。

**Redlock 算法 5 步**（多 master 部署，如 5 台）⭑：

1. **获取当前时间**（以毫秒为单位）。
2. 按顺序向 **5 个 master 节点请求加锁**，客户端设置网络连接和响应超时时间，且**超时时间要小于锁的失效时间**（如 50ms）。
3. 客户端**使用当前时间减去步骤 1 的时间**，得到**获取锁使用的时间**；当且仅当**超过一半（N/2+1，即 3/5）**的 master 节点都获得锁，并且**总用时小于锁的有效时间**时，才算加锁成功。
4. 如果获取锁失败，则**在所有的 master 节点上解锁**（即便有些节点根本没加成功）。
5. 简化版：若在 **N/2+1** 个节点成功加锁，并且**使用的时间小于失效时间**，即可认为加锁成功。

> **加分点（讲义未提）**：Redlock 存在**正确性争议**——Kleppmann（2016《How to do distributed locking》）指出在 **GC 长停顿、时钟跳变、网络延迟**下，持有者可能"以为自己还持锁"而造成双写；且 Redlock **不提供单调递增的 fencing token**。因此工程上要区分：**效率锁**（防重复计算，单实例 Redis 锁 + 看门狗足矣）vs **正确性锁**（双写即资损，应改用 etcd/ZK + fencing token，或把操作做成幂等）。见第十一节。

### 6.12 其余常考细节

- **Redis 事务**：`MULTI` / `EXEC` / `WATCH` / `DISCARD`——**支持一次执行多个命令**；其他客户端的请求不会插到事务中间。
- **Redis 跳表**：**有序集合（zset）**底层数据结构；**平均 O(log N)**，**空间复杂度 O(N)**，比红黑树更易实现、范围查询更快。
- **Hash 冲突**：**链地址法**（HashMap 同款），红黑树是对链表过长时的优化。
- **RESP 协议**：Redis 1.2 引入的**序列化通信协议**，Redis 2.0 之后成为主要通信协议。
- **布隆过滤器**：由**长结构的数据结构 + 多个 Hash 函数**组成，用于**判断一个元素是否在一个集合中**；**空间效率和查询效率都很高**，但**有误判**。

### 8.2 分布式演进路线（案例图题常考）⭑

```text
单机（页面+数据库同机）
  → 数据库与 Web 服务器分离（解决数据库竞争）
  → 负载均衡（多台应用服务器 + 共享数据库）
  → 数据库主从（读写分离）+ 缓存（Memcache/Redis）
  → 分布式存储 / 微服务
```

**核心问题与对策**：

| 问题 | 现象 | 对策 |
| ---- | ---- | ---- |
| **Session 不一致** | 应用服务器集群，用户请求落到不同服务器，Session 不共享 | ① **负载均衡做 session 粘滞** ② **Redis 集中管理 Session**（用户每次访问携带 session id / cookie）③ **数据库存储** |
| **数据库读压力大** | 读多写少 | **主从复制 + 读写分离**（读从库） |
| **数据库连接与压力** | 连接数受限、单点故障 | **连接池 + 读写分离** |
| **热点数据** | 大量请求打 DB | **加缓存层**（Memcache / Redis） |

### 8.3 CDN 与 REST

**CDN**（Content Delivery Network，内容分发网络）：

- 原理：**构建在网络之上的内容分发网络**，依靠部署在各地边缘的**缓存服务器**，通过中心平台的**负载均衡**、内容分发、调度等功能模块，使用户就近获取所需内容，**降低网络拥塞、提高响应速度和命中率**。
- 关键技术：**全局负载均衡**、**内容分发**、**调度**、**边缘服务**。

**REST**（Representational State Transfer，表述性状态转移）：**只使用 HTTP 和 XML** 进行基于 Web 的技术，可**降低开发的复杂度**，提高系统的**可伸缩性**。**五个原则**：① 网络上所有的事务都是**资源** ② 每个资源都有一个**唯一的资源标识** ③ 通过**连接接口**对资源进行操作 ④ 对资源的**操作不会改变资源标识** ⑤ 所有的操作都是**无状态的**。

### 8.4 微服务：4 优势 + 4 挑战 ⭑

**优势**：① **解决复杂性问题**（把庞大的单一模块应用分解为一系列服务，功能不变）② 每个服务可**独立开发**，开发者自由选择技术，服务来决定 API 约定 ③ 每个服务都能**独立配置** ④ 每个服务都能**独立调整**（配置容量与可用性限制的实例数）。

**挑战**：① **并非所有系统都能转成微服务**（底层操作不推荐服务化）② 部署**更费资源**（每个服务要独立部署，容器技术可缓解）③ **性能问题**（只能通过标准接口调用，可能产生延迟或调用出错）④ **数据一致性问题**（分布式部署让数据一致性更加困难）。

### 8.5 XML vs JSON

| 维度 | XML | JSON |
| ---- | ---- | ---- |
| 优点 | 格式统一、符合规范、容易与其他系统进行**数据交换**；支持**多种数据编码** | 格式统一、**数据格式比较紧凑**、易于读写；**支持多种语言** |
| 缺点 | 文件庞大、**解析开销大**、客户端编写麻烦、**不同浏览器返回的结果不一致** | 编码冗余、**不能完全使用 eva() 进行 JSON 数据读取**、服务端完全解析成**代码**才能使用 |

> **常见误答**：把 JSON 说成"性能一定高于 XML"。**JSON 格式比较紧凑、占用带宽少**是相对 XML 的优势，但**服务端要完全解析成代码才能使用**，CPU 未必更省。

### 8.6 其他

- **无状态服务**：对单次请求的处理**不依赖其他请求**，处理所需信息要么包含在这个请求里，要么可从外部获得，**服务本身不存储任何信息**。
- **有状态服务**：与无状态相反，会**在自身保存一些数据**。
- **响应式 Web 设计**：一种**网页页面设计布局**，理念是集中创建页面的图片排版大小，**根据用户行为与设备环境进行动态调整**；方法与策略：① **流式布局**和**弹性化设计**（使用相对单位，设置百分比而非具体值）② **响应式图片**（不仅同比缩放图片，在小设备上降低图片分辨率）。

**问题 2（原理题）**：为什么 Ping/Echo 和心跳模式都能保证可靠性？

- **Ping/Echo**：一种**检测网络连通状态**的技术。客户端向服务器发一个 "ping" 请求，服务器收到后立即回复 "echo" 响应，客户端据此确认连接与服务器是否正常。
- **心跳**：一种**维持长连接**的技术，通常客户端定期（心跳消息）向服务器发送心跳包，对方收到后回复确认，若长期没收到则认为连接已断。
- **注意**：心跳**通常每 10 秒一次**（或 5 秒、默认 1 秒），而 ping/echo 策略的**发送请求要更频繁**。
- **原因**：心跳消息通常**非常小，只包含简单的标识信息**，而 ping/echo 请求和响应**可能包含更多数据**。
- **持久性**：心跳主要用于**维持连接的活跃状态**，ping/echo 主要用于**检测连接状态**，后者**可能需要更频繁的交互**。

> **易错点**：**可靠性的设计策略与可用性完全相同**（心跳、Ping/Echo、冗余、选举），但**可用性还要看"故障间隔时间 / 恢复速度"**。

### 10.5 数据库超纲题：互斥锁 / 逻辑过期

**2025 年 11 月 · 试题三**（分布式高并发系统，数据互斥更新）：

- **问题 1（互斥锁流程图填空）**：(1) **获取互斥锁成功** （2) **查询数据库重建缓存数据** （3) **写入缓存** （4) **释放锁** （5) **获取互斥锁失败**。
- **问题 2（逻辑过期流程图填空）**：(1) **创建新线程** （2) **返回过期数据** （3) **写入缓存，重置逻辑过期时间** （4) **返回过期数据** （5) **命中缓存，且未过期**。
- **问题 3（优缺点 + 推荐意见）**：

**王工方案（互斥锁）**：

- **优点**：保证缓存**更新与数据库查询的同步**，数据一致性**好**。
- **缺点**：**性能瓶颈**（锁竞争可能导致请求阻塞，增加响应延迟）；**复杂度高**（需实现分布式锁，增加了系统的复杂性和运维难度）。
- **单点故障风险**：若有锁的进程崩溃，可能**锁超时机制**失效，否则会长时间阻塞。
- **子方案分析**：高并发下，**请求快速返回**（即使旧数据）用户体验好；但**数据存在短暂不一致**。

**李工方案（逻辑过期）**：

- **优点**：**性能高**；**可用性好**；**避免锁竞争导致长时间等待**。
- **缺点**：**数据可能过期**（读取时直接返回旧数据并触发更新）。
- **实现难点**：**需要确保缓存数据在逻辑过期时不会被其他请求覆盖**（加锁保护）。
- **子方案分析**：若有锁的进程崩溃、需要**时间戳**或版本号来避免旧值覆盖新值。

**推荐**：业务对**数据一致性要求极高**（如金融交易、库存扣减）且能接受性能损失时，**用互斥锁**；否则**用逻辑过期**，以保证可用性。

| **数据丢失或同步延迟** | 终端无法及时从**数据库**读取数据 → 缓存与终端数据不一致 | ① **离线优先策略**：终端在**弱网时仍可读写本地**（如 SQLite），待网络恢复后自动同步 |
| **增量同步与冲突解决** | 终端需**按时间戳或版本号**做增量同步 | ② **冲突解决策略**：采用**时间戳、版本号或操作合并**（如 OT 算法）解决冲突 |
| **本地缓存与降级策略** | 关键数据（如菜单、科室）**预加载至本地** | ③ **关键数据**（如菜单、科室）预加载至本地，**网络异常时使用缓存数据提供服务** |
| **异步消息队列** | 终端向服务端**提交预约数据**存在网络延迟 | ④ **异步消息队列**（如 RabbitMQ/Kafka）异步上报，最终保证数据一致 |
| **心跳检测与自动重试** | 网络状态异常导致**数据不一致** | ⑤ **心跳检测与自动重试**，在恢复后自动重试同步，确保数据最终一致 |

> **选择填空技巧**：题目问"realm 是移动端框架""ktor 是服务器端框架"——**这是靠常识题，不靠记忆**。如果题目用移动端框架，一定是**客户端**框架；如果用服务器框架，一定是**服务端**框架。

**2025 年 11 月 · 试题四**（AI 嵌入式操作系统）：

- **问题 1（9 分）智能化操作系统的实质与主要功能**：

> **实质**：智能化操作系统是传统嵌入式操作系统的**增强形态**，其核心在于**将人工智能技术（如机器学习、推理引擎、决策模型）与操作系统底层机制深度融合**，形成具备感知、决策、执行能力的系统化平台。它并非简单叠加 AI 应用，而是**使 AI 成为系统的基础能力，实现从"被动响应"到"主动适应"的转变**。
>
> 主要功能：① **自适应管理**（根据环境、负载变化动态调整资源分配、功耗策略）② **智能推理与决策**（内置推理引擎，对系统状态和外部输入实时分析，自主做出决策）③ **自主学习与优化**（利用在线学习或迁移学习技术，持续改进系统策略）④ **自然交互支持**（集成语音识别、视觉理解等感知模块，提供更人性化的交互接口）⑤ **增强的安全与可靠性**（通过行为分析、异常检测提升系统安全防护能力）。

- **问题 2（9 分）AI for OS 与 OS for AI 的差异**：

| | **AI for OS**（AI 赋能操作系统） | **OS for AI**（操作系统支撑 AI） |
| ---- | ---- | ---- |
| 定义 | **利用 AI 技术来优化、提升操作系统本身的运行效率与运行秩序**，**AI 作为工具服务于 OS 内部机制** | **指操作系统的设计**（改造操作系统内核、资源管理与调度机制、故障检测等**优化方面**）以**支撑 AI 在 OS 内部机制上的运行效率** |
| 目标 | 提升 OS 在资源调度、能耗管理、故障检测等方面的智能水平 | **为 AI 任务提供专门的运行时环境与硬件加速抽象** |
| 实例 | 智能电源管理、**智能调度**、能耗优化 | 容器编排、**统一异构调度**、故障恢复 |
| 共同点 | 两者可融合，共同构成智能化操作系统 | |

- **问题 3（7 分）轻量化内核特点**：

> ① **小型化与低功耗**（内核体积小、内存占用少，适用于资源受限的嵌入式设备）② **强实时性**（提供确定性的任务响应时间，满足工业控制等实时要求）③ **模块化与可裁剪**（功能组件可按需配置，便于针对特定任务定制）④ **安全可靠**（采用嵌入式或混合内核架构，隔离核心功能与驱动，提升安全性）⑤ **高效通信机制**（支持多核间高效数据交换，适合 AI 模型与流式数据处理）⑥ **应用场景举例**：
> - **智能家居中枢**：采用轻量化内核搭载语音识别、环境推理模块，实现低功耗、快速响应的设备控制。
> - **工业边缘网关**：在资源有限的网关设备上，通过轻量内核调度多个 AI 推理任务，实时处理传感器数据并进行预测性维护。
> - **自动驾驶感知单元**：采用轻量化实时内核管理摄像头、雷达等传感器数据流，实时执行目标检测与预测模型。

## 十一、易错点与补充（讲义之外的自查）

> **常见误答 1：Redis 6.0 之后"变成多线程"了。**
> 准确说法：**Redis 6.0 引入的是 I/O 多线程**（网络读写、协议解析交给 IO 线程并行处理），**命令执行仍然是单线程**（这是保证原子性的核心）；**Redis 7.0** 进一步优化（I/O 线程默认启用、部分命令可并行执行）。所以"Redis 是单线程"和"Redis 6+ 有多线程"**都不算错，但必须说清楚是哪部分多线程**——案例里若问"为什么 Redis 快"，答"单线程命令执行 + 多路复用 epoll + 内存操作"才对。

> **常见误答 2：Redlock 是"更安全的分布式锁"所以无脑用。**
> 准确说法：Redlock 是 Redis 作者 antirez 提出的**多节点多数派加锁算法**（5 节点拿 3 个即成功）；但 **Kleppmann（2016）指出其在 GC 长停顿、时钟跳变、网络延迟下无法保证安全，且不提供 fencing token**。工程结论：**效率锁**（防重复计算/任务双跑）用单实例 Redis 锁 + 看门狗即可；**正确性锁**（双写即资损）应改用 etcd/ZK + fencing token，或**把操作做成幂等**。案例若问"对比 Redlock 与单实例锁的优劣"，写清这两层是加分点。

> **常见误答 3：把"批处理"和"管道-过滤器"混用。**
> **批处理 = 以整体为单位**（每个阶段产生一个中间文件，如传统编译器）；**管道-过滤器 = 前一个的输出即后一个的输入**（如编译器各阶段），且**不同过滤器可并行**。

> **常见误答 4：架构风格"客户/服务器"只有两层。**
> 讲义明确给了两层 C/S 和**三层 C/S（表示层、功能层、数据层）**，答题时若题目给的是三层图，空格填"表示层 / 功能层 / 数据层"。

> **常见误答 5：数据流图的平衡原则只说"输入输出数量相等"。**
> 准确说法：**父图某条输入数据流的数目 = 子图输入数据流总数**；**父图某条输出数据流的数目 = 子图输出数据流总数**。另外**"输入数据流全部来自该子图、输出数据流全部输出到该子图"的加工，是整体的一张子图**。

> **常见误答 6：Petri 网的关联矩阵方向搞反。**
> 讲义口径：**行 = 库所 P0～P9，列 = 变迁 T0～T8**；元素 **a(i,j)** 表示**变迁 T_j 对库所 P_i 的影响**：**+1 产生令牌、-1 消耗令牌、0 无关**。若题目问"行代表什么"，答**库所**；问"列代表什么"，答**变迁**。
