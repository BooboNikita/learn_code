## 一、软件过程模型

### 1.1 传统模型

| 模型                  | 特点 / 适用                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------ |
| **瀑布模型**            | 严格串行，**前一阶段的输出是后一阶段的输入**，每阶段伴随里程碑；缺点：需求难以一次确定、**变更代价高**、结果难以预见、**各阶段不能并行**                                   |
| **原型模型**            | 用快速构建的原型捕获确认需求。分**抛弃型**（确认需求后废弃重写）与**演化型**（在此原型上不断补充完善成产品）                                                   |
| **螺旋模型**            | 瀑布 + 原型，**加入风险分析**；每次迭代含 4 项活动：制定计划、**风险分析**、实施工程、客户评估。适用于**大型复杂、高风险**系统                                     |
| **喷泉模型**            | 面向对象的过程模型，特点是**各阶段之间无明显边界（无间隙）、可迭代、可无次序**（分析与设计、编码之间没有明显界限）                                                  |
| **V 模型**            | 测试与开发阶段**一一对应**：单元测试↔详细设计、集成测试↔概要设计、系统测试↔需求分析、验收测试↔需求                                                        |
| **增量模型**            | 先开发**核心模块功能**，与用户确认后再开发次级核心功能，**优先级最高的服务最先交付**                                                               |
| **RAD（快速应用开发）**     | 瀑布的**高速变种 + 构件化开发**；用一系列重点突出的研讨会（项目投资方、用户、系统分析师、设计人员、开发人员一起参与）加速需求分析和设计；局限：并非所有应用都适合、需求分析时间短需各方配合、**不适合新技术** |
| **CBSD（基于构件的开发模型）** | 利用**预先包装好的构件**构造应用系统；特点是**增强复用性**，构建一个构件库供其他系统复用，因此可提高可靠性、节省时间和成本                                            |
| **形式化方法模型**         | 建立在**严格数学基础**上的一种软件开发方法，主要活动是生成计算机软件**形式化的数学规格说明**                                                           |

### 1.2 RUP（统一过程）⭑

- **三大特点**：用例驱动、以**体系结构为中心**、**迭代与增量**。
- **四大阶段** ⭑：

| 阶段       | 任务                                                                                   |
| -------- | ------------------------------------------------------------------------------------ |
| **初始阶段** | 为系统建立**业务模型**并确定项目的**边界**；识别与系统交互的外部实体，定义系统与外部实体交互的特性                                |
| **细化阶段** | **分析问题领域、建立完善的架构**；淘汰项目中最高风险的元素；必须理解整个系统的基础上对**架构**做出决策（范围、主要功能和性能等非功能需求），并为项目建立支持环境 |
| **构建阶段** | 开发所有剩余的构件和应用程序功能，**把构件集成为产品**并详细测试；目标是**通过优化资源和避免不必要的返工，使开发成本降到最低**                  |
| **移交阶段** | 把产品**提交给用户使用**；进行 β 测试、制作产品发布版本、培训用户和维护人员、获得用户对当前版本的反馈                               |

- **核心概念**：角色（Role）、活动（Activity）、制品（Artifact）、工作流（Workflow）。
- **九个核心工作流**：业务建模、需求、分析与设计、实现、测试、部署（**6 个核心过程工作流**）；配置与变更管理、项目管理、环境（**3 个核心支持工作流**）。
- **RUP 的特点（三条）**：
  1. **用例驱动**——需求分析、设计、实现和测试等活动都是用例驱动的。
  2. **以体系结构为中心**——包括系统的总体组织和全局控制、通信协议等，是一个多维的结构，会以多个视图来描述。在典型的 **4＋1 视图模型**中：

| 视图                            | 关心的人      | 关注内容                      |
| ----------------------------- | --------- | ------------------------- |
| **用例视图**（Use Case View）       | 分析人员/测试人员 | 系统行为，是系统的功能               |
| **逻辑视图**（Logical View）        | 最终用户      | 系统的功能，侧重于**逻辑视图**         |
| **进程视图**（Process View）        | 系统集成人员    | 性能、可伸缩性、吞吐率，侧重于**进程视图**   |
| **实现视图**（Implementation View） | 程序员       | 系统的配置、装配等问题，侧重于**实现视图**   |
| **部署视图**（Deployment View）     | 系统工程师     | 软件的发布、安装、拓扑结构，侧重于**部署视图** |

1. **迭代与增量**——把整个项目开发分为多个迭代过程，每次只考虑系统的一部分需求，在已完成部分基础上增加的新的功能实现。

### 1.3 敏捷模型 ⭑

**敏捷宣言（4 条价值观）**：个体和交互 > 过程和工具；可以工作的软件 > 面面俱到的文档；客户合作 > 合同谈判；响应变化 > 遵循计划。

**与其他方法的两个区别** ⭑：① 是"**适应性**"而非"**预设性**"；② 是"**面向人**"而非"面向过程"。

| 敏捷方法            | 要点                                                                              |
| --------------- | ------------------------------------------------------------------------------- |
| **极限编程 XP**     | 基础价值观：**交流、朴素、反馈、勇气**；任何软件项目都可从**4 个方面**改进（加强交流、从简单做起、寻求反馈、勇于实事求是）              |
| **水晶系列方法**      | 与 XP 一样，都**以人为中心**；但在实践上有所不同，目的是发展一种提倡"**机动性**"的方法，包含核心元素，每个都各有特色（过程模式、工作产品、实践） |
| **并列争球法 Scrum** | 迭代增量过程，把每段时间（如 **30 天**）一次的迭代称为一个**冲刺（Sprint）**；多个**自组织、自洽**的小组**并行地递增**实现产品    |
| **特征驱动开发 FDD**  | 要素：**人、过程、技术**；**5 个核心过程**——开发整体对象模型、构造特征列表、计划特征开发、特征设计、特征构建                    |

## 二、逆向工程 ⭑

- **定义**：软件的逆向工程是**分析程序**，力图在**比源代码更高的抽象层次上**建立程序的表示过程；逆向工程是**设计的恢复过程**。
- **四个抽象级别** ⭑：

| 级别      | 内容                                          |
| ------- | ------------------------------------------- |
| **实现级** | 程序的抽象语法树、符号表、过程的设计表示                        |
| **结构级** | 反映程序分量之间相互依赖关系的信息（调用图、结构图、程序和数据结构）          |
| **功能级** | 反映程序段功能及程序段之间关系的信息（数据和控制流模型）                |
| **领域级** | 反映程序分量或程序诸实体与**应用领域概念**之间的对应关系的信息（如 E-R 模型） |

> **易错点**：抽象级别由高到低为 **领域级 > 功能级 > 结构级 > 实现级**；其中**领域级抽象级别最高，但完备性最低**；**实现级完备性最高**。

- **四个相关概念** ⭑：

| 概念       | 含义                                                               |
| -------- | ---------------------------------------------------------------- |
| **重构**   | 指**在同一抽象级别上**转换系统描述形式                                            |
| **设计恢复** | 指借助工具从已有程序中**抽象出**有关数据设计、总体结构设计和过程设计等方面的信息                       |
| **再工程**  | 在逆向工程所获得信息的基础上，**修改或重构**已有系统，产生系统的一个新版本；包括**逆向工程、新需求的考虑、正向工程**三步 |
| **正向工程** | 不仅从现有系统中恢复设计信息，而且**使用该信息去改变或重构**现有系统，以改善其整体质量                    |

## 三、需求工程

### 3.1 需求获取六法 ⭑

| 方法          | 适用                                            |
| ----------- | --------------------------------------------- |
| **用户面谈**    | 1 对 1～3 人、有代表性的用户；面谈后需**复查记录**，确保准确性、完整性、可理解性 |
| **需求专题讨论会** | 集中各相关方讨论，与会者可在应用需求上达成共识，**对操作步骤达成统一**         |
| **问卷调查**    | 用户多、无法一一访谈时，可用于确认假设和收集统计数值                    |
| **现场观察**    | 通过在现场观察用户的**实际业务执行过程**来全面了解业务                 |
| **原型化方法**   | 需求早期、具体需求存在很多不确定性时，通过开发系统原型与用户多次迭代确定需求        |
| **头脑风暴法**   | 面向**全新业务领域**、业务流程存在高度不确定性时，激发新观点，从而确定具体需求     |

### 3.2 结构化需求分析 ⭑

- 特点：**自顶向下、逐步分解、面向数据**。
- **三大模型 + 数据字典**：

| 模型   | 表达工具          |
| ---- | ------------- |
| 功能模型 | **数据流图 DFD**  |
| 行为模型 | **状态转换图 STD** |
| 数据模型 | **E-R 图**     |
| （补充） | **数据字典 DD**   |

- **数据流图四种元素** ⭑：**外部实体、加工（数据变换）、数据存储、数据流**（判定树/判定表用于分析数据流图中的**加工**）。
- **数据字典 DD 的 5 项** ⭑：**数据项、数据结构、数据流、数据存储、处理过程**。
  - 数据流图描述了系统的分解，但**没有对图中各成分进行说明**，数据字典就是为数据流图中的每个数据流、文件、加工（以及组成数据流或文件的数据项）做出说明。
  - **数据项是不可再分**的数据单位；**数据结构**反映数据之间的**组合关系**。

### 3.3 需求变更控制 ⭑

- **流程**：**问题分析和变更描述 → 变更分析和成本计算 → 变更实现**。
  - 一旦确定了**需求基线**，所有已建议的变更都要遵循变更控制过程。
  - 变更分析：对变更提议进行**影响分析和评估**；变更实现：根据变更的影响范围，按**开发的过程模型**执行相应的变更。
- **CCB（变更控制委员会）** ⭑：是**项目所有者权益代表**，负责**裁定接受哪些变更**；成员由项目所涉及的多方成员共同组成，通常包括用户和实施方的**决策人员**。**CCB 是决策机构，不是作业机构**——通过评审手段决定项目是否能变更，**但不提出变更方案**。
- **CCB 决策过程**：制定决策 → 交流情况 → 重新协商约定。

### 3.4 需求跟踪

- 用途：编制每个需求同系统元素之间的联系文档，这些元素包括其他需求、体系结构、其他设计部件、源代码模块、测试、帮助文件和文档等。
- **两种方式** ⭑：
  - **正向跟踪**：检查产品需求规格说明书中的每个需求是否都能在后续工作成果中找到对应点。
  - **逆向跟踪**：检查设计文档、代码、测试用例等工作成果是否都能在产品需求规格说明书中找到出处。

## 四、面向对象与 UML

### 4.1 基本概念

- **对象**：由数据及其操作所构成的**封装体**，是系统中用来描述客观事务的一个实体；通常由**对象名、属性和方法** 3 个部分组成。
- **类**：现实世界中实体的**形式化描述**，将该实体的属性（数据）和操作（函数）封装在一起。**对象是类的实例，类是对象的模板**。
- **类的三种分类** ⭑：

| 类型            | 职责                                                                    |
| ------------- | --------------------------------------------------------------------- |
| **实体类**       | 表示现实世界中真实的实体，如人、物等                                                    |
| **接口类 / 边界类** | 为用户提供一种与系统合作交互的方式，分**人**和**系统**两大类（展示屏、窗口、Web 窗体、对话框、菜单、列表框、条形码、二维码等） |
| **控制类**       | 用来控制活动流，**充当协调者**                                                     |

- **抽象**：通过特定的实例抽取**共同特征**以后形成概念的过程；强调主要特征、忽略次要特征。一个对象是现实世界中的一个实体的抽象，一个类是**一组对象的抽象**。

### 4.2 UML 关系 ⭑

| 关系     | 说明                                                                               |
| ------ | -------------------------------------------------------------------------------- |
| **依赖** | 一个事物的语义**依赖于**另一个事物的语义的变化而变化                                                     |
| **关联** | 一种结构关系，描述了一组链，链是对象之间的连接。**分为组合和聚合，都是部分和整体的关系，其中组合事物之间关系更强**。两个类之间可以有多个由不同角色标识的关联 |
| **泛化** | **一般 / 特殊**的关系，子类和父类之间的关系                                                        |
| **实现** | 一个类元指定了另一个类元保证执行的**契约**                                                          |

### 4.3 UML 图（14 种）⭑

| 图            | 说明                                                     |
| ------------ | ------------------------------------------------------ |
| **用例图**      | 由参与者（Actor）、用例（Use Case）、边界以及它们之间的关系构成，用于描述**系统功能**的视图 |
| **类图**       | 展现一组对象、接口、协作和它们之间的关系（关联、依赖、实现、泛化）                      |
| **对象图**      | 描述一组对象及它们之间的关系，描述了在类图中所建立的事物实例的**静态快照**                |
| **构件图**      | 描述一个封装的类和它的接口、端口，以及由内嵌的构件和连接件构成的内部结构                   |
| **组合结构图**    | 用于画出结构化类的内部内容                                          |
| **顺序图**（序列图） | 由一组对象或参与者以及它们之间可能发送的消息构成，**强调消息的时间次序**                 |
| **通信图**      | 强调收发消息的对象或参与者的**结构组织**，强调对象之间的**组织结构（关系）**             |
| **定时图**      | 强调消息跨越不同对象或参与者的**实际时间**，不仅仅只是关心消息的相对顺序                 |
| **状态图**      | 用来描述一个特定对象的所有可能的状态，以及由于各种事件的发生而引起的**状态之间的转移和变化**       |
| **活动图**      | 将进程或其他计算的结构展示为计算内部一步步的控制流和数据流，**可并行**                  |
| **部署图**      | 描述软件和硬件组件的**物理结构**以及处理节点的组件分布情况，**描述系统的物理结构**          |
| **制品图**      | 描述计算机中一个系统的物理结构，通常与部署图一起使用                             |
| **包图**       | 描述由模型本身分解而成的组织单元，以及它们之间的依赖关系                           |
| **交互概览图**    | 是**活动图和顺序图的混合物**                                       |

> **易错点**：**活动图**能描述系统的物理结构？不对——**部署图**描述系统的物理结构（真题 2025-11 第 18 题）。另外**分支（decision）**&#x7528;菱形、只有一个入流、输出流带**监护条件**且只有一条被执行；**分叉（fork）**&#x8868;示并发开始，有一个入流、多个输出流**同时执行**，**不需要监护条件**。

## 五、结构化设计

### 5.1 设计总览

- **系统设计主要目的**：为系统制定**蓝图**，在各种技术和实施方法中**权衡利弊**，精心设计，合理地使用各种资源，最终描绘出新系统的详细设计方案。
- **系统设计方法**：结构化设计方法、面向对象设计方法。
- **两类设计** ⭑：

| 设计       | 任务                                                                    |
| -------- | --------------------------------------------------------------------- |
| **概要设计** | 又称**系统总体结构设计**，是将系统的功能需求分配给软件模块，确定每个模块的功能和调用关系，形成软件的**模块结构图**（即系统结构图） |
| **详细设计** | 模块内部详细设计、模块内数据结构设计、数据库的物理设计、其他设计（代码、输入/输出格式、用户界面）、编写详细设计说明书、评审        |

- **系统设计基本原理**：**抽象化**；**自顶向下，逐步求精**；**信息隐藏**；**模块独立（高内聚，低耦合）**。
- **系统设计原则** ⭑：保持模块的大小适中；尽可能减少调用的深度；**多扇入，少扇出**；**单入口，单出口**；模块的作用域应该在模块之内；功能应该是可预测的。

> **扇入/扇出**：**扇出**是一个模块**直接调用的下层模块的数量**；**扇入**是直接调用该模块的上级模块数量。设计时追求"**多扇入、少扇出**"。

### 5.2 耦合（7 级，越低越好）⭑

| 耦合        | 定义                                                    | 记忆关键字         |
| --------- | ----------------------------------------------------- | ------------- |
| **无直接耦合** | 两个模块之间没有直接的关系，分别从属于不同模块的调用和控制，不传递任何信息                 | 无直接关系         |
| **数据耦合**  | 两个模块之间有调用关系，传递的是**简单的数据值**，相当于高级语言中的值传递               | 传递数据值调用       |
| **标记耦合**  | 两个模块之间传递的是**数据结构**                                    | 传递数据结构        |
| **控制耦合**  | 一个模块调用另一个模块时，传递的是**控制变量**，被调用模块通过该控制变量的值有选择地执行块内的某一功能 | 控制变量、选择执行某一功能 |
| **外部耦合**  | 模块间通过**软件之外的环境**联结（如 I/O 将模块耦合到特定的设备、格式、通信协议）         | 软件外部环境        |
| **公共耦合**  | 通过一个**公共数据环境**相互作用的那些模块间的耦合                           | 公共数据结构        |
| **内容耦合**  | 当一个模块直接使用另一个模块的**内部数据**，或通过**非正常入口**转入另一个模块内部时        | 模块内部关联        |

### 5.3 内聚（7 级，越高越好）⭑

| 内聚       | 定义                                                            | 记忆关键字         |
| -------- | ------------------------------------------------------------- | ------------- |
| **偶然内聚** | 一个模块内的各处理元素之间**没有任何联系**                                       | 无直接关系         |
| **逻辑内聚** | 模块内执行若干个**逻辑上相似**的功能，通过参数确定该模块完成哪一个功能                         | 逻辑相似、参数决定     |
| **时间内聚** | 把需要**同时执行**的动作组合在一起形成的模块                                      | 同时执行          |
| **过程内聚** | 一个模块完成多个任务，这些任务**必须按指定的过程执行**                                 | 指定的过程顺序       |
| **通信内聚** | 模块内的所有处理元素都在**同一个数据结构**上操作，或者各处理使用**相同的输入数据**或者产生**相同的输出数据**  | 相同数据结构、相同输入输出 |
| **顺序内聚** | 一个模块中的各个处理元素都密切相关于同一功能，且必须**顺序执行**，**前一个功能元素的输出就是下一个功能元素的输入** | 顺序执行、输入为输出    |
| **功能内聚** | **最强的内聚**，模块内的所有元素**共同作用完成一个功能，缺一不可**                         | 共同作用、缺一不可     |

> **背两个口诀**：耦合由低到高——"**无数标控外公内**"（无直接、数据、标记、控制、外部、公共、内容）；内聚由低到高——"**偶逻时过通顺功**"（偶然、逻辑、时间、过程、通信、顺序、功能）。
>
> **两个高频坑**：① 传**标志位/开关**去控制对方内部逻辑，看着像"传数据"，其实是**控制耦合**；② "共享同一数据"是**通信内聚**，"前一个的输出是后一个的输入"才是**顺序内聚**，分界线在**数据流向**。

## 六、面向对象设计

### 6.1 设计原则（6 条）⭑

| 原则            | 含义                                                                                                    |
| ------------- | ----------------------------------------------------------------------------------------------------- |
| **开闭原则**      | 软件实体（类、模块、函数等）应该是**可以扩展的，即开放的；但是不可修改的，即封闭的**                                                          |
| **里氏替换原则**    | 子类型必须能够替换它们的**基类型**，即任何父类可以出现的地方，子类都可以出现                                                              |
| **依赖倒置原则**    | **抽象不应该依赖于细节，细节应该依赖于抽象**——要针对接口编程，而不是针对实现编程                                                           |
| **组合/聚合复用原则** | 又称**合成复用原则**，在新的对象中**通过组合关系或聚合关系**来使用一些已有的对象；一般如果两个类之间是 "**has-a**" 关系则使用组合或聚合，如果是 "**is-a**" 关系则使用继承 |
| **接口隔离原则**    | 使用**多个专门的接口**比使用单一的总接口要好；每个接口应该承担一种相对独立的角色，不多不少                                                       |
| **最少知识原则**    | 又称**迪米特法则（Law of Demeter）**，指一个软件实体应当尽可能地**少与其他实体发生相互作用**（其中一个类如果需要调用另一个类的某个方法，可以通过第三者转发这个调用）         |

> 这六条是讲义明确讲的；另有**单一职责原则**（一个类只应有一个引起它变化的原因），常与前六条并称"面向对象设计七大原则"。

### 6.2 设计模式

- **四个基本要素** ⭑：**模式名称**、**问题**（应该在何时使用模式）、**解决方案**（设计的内容）、**效果**（模式应用的效果）。
- **三大分类** ⭑：

| 分类          | 模式（共 23 个）                                                                                                                                                      |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **创建型（5）**  | 工厂方法 factory method、抽象工厂 abstract factory、建造者 builder、原型 prototype、**单例 singleton**                                                                             |
| **结构型（7）**  | 外观 facade、适配器 adapter、桥接 bridge、组合 composite、**装饰 decorator**、享元 flyweight、代理 proxy                                                                             |
| **行为型（11）** | 职责链 chain of responsibility、命令 command、解释器 interpreter、迭代器 iterator、中介者 mediator、备忘录 memento、观察者 observer、状态 state、策略 strategy、模板方法 template method、访问者 visitor |

## 七、软件测试

### 7.1 测试方法

- **静态测试**：被测试程序**不运行**，只依靠**分析或检查源程序的语句、结构、过程**等来检查程序是否有错。包括**代码检查**（代码审查、代码走查）、静态结构分析、代码质量度量等；静态分析可分析数据类型、控制流、路径、程序变异、接口等。
- **动态测试**：通过**运行**被测程序，对得到的运行结果与预期的结果进行比较分析，同时分析运行效率和健壮性能等。**3 个步骤：构造测试实例 → 执行程序 → 分析结果**。

| 方法             | 关注点                                         | 常用技术                                              |
| -------------- | ------------------------------------------- | ------------------------------------------------- |
| **黑盒测试**（功能测试） | 把程序看成一个**黑盒**，不管内部结构和特性，只按**需求规格说明书**设计测试用例 | **等价类划分、边界值分析、错误推测法、因果图法**（主要考虑输入条件的**组合情况**）     |
| **白盒测试**（结构测试） | 主要借助程序的**内部逻辑**和相关信息                        | **逻辑覆盖**（语句覆盖、判定覆盖、条件覆盖、判定/条件覆盖、条件组合覆盖）、路径覆盖、循环覆盖 |
| **灰盒测试**       | 介于黑盒与白盒之间                                   | 像黑盒测试那样看输入输出的正确性，也像白盒测试那样关注内部逻辑                   |
| **自动化测试**      | 在预先设定的条件下自动运行被测程序，并分析运行结果                   | 把人驱动的测试行为转化为机器执行                                  |


> **静态测试 vs 动态测试**：分界就是"**程序有没有真正跑起来**"。**测试 vs 调试**：测试是**发现错误**，由测试人员执行、有已知的标准答案；调试是**定位并改正错误**，由开发人员执行。

### 7.2 测试阶段（6 个）⭑

| 阶段         | 依据 / 要点                                                                                                                                              |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **① 单元测试** | 又称**模块测试**，对象是可独立编译/汇编的程序模块、软件构件或 OO 中的类（统称模块）；依据**软件详细设计说明书**；模块规模小、功能单一，**首先用静态测试方法**，再以**基本路径测试**为主（白盒），采用黑盒测试补充。可靠性要求高时以**白盒测试**为主（满足覆盖率/路径覆盖准则） |
| **② 集成测试** | 检查**模块之间以及模块和已集成的软件之间的接口关系**，验证已集成的软件是否符合设计要求；依据**软件概要设计文档**；一般采用**白盒测试和黑盒测试结合**的方法                                                                  |
| **③ 系统测试** | 采用**黑盒测试**，检查系统是否符合软件需求；内容包括功能、性能、健壮性、安装/反安装、用户界面、压力、可靠性、安全性测试等；结束标志是**已达到测试目标规定的需求覆盖率，且所有发现的缺陷都已回归封闭**                                              |
| **④ 性能测试** | 通过自动化测试工具模拟多种**正常、峰值以及异常负载**条件，对系统的各项性能指标进行测试                                                                                                        |
| **⑤ 验收测试** | 验证软件的功能、性能和其他特性**是否与用户需求一致**；包括**α 测试**（开发方在开发环境进行，用户参与）、**β 测试**（用户在实际使用环境下进行，通过后才能交付）、**验收测试**（真实用户工作环境下，检验是否满足开发技术合同或 SRS）                        |
| **⑥ 回归测试** | 测试目的是**软件变更之后，变更部分的正确性和对需求变更的符合性**，以及软件原有的、正确的功能、性能和其他规定的要求的**不损坏**                                                                                  |

**④ 性能测试里的两个易混点** ⭑：

| 术语       | 定义                                                  |
| -------- | --------------------------------------------------- |
| **负载测试** | 确定在各种工作负载下系统的性能，目标是测试当**负载逐渐增加时**，系统各项性能指标的**变化情况** |
| **压力测试** | 通过确定一个系统的**瓶颈或者不能接受的性能点**，来获得系统能提供的**最大服务级别的测试**    |

### 7.3 其他测试

- **AB 测试**：为 Web 或 App 界面或流程**制作两个或多个版本**，在同一时间维度，分别让组成成分相同（相似）的访客群组**随机**访问这些版本，收集各群组的用户体验数据和业务数据，最后分析、评估出最好版本正式采用。
- **Web 测试**：是**针对 Web 应用**的一类测试。由于 Web 应用与用户直接相关且通常需要承受长时间的大量操作，其功能和性能都必须经过可靠的验证。
- **链接测试**：链接是 Web 应用系统的一个主要特征，是页面之间切换和指导用户去未知地址页面的手段。链接测试分 3 个方面：**所有链接是否按指示确实链接到了该页面**、**所链接的页面是否存在**、**保证 Web 应用系统上没有孤立的页面**。
- **表单测试**：用户通过表单提交信息时希望表单能正常工作。若使用表单在线注册，要确保提交按钮能正常工作，注册完成后应返回注册成功的信息。
