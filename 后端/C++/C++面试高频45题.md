## 一、指针·引用·内存管理（1–10）

> 本节为**速答要点**，完整版（含更多代码、追问、陷阱）见 [C++ 指针引用与内存管理面试题](C++指针引用与内存管理面试题.md)。

### 1. 常量指针和指针常量有何区别？

**考察点**：`const` 与 `*` 的相对位置，即顶层 / 底层 const。

- **指针常量** `int* const p`：指针**本身**是常量（`const` 在 `*` **右边**），不能改绑，但 `*p` 可改。
- **常量指针**（指向常量的指针）`const int* p`：指向的**内容**是常量（`const` 在 `*` **左边**），可以改绑，但 `*p` 不能改。
- 记忆法：**从右往左读** —— `int* const p` → "p is a const pointer to int"。
- 归类：`int* const` 是**顶层 const**；`const int*` 是**底层 const**。顶层 const 在拷贝/赋值时**被忽略**，底层 const **不能丢弃**。

```cpp
int a = 1, b = 2;
int* const p1 = &a;       // p1 不可改绑；*p1 可改
const int* p2 = &a;       // p2 可改绑；*p2 不可改
const int* const p3 = &a; // 两者皆不可改
// p1 = &b;  // ❌ 顶层 const
// *p2 = 3;  // ❌ 底层 const
```

### 2. 引用和指针如何选择？

**考察点**：语义表达能力（可空、可改绑、所有权）与性能。

- **引用不能为空、不能改绑**；**指针可空、可改指、可做算术**。
- 选择规则按**语义**判断：

| 场景 | 选择 | 原因 |
| ---- | ---- | ---- |
| 参数一定存在且不想拷贝 | `const T&` | 语义清晰、无拷贝 |
| 需要修改调用方对象 | `T&` | 无需判空 |
| 参数可能"不存在" | `T*` / `std::optional` | 引用无法表达空 |
| 需要改绑 / 遍历数组 | 指针 | 引用不可改绑 |
| 表达"拥有资源" | 智能指针 | 明确所有权 |
| 表达"借用、不拥有" | 引用 或 `T*` | Core Guidelines |
| 拷贝构造、`operator<<` | **必须引用** | 值传递会无限递归 |

- **性能**：引用通常按指针实现但无额外语义开销，`sizeof(T&) == sizeof(T)`；且编译期易优化。
- **安全**：引用无"空引用"风险，但**不能防悬垂**（返回局部变量的引用同样致命）。
- 工程约定：**裸指针 = 非拥有且可空，引用 = 非拥有且非空，智能指针 = 拥有。**

### 3. `nullptr` 和 `NULL` 有何区别？

**考察点**：C++11 引入 `nullptr` 的动机 —— 类型安全与重载决议。

| 维度 | `NULL` | `nullptr` |
| ---- | ------ | --------- |
| 本质 | 宏，整型常量 `0` | 关键字，`std::nullptr_t` |
| 能否隐式转指针 | 能（经由字面量 0） | 能 |
| 能否隐式转整数 | **能** | **不能**（除 `bool`） |
| 重载/模板行为 | 走整型版本，易错 | 走指针版本，符合直觉 |

```cpp
void f(int);
void f(char*);
f(NULL);      // 调用 f(int) —— 语义错误！
f(nullptr);   // 调用 f(char*) ，明确

template <typename T> void g(T);
g(NULL);      // T 推导为 int，不是指针
g(nullptr);   // T 推导为 std::nullptr_t
```

> 结论：C++11 起**一律用 `nullptr`**。

### 4. RAII 的核心机制是什么？

**考察点**：C++ 资源管理的基石。

- **RAII = 资源获取即初始化**：把资源的生命周期**绑定到栈对象的生命周期** —— 构造函数获取资源，析构函数释放资源。
- 依赖 **C++ 的确定性析构**：作用域正常结束、`return`、`break`/`continue`/`goto` 跳出、**异常栈展开**，都会自动析构。
- 因此 RAII **天然异常安全**，不需要 `finally`（C++ 也没有）。
- 标准库范例：`unique_ptr`/`shared_ptr`、`lock_guard`/`unique_lock`、`fstream`、`vector`/`string`。
- 设计要点：构造中获取（失败就抛异常）；析构函数应 **`noexcept`**（栈展开期间抛异常 → `std::terminate`）。
- **失效边界**：`longjmp`、`std::exit`/`abort`、未捕获异常触发 `terminate`、信号处理函数跳出。

```cpp
class FileGuard {
    std::FILE* fp_;
public:
    explicit FileGuard(const char* p) : fp_(std::fopen(p, "r")) {
        if (!fp_) throw std::runtime_error("open failed");
    }
    ~FileGuard() { if (fp_) std::fclose(fp_); }   // 无论如何都执行
    FileGuard(const FileGuard&) = delete;
    FileGuard& operator=(const FileGuard&) = delete;
};
```

### 5. `new`/`delete` 与 `malloc`/`free` 有何区别？

**考察点**：运算符 vs 库函数、构造/析构的介入。

| 维度 | `new` / `delete` | `malloc` / `free` |
| ---- | ---------------- | ----------------- |
| 本质 | **运算符**（`operator new` 可重载） | **标准库函数**（`<cstdlib>`） |
| 调用构造/析构 | **是**（new 先分配再构造，delete 先析构再释放） | 否，只操作裸内存 |
| 返回类型 | 具体类型指针，无需强转 | `void*`，**须强转** |
| 大小 | 编译器推导 `sizeof(T)` | 手工计算字节数 |
| 失败行为 | 抛 `std::bad_alloc`（`nothrow` 返回 `nullptr`） | 返回 `NULL` |
| 数组 | `new[]`/`delete[]` 配套（记录元素个数） | 只按字节数分配 |
| 定制 | 可在类内重载（对象池/内存追踪） | 只能全局替换 |

- **绝不能混用**：`new` 配 `free`、`malloc` 配 `delete` 都是 UB。
- `new[]` 必须配 `delete[]`：对有非平凡析构的类型，分配器会额外记录元素个数（cookie）。
- `new` 表达式 = `operator new` 分配 + 构造函数；异常时编译器自动回滚 `operator delete`。
- **placement new** 只构造不分配：`new (buf) T(...)`，需手动 `p->~T()`。

```cpp
A* a = new A(1);            // 分配 + 构造
delete a;                   // 析构 + 释放
int* p = new (std::nothrow) int[100];
if (!p) { /* 处理 */ }
delete[] p;

void* raw = ::operator new(sizeof(A));
A* b = new (raw) A(2);      // placement new
b->~A();
::operator delete(raw);
```

### 6. 栈和堆有何区别？

**考察点**：两种存储区的管理与使用差异。

| 维度 | 栈（Stack） | 堆（Heap） |
| ---- | ----------- | ---------- |
| 管理者 | **编译器**自动 | **程序员**（或 RAII） |
| 分配时机 | 编译期确定大小与偏移 | 运行期动态 |
| 速度 | 极快（移动栈指针，O(1)） | 较慢（分配器查找 + 可能系统调用） |
| 大小 | 小且固定（Linux 默认 8MB/线程） | 大（受虚拟地址空间与物理内存限制） |
| 增长方向 | 高地址 → 低地址 | 低地址 → 高地址 |
| 碎片 | 无 | 有（内部/外部碎片） |
| 生命周期 | 作用域结束自动回收 | 显式释放（或进程退出） |
| 线程关系 | **每线程私有** | **进程内共享** |
| 典型故障 | 栈溢出（递归过深、超大局部数组） | 内存泄漏、碎片、OOM |

- 栈的"分配"本质是**函数序言里的一条指令**（如 `sub rsp, 0x20`），不走任何数据结构查找。
- "栈快"不只因指针加减，还因**局部性好**（热缓存），堆对象分散易 cache miss。
- 现代实践：优先用**栈对象 + RAII**，把堆分配限定在真正需要动态生命周期的场合。

### 7. 栈和堆的内存分配方式有何不同？

**考察点**：从"编译器生成的指令"到"分配器实现"的层次差异。

**一、栈**：由编译器在函数序言/尾声生成 `sub rsp, N` / `add rsp, N`，用 rbp/rsp 相对寻址；部分变量直接放寄存器。特点是 **O(1)、无碎片、无锁、无系统调用**（除非触发缺页补页）。每次调用建立**栈帧**（返回地址、保存寄存器、参数、局部变量）。

**二、堆**：

1. **算法层**（glibc malloc）：维护 **chunk 链表**（fastbins/smallbins/largebins/unsorted bin），采用**首次适应 + 分割 + 合并**。
2. **系统调用层**：`brk`/`sbrk` 抬高 program break 扩展堆（适合小分配，释放后不归还内核）；大分配走 `mmap`（默认阈值约 128KB），`free` 时 `munmap` 归还内核。
3. **工程级分配器**（tcmalloc/jemalloc/mimalloc）：thread cache（无锁）→ central cache → page heap，按 size class 分级，降低锁竞争与碎片。
4. 每块前有**元数据头**（size / in-use / prev_size）→ 实际占用 > 请求字节数（内部碎片来源）。

| 维度 | 栈 | 堆 |
| ---- | -- | -- |
| 分配动作 | 修改栈指针寄存器 | 查空闲链表/分级缓存 + 可能 `brk`/`mmap` |
| 释放动作 | 恢复栈指针 | 归还 bins / 延迟合并 / `munmap` |
| 元数据 | 无（编译期确定偏移） | 每块有头部 + 分配器全局结构 |
| 并发 | 线程私有，无竞争 | 共享，需锁/线程缓存 |
| 碎片 | 无 | 内部 + 外部碎片 |

> 一句话：**栈分配是"移动指针"，堆分配是"分配器管理 + 可能系统调用"。**

### 8. 全局、局部、静态局部对象何时初始化和销毁？

**考察点**：三种存储期的初始化与销毁时机。

| 对象 | 存储期 | 初始化时机 | 销毁时机 |
| ---- | ------ | ---------- | -------- |
| 全局 / 命名空间作用域 | 静态存储期 | 静态初始化在**编译期或加载时**；动态初始化在 **`main` 之前** | **`main` 返回后**，按初始化**逆序** |
| 局部（自动）对象 | 自动存储期 | **执行到定义语句时** | **离开作用域时**（含异常栈展开） |
| 静态局部对象 | 静态存储期 | **首次执行到该定义**时（只一次） | `main` 返回后，与全局对象一起逆序销毁 |

- **静态初始化顺序问题（SIOF）**：不同编译单元中全局对象的动态初始化顺序**未定义**，A 的构造若使用 B 的全局对象可能拿到未初始化对象（UB）。
- **根治办法**：改用函数内静态局部变量（Meyers Singleton）；**C++11 起保证其初始化线程安全**（编译器生成守卫变量 `__cxa_guard_acquire/release`）。

```cpp
std::vector<int>& data() {
    static std::vector<int> d{1, 2, 3};   // 首次调用时构造，线程安全
    return d;
}
```

- 局部对象的初始化点是**定义语句执行时**（不是函数入口），`goto`/`switch` 跳过定义则不构造。
- 析构顺序：**先构造的后析构**；`main` 返回后应确保线程已 join，避免"静态对象析构后仍被访问"。

### 9. 类成员初始化顺序由什么决定？

**考察点**：初始化列表顺序 ≠ 实际初始化顺序。

- 成员的实际初始化顺序**由成员在类中的声明顺序决定**，**与初始化列表书写顺序无关**。
- 完整顺序：① **虚基类** → ② **基类**（按继承列表声明顺序）→ ③ **成员变量**（按声明顺序）→ ④ 构造函数体。
- 写反会导致"用未初始化的成员去初始化另一个成员"（值不确定），`-Wreorder` 会警告。

```cpp
class Bad {
    int b_;   // 声明在前 → 实际先构造 b_
    int a_;
public:
    Bad(int v) : a_(v), b_(a_ + 1) {}   // ⚠️ b_ 用的是未初始化的 a_
};
```

- **必须在初始化列表中初始化**的成员：`const` 成员、**引用成员**、**无默认构造函数的类类型成员**、基类子对象。
- 析构顺序恰好相反：成员逆序 → 基类 → 虚基类。
- 连锁结论：**基类先于派生类构造** → "在基类构造中调用虚函数不会多态"。

### 10. 构造中途抛异常，已构造成员如何释放？

**考察点**：部分构造对象的析构规则 + 栈展开。

- 规则：构造函数抛异常时，**该对象的析构函数不会被调用**（对象从未完整构造），但**已构造完成的基类子对象与成员子对象会按逆序自动析构**。
- 机制是**栈展开**：编译器为构造函数生成异常表（`.eh_frame`），异常抛出时逐个回滚已完成的构造步骤。

```cpp
struct Member {
    Member(const char* n) : name(n) { std::cout << "ctor " << name << "\n"; }
    ~Member()                        { std::cout << "dtor " << name << "\n"; }
    const char* name;
};
struct Foo {
    Member m1{"m1"}; Member m2{"m2"};
    Foo() { throw std::runtime_error("boom"); }
    ~Foo() { std::cout << "~Foo\n"; }   // 不会执行
};
// 输出：ctor m1 / ctor m2 / dtor m2 / dtor m1  —— 没有 ~Foo
```

**工程含义**：

1. **裸资源会泄漏**：构造函数里 `p_ = new int[100];` 后再抛异常 → 泄漏。**解决：成员一律用 RAII 类型。**
2. **这块内存本身会被释放**（`operator delete` 由 `new` 表达式在异常时调用），泄漏的只是没交给 RAII 的裸资源。
3. 可用**函数 try-block** 捕获初始化列表的异常（catch 里成员已被析构，不能再访问成员或 `this`）。
4. **两条铁律**：成员用 RAII 类型；析构函数保持 `noexcept`。

## 二、移动语义与拷贝控制（11–14）

### 11. 什么是移动语义？

**考察点**：右值引用 + 资源转移，避免深拷贝。

**要点**：

- 移动语义把源对象的**资源所有权"转移"**给目标对象，而不是复制一份。典型：`std::vector<int> b = std::move(a);` 时 b 直接接管 a 的堆缓冲区，a 被置空。
- 依赖 C++11 的两个基石：**右值引用 `T&&`** 与**值类别（value category）** —— 左值 `lvalue`（有名字、可取地址）、纯右值 `prvalue`（临时量）、将亡值 `xvalue`（被 `std::move` 转换后的对象）。
- 编译器为可移动类型生成（或手写）**移动构造 `T(T&&)`** 与**移动赋值 `T& operator=(T&&)`**。
- 移动后的源对象处于 **"有效但未指定"（valid but unspecified）** 状态：可以析构、可以重新赋值，但**不要读它的值**。
- **生效条件（易错）**：移动的本质是"窃取指针"。对**只有内置成员**的类型（`int`、`struct{int a;}`）移动与拷贝没有区别；`std::array<T,N>` 也是逐元素移动。
- 三大用途：**容器扩容**（把旧元素移到新内存）、`std::unique_ptr` 所有权转移、按值返回大对象。

```cpp
class Buffer {
    char* data_; size_t n_;
public:
    explicit Buffer(size_t n) : data_(new char[n]), n_(n) {}
    ~Buffer() { delete[] data_; }

    // 移动构造：窃取资源，源置空
    Buffer(Buffer&& o) noexcept : data_(o.data_), n_(o.n_) { o.data_ = nullptr; o.n_ = 0; }
    // 移动赋值：先释放自身，再窃取
    Buffer& operator=(Buffer&& o) noexcept {
        if (this != &o) { delete[] data_; data_ = o.data_; n_ = o.n_; o.data_ = nullptr; o.n_ = 0; }
        return *this;
    }
    Buffer(const Buffer&) = delete;
    Buffer& operator=(const Buffer&) = delete;
};

Buffer a(1024);
Buffer b = std::move(a);   // 移动构造：b 接管 a 的缓冲区，a 变成空壳
```

> **追问：移动一定更快吗？** 只有持有堆资源/句柄的类型才有收益；trivially copyable 类型移动 = 拷贝。

### 12. `std::move` 做了什么转换，是否真的移动数据？

**考察点**：`std::move` 只是类型转换，不搬数据。

**要点**：

- `std::move(x)` 的实现约等于 `static_cast<std::remove_reference_t<T>&&>(x)`：把表达式**无条件转换成一个右值引用（xvalue）**。
- 它**本身不移动、不拷贝、不释放任何数据**，只在类型层面工作，编译后**零开销**。
- 真正"搬数据"的是目标类型的**移动构造 / 移动赋值**。所以 `std::move(a);`（没有接收对象）什么都不会发生。
- **对 `const T` 使用 `std::move` 会得到 `const T&&`**，只能匹配拷贝构造（移动构造通常不接受 const 右值引用）—— 这是"用了 std::move 却还在拷贝"的常见原因。
- `std::move` 是一种**语义契约**："我不再需要这个对象了"，告诉编译器/调用者可以掏空它。

```cpp
std::string a = "hello";
std::string b = std::move(a);   // 触发移动构造 → b 接管堆内存，a 变为有效但未指定

const std::string c = "world";
std::string d = std::move(c);   // ❗ const 右值 → 仍然匹配拷贝构造，发生拷贝
```

**`std::move` vs `std::forward`**：

| | `std::move` | `std::forward<T>` |
| -- | ----------- | ----------------- |
| 条件 | **无条件**转右值 | **有条件**：仅当 `T` 是右值引用类型时才转右值，否则保持左值 |
| 用途 | 确定要掏空某对象 | 完美转发模板参数 |
| 场景 | 移动构造/赋值实参 | `template<class T> void f(T&& x) { g(std::forward<T>(x)); }` |

### 13. 拷贝构造、拷贝赋值、移动构造、移动赋值有何区别？

**考察点**：五法则与四类特殊成员函数。

| 操作 | 典型签名 | 触发举例 | 对源对象 | 建议 |
| ---- | -------- | -------- | -------- | ---- |
| 拷贝构造 | `T(const T&)` | `T b = a;`、按值传参、放入容器 | 不变 | 深拷贝或引用计数 +1 |
| 移动构造 | `T(T&&) noexcept` | `T b = std::move(a);`、返回临时量 | **被掏空** | 窃取资源并置空源 |
| 拷贝赋值 | `T& operator=(const T&)` | `b = a;` | 不变 | 释放旧资源再深拷贝，处理自赋值 |
| 移动赋值 | `T& operator=(T&&) noexcept` | `b = std::move(a);` | **被掏空** | 释放旧资源再窃取 |

**要点**：

- 构造版负责**创建新对象**；赋值版负责**覆盖已存在对象**。
- **拷贝赋值必须处理自赋值**（`a = a`）并释放旧资源，惯用 **copy-and-swap**：

```cpp
struct Vec {
    int* data_; size_t n_;
    Vec(const Vec& o) : data_(new int[o.n_]), n_(o.n_) {
        std::copy(o.data_, o.data_ + o.n_, data_);
    }
    Vec(Vec&& o) noexcept : data_(o.data_), n_(o.n_) { o.data_ = nullptr; o.n_ = 0; }

    // copy-and-swap：一次实现拷贝赋值，天然自赋值安全 + 强异常安全
    Vec& operator=(Vec o) { swap(*this, o); return *this; }
    friend void swap(Vec& a, Vec& b) noexcept {
        std::swap(a.data_, b.data_); std::swap(a.n_, b.n_);
    }
    ~Vec() { delete[] data_; }
};
```

- **移动操作必须标 `noexcept`**：否则 `std::vector` 扩容时不会使用移动（为满足强异常安全保证，改用拷贝），性能显著下降。
- **三/五/零法则**：定义了析构/拷贝/移动之一，通常要定义（或 `= default`/`= delete`）全部五个；能靠成员 RAII 自动完成就别手写（零法则）。
- 声明了移动操作后，**拷贝操作会被隐式删除**（除非显式 `= default`）—— 这是"只写移动构造后代码无法拷贝"的原因。
- `T b = a;` 是**拷贝构造**（初始化），不是赋值。

### 14. 构造和赋值有何区别？

**考察点**：初始化 ≠ 赋值。

| 维度 | 构造 | 赋值 |
| ---- | ---- | ---- |
| 对象状态 | 对象**还不存在**：分配内存 + 初始化 | 对象**已存在**且已初始化 |
| 调用 | 构造函数 | `operator=` |
| 资源处理 | 直接获取/初始化 | 必须**先释放/覆盖旧资源** |
| 返回值 | 无 | 返回 `*this` 引用以支持链式赋值 |
| 触发场景 | 定义变量、传参、按值返回、`new` | `a = b;` |

**要点**：

- **初始化 ≠ 赋值**：`T a = b;` 和 `T a(b);` 都是**拷贝构造**（初始化），`a = b;` 才是赋值。内置类型 `int x = 1;` 同样是初始化。
- 赋值运算符要负责三件事：**处理自赋值、释放旧资源、返回引用**；构造函数不需要。
- `const` 成员、引用成员、无默认构造的类成员只能**初始化**（初始化列表/NSDMI），不能赋值 —— 这是"必须用初始化列表"的根本原因（详见第 43 题）。

## 三、面向对象与多态（15–24）

### 15. 虚函数如何实现动态多态？

**考察点**：虚表（vtable）与虚表指针（vptr）机制。

**要点**：

- 每个**含虚函数的类**由编译器生成一张 **虚表 vtable**（编译期确定，存放该类各虚函数的地址，通常在 `.rodata`）；每个**对象**内嵌一个 **虚表指针 vptr**，指向其**动态类型**对应的虚表。
- 构造对象时设置 vptr：先指向基类虚表，派生类构造完成后改写为派生类虚表。
- 通过**基类指针/引用**调用虚函数时，编译器生成"取 `obj->vptr` → 查虚表槽位 → **间接跳转**"。槽位索引在继承体系中**固定**，这也是"重写必须签名一致"的原因之一。
- 因此调用哪个函数由对象**运行期的动态类型**决定 → **动态绑定 / 动态多态**。
- **不走虚表的情况**（编译期已知类型 → 静态绑定）：对象直接调用 `obj.f()`、显式限定 `p->Base::f()`、构造/析构期间的虚调用（vptr 指向当前类）、被 `final` 修饰的类/函数。
- 现代编译器会做 **devirtualization（去虚化）**。

```cpp
struct Base { virtual void f() { puts("Base"); } virtual ~Base() = default; };
struct Der : Base { void f() override { puts("Der"); } };

Base* p = new Der;
p->f();      // 间接：p->vptr → Der 的 vtable → Der::f → 输出 "Der"
delete p;    // 虚析构：先 ~Der 再 ~Base
```

> RTTI（`type_info`）通常放在虚表 `-1` 槽位附近，`dynamic_cast` / `typeid` 依赖它。

### 16. 函数重载和重写有何区别？

**考察点**：静态绑定 vs 动态绑定。

| 维度 | 重载 overload | 重写 override |
| ---- | ------------- | ------------- |
| 位置 | **同一作用域**（同类/同命名空间） | **基类与派生类**之间 |
| 条件 | 同名、**参数列表不同**（类型/个数/顺序）；返回类型不参与 | 同名、**参数列表与 const 限定完全相同**、基类函数为 `virtual` |
| 绑定时机 | **编译期**（重载决议 + 名字修饰 mangling） | **运行期**（虚表分发） |
| 多态类型 | 静态多态 | 动态多态 |
| 关键字 | 无 | `override`（建议必加，编译期校验） |

**要点**：

- 重载**不能**只靠返回类型区分；`const` 成员函数与非 const 版本**可以**构成重载（隐含的 `this` 参数类型不同）。
- 重写的例外：返回类型可以**协变**（基类返回 `Base*`，派生类返回 `Der*`）。
- 名字修饰（mangling）是重载可实现的底层机制：`f(int)` 与 `f(double)` 修饰成不同符号（可用 `nm`/`c++filt` 观察）。

### 17. 什么是函数隐藏？

**考察点**：派生类作用域的名字查找规则（name hiding）。

**要点**：

- 派生类中声明了与基类**同名**的函数（**不管参数是否相同**、不管基类是否为虚函数），基类中**所有同名函数**在派生类作用域内都被**隐藏**。
- 根源：**名字查找先在派生类作用域进行，一旦找到名字就停止**，不再向基类作用域继续查找（重载决议发生在找到名字之后）。
- **恢复方式**：
  1. `using Base::f;` 把基类同名函数引入派生类作用域（与派生类版本构成重载）；
  2. 显式限定：`obj.Base::f()`、`p->Base::f()`；
  3. 通过**基类指针/引用**调用。
- **典型坑**：派生类想"重写"却写错签名（漏 `const`、参数类型不同）→ 变成**隐藏**而非重写，多态静默失效；加 `override` 可让编译器直接报错。

```cpp
struct Base { void f(int); virtual void g(); };
struct Der : Base {
    void f(double);     // 隐藏 Base::f(int) —— 不是重载，也不是重写！
    void g() override;  // 重写
    using Base::f;      // 不加这行，d.f(1) 会调用 Der::f(double)
};
Der d;
d.f(1);          // 无 using：Der::f(double)；有 using：Base::f(int)（精确匹配）
```

### 18. 函数隐藏会隐藏基类哪些函数？

**考察点**：隐藏的范围。

**要点**：

- 隐藏的是**基类中所有同名的成员**，包括：
  - **全部重载版本**（即使参数列表与派生类版本毫无关系）；
  - 同名但**签名不同**的虚函数（这时是隐藏而非重写，多态失效）；
  - 若派生类定义了**同名的数据成员**，也会隐藏基类的同名数据成员（用 `obj.Base::x` 访问）。
- **隐藏原则**：**只看名字，不看参数**。只要派生类作用域出现了这个名字，基类的同名成员就被遮挡。
- 不受影响的：不同名的函数、通过 `using` 引入的名字、显式限定访问的成员。

**三者对比记忆**：

| 情形 | 结论 |
| ---- | ---- |
| 同作用域、同名、**参数不同** | **重载** |
| 跨继承、同名、**参数相同**、基类 `virtual` | **重写** |
| 跨继承、同名（**不论参数是否相同**） | **隐藏**（其中"同名同参但基类非虚"也属隐藏） |

### 19. 函数重载属于哪种多态？

**考察点**：多态的分类。

**要点**：

- 函数重载属于 **静态多态（编译期多态 / 静态绑定）**：调用哪个函数在**编译期**由实参类型经**重载决议**确定，运行期**没有额外分派开销**（直接调用，可内联）。
- 与之对应的**动态多态（运行期多态）**= 虚函数重写（配合 RTTI / `dynamic_cast`）。
- **重载决议三步**：① 作用域查找名字 → ② 收集候选函数（含 ADL 实参依赖查找）→ ③ 按**标准转换序列**优劣选出最佳匹配，必要时判定二义性（ambiguous）。

### 20. C++ 还有哪些静态多态？

**考察点**：编译期多态的全家桶。

**要点**：

| 机制 | 说明 |
| ---- | ---- |
| **函数重载 / 运算符重载** | 编译期决议，最基础的静态多态 |
| **模板**（函数/类/变量/别名模板） | 用具体类型**实例化**出不同代码 |
| **CRTP**（奇异递归模板模式） | `template<class D> struct Base { void f(){ static_cast<D*>(this)->impl(); } };` —— 编译期分发，无虚表开销 |
| **`constexpr` / `if constexpr`（C++17）** | 编译期计算与分支（`if constexpr` 可让不同类型走不同分支且**不实例化**废弃分支） |
| **Concepts（C++20）** | 约束模板参数，编译期检查与重载选择 |
| **SFINAE / `enable_if` / tag dispatch** | 用重载决议做编译期条件选择 |
| **`std::variant` + `std::visit`** | 静态分发（编译期生成访问表） |

**静态 vs 动态多态**：

| 维度 | 静态多态 | 动态多态 |
| ---- | -------- | -------- |
| 决议时机 | **编译期** | **运行期** |
| 机制 | 重载 / 模板 / CRTP / Concepts | 虚表 + vptr |
| 运行期开销 | 零分派开销，可内联 | 间接跳转、无法内联、多一个 vptr |
| 灵活性 | 类型集合编译期确定 | 运行期可扩展/可插拔 |
| 代价 | 模板多实例化导致代码膨胀 | 无代码膨胀，但调度开销 |

### 21. C++ 有哪些智能指针？

**考察点**：所有权语义与开销。

| 智能指针 | 语义 | 可拷贝 | 开销 | 典型场景 |
| -------- | ---- | ------ | ---- | -------- |
| `std::unique_ptr` | **独占**所有权，不可拷贝只可移动 | ❌ | **零额外开销**（与裸指针同大小） | 默认首选；工厂返回、PImpl、数组 `unique_ptr<T[]>` |
| `std::shared_ptr` | **共享**所有权，引用计数 | ✅ | 控制块 + **原子**引用计数（约两个指针大小） | 多方共享同一生命周期 |
| `std::weak_ptr` | **弱引用**，不增计数，需 `lock()` 提升 | ✅ | 共享同一控制块 | **打破循环引用**、缓存、观察者 |

**要点**：

- `auto_ptr`（C++98）：拷贝即转移所有权的失败设计，**C++11 弃用、C++17 移除**；`scoped_ptr` 是 boost 的（对应 `unique_ptr`）。
- 优先用 **`std::make_unique<T>(...)` / `std::make_shared<T>(...)`**：更异常安全，`make_shared` 还把控制块与对象放在**同一块内存**（少一次分配，但对象内存要等 weak 计数也为 0 才释放）。
- `unique_ptr` 通过 `std::move` 转移所有权；`shared_ptr` 的**引用计数是原子操作**（多线程安全），但**指向的对象本身不保证线程安全**。
- `shared_ptr` **循环引用会导致内存泄漏**，用 `weak_ptr` 打破。
- **自定义删除器**：`unique_ptr<T, D>` 中删除器是**类型的一部分**（零开销）；`shared_ptr` 的删除器不改变类型（存在控制块里，略有开销）。
- `enable_shared_from_this` + `shared_from_this()`：让对象安全地获取自身的 `shared_ptr`（避免 `shared_ptr(this)` 造成二次控制块）。

```cpp
auto up = std::make_unique<Foo>(1);
auto sp = std::move(up);                       // 所有权移交

std::shared_ptr<Node> a = std::make_shared<Node>();
std::shared_ptr<Node> b = a;                   // 计数 = 2

struct Node { std::shared_ptr<Node> next; std::weak_ptr<Node> prev; };  // 打破循环
```

### 22. 虚函数调用比普通调用多哪些开销？

**考察点**：动态分派的运行期与空间代价。

**要点**：

- **间接跳转**：普通调用是 `call 立即数地址`（编译期确定）；虚调用需 ① 读 `obj->vptr` → ② 查虚表槽位 → ③ **间接 `call`**（`mov rax,[rdi]; call [rax+off]`），多两次内存访问。
- **分支预测失败**：间接跳转目标多变时，BTB（分支目标缓冲）难以预测，可能流水线停顿（现代 CPU 的间接分支预测能大幅缓解，但类型数量多、模式随机时仍吃亏）。
- **无法内联**（除非编译器 **devirtualization** 成功）：失去内联带来的常量传播、循环优化、寄存器分配等一连串机会，这是**最大的实际性能损失**。
- **空间开销**：每个对象多一个 **vptr**（64 位下 8 字节，破坏小对象的紧凑性）；每个类一张虚表（rodata）。
- **限制优化与内存布局**：带虚函数的类**不是标准布局 / 不是 POD**，影响 `memcpy` 序列化、C ABI 互操作。
- **缓存局部性**：`vptr → vtable → 函数地址` 是两次间接访问，代码也不在附近，易 cache miss。

**减少开销的手段**：`final` 修饰类/函数、对象直接调用、编译期类型已知、`-O2` 的去虚化、`-flto`（链接期优化）、用 CRTP/模板替代虚函数（把多态前移到编译期）。

### 23. 构造函数能否为虚函数，为什么？

**考察点**：vptr 的设置时机。

**要点**：

- **不能是虚函数**，两个原因：
  1. **机制上不可能**：虚函数分派依赖对象内**已初始化好的 vptr**，而 vptr 恰恰是在**构造函数执行过程中**由编译器逐层写入的（先基类后派生类，每次都改写）。构造之前对象不存在，没有 vptr，无法完成虚分派。
  2. **语义上矛盾**：`new Der` 时编译期就知道要构造哪个具体类型，无需运行期分派；而**基类构造函数执行时派生类部分尚未构造**，即使能分派也不该调用派生类版本（否则会使用未初始化的成员）。
- 但**构造函数体内可以调用虚函数**：分派确实发生，只是绑定到**当前正在构造的那个类**（vptr 指向当前类的虚表），**不会**多态到最终派生类型。

```cpp
struct Base { Base() { f(); } virtual void f() { puts("Base::f"); } };
struct Der : Base { void f() override { puts("Der::f"); } };

Der d;   // 输出 Base::f —— 基类构造期间 vptr 还指向 Base
```

- **同理**：**析构函数可以是虚函数**（对象已完整存在，vptr 有效），但析构期间的虚调用同样降级到当前类。
- 若确实需要在构造完成后触发多态行为，用**两段式初始化**（构造函数 + `init()`，或用工厂函数）。

### 24. 基类析构函数为何通常声明为虚函数？

**考察点**：通过基类指针删除派生类对象的安全性。

**要点**：

- 场景：`Base* p = new Der; delete p;`
  - `~Base` **不是虚函数**：`delete p` 只调用 `~Base`（静态绑定）→ **派生类部分不被析构**（资源泄漏），**未定义行为**。
  - `~Base` **是虚函数**：`delete p` 先调用 `~Der` 再调用 `~Base`（虚表分派）。
- **核心规则**：**只要一个类可能被用作"多态基类"（即通过基类指针/引用删除派生类对象），其析构函数就应当声明为 `virtual`。**
- **反面规则**：不打算被继承或多态删除的类**不要随意加虚析构** —— 会引入 vptr，破坏 trivially copyable / 标准布局，增加对象体积，并**抑制移动操作的隐式生成**。
- 配套要点：
  - 基类虚析构会**抑制移动构造/移动赋值的隐式生成**，需要显式 `= default`。
  - 可写**纯虚析构** `virtual ~Base() = 0;` 使基类抽象，但**必须提供定义**（派生类析构会调用它）。
  - 若基类析构**非虚**，但用 `std::shared_ptr<Base>` 管理，仍能正确删除派生类对象 —— 因为 `shared_ptr` 在构造时就**记住了正确的删除器**（这是 `shared_ptr` 相对裸指针的安全优势之一）。

```cpp
struct Base { virtual ~Base() = default; };      // 多态基类
struct Der : Base { ~Der() override { /* 释放资源 */ } };

Base* p = new Der;
delete p;   // ✅ ~Der → ~Base；若 ~Base 非虚则是 UB
```

## 四、STL 容器与迭代器（25–33）

### 25. STL 有哪些常用容器？

**考察点**：容器分类与选择依据。

| 类别 | 容器 | 底层 / 特点 |
| ---- | ---- | ----------- |
| **顺序容器** | `vector`、`deque`、`list`、`forward_list`、`array` | vector/deque 支持随机访问；list 是双向链表 |
| **关联容器（有序）** | `map`、`set`、`multimap`、`multiset` | **红黑树**，有序，操作 O(log n) |
| **无序关联容器** | `unordered_map/set/multimap/multiset` | **哈希表**，平均 O(1) |
| **容器适配器** | `stack`、`queue`、`priority_queue` | 基于 deque/vector 的接口封装（`priority_queue` 是堆） |
| **字符串 / 定长** | `string`、`array` | `string` 类似 vector；`array` 是栈上定长数组 |
| **视图（非容器）** | `string_view`、`span` | 不拥有数据，只提供视图 |
| **C++23 新增** | `flat_map`、`flat_set`、`mdspan` | 有序向量实现，缓存友好 |

**选择原则**：

- 默认首选 **`vector`**（随机访问 + 尾部增删 + 缓存友好）；
- 头部也要 O(1) 增删 → `deque`；
- 频繁在**已知位置**中间插入删除、且需要**迭代器稳定** → `list`；
- 需要**有序**遍历 / 范围查找 → `map` / `set`；
- 只需快速**按键查找**、无顺序要求 → `unordered_map` / `unordered_set`；
- 固定大小、不想堆分配 → `std::array`。

**补充**：`map` 底层是红黑树（插入不使迭代器失效）；`unordered_*` 采用链地址法 + 桶，**装载因子超限时 rehash**；`priority_queue` 默认 `std::less` → **大顶堆**。

### 26. `vector` 和 `list` 底层存储有何区别？

**考察点**：连续存储 vs 节点式存储的连锁影响。

| 维度 | `vector` | `list` |
| ---- | -------- | ------ |
| 底层结构 | **连续动态数组**（一整块堆内存） | **双向链表**（每个元素一个独立节点） |
| 内存布局 | 元素连续，无额外指针 | 节点分散，每节点含**前驱/后继两个指针** |
| 随机访问 | **O(1)**（指针加减） | **O(n)**（必须遍历） |
| 尾部插入/删除 | 均摊 O(1)（可能扩容） | O(1) |
| 中间/头部插入删除 | O(n)（搬移元素） | O(1)（改指针；但定位仍是 O(n)） |
| 迭代器失效 | 扩容则全部失效；否则插入点及之后失效 | 插入不失效；删除只失效被删元素 |
| 缓存局部性 | **好**（预取友好、顺序访问快） | **差**（节点随机分布，频繁 cache miss） |
| 每元素额外开销 | 无（但可能有预留 capacity 浪费） | 2 个指针（64 位下 16 字节/节点） |
| 典型场景 | **绝大多数情况** | 已知位置的频繁增删、需要稳定迭代器、元素拷贝代价极高 |

**结论**：**默认选 `vector`**。`list` 只在"**迭代器必须稳定**"或"确实频繁中间增删且元素拷贝代价高"时才更优 —— 而这两种场景现代实践中常常用 `deque`、`vector` + 索引、或"指针容器 `vector<unique_ptr<T>>`"就能更好地替代（因为 list 的 cache miss 代价往往超过 O(n) 搬移的代价）。

### 27. `vector` 如何扩容？

**考察点**：扩容流程与摊还复杂度。

**触发条件**：`push_back` / `insert` 时 `size() == capacity()`（没有预留空间）。

**扩容过程**：

1. 申请**新内存**（容量 `new_cap = max(old * growth, old + 1)`，实现相关）；
2. 把旧元素**移动构造**（若移动构造是 `noexcept`）或**拷贝构造**到新内存；
3. **析构**旧元素；
4. **释放**旧内存；
5. 插入新元素。

**复杂度**：单次最坏 **O(n)**，但**均摊 O(1)** —— 用等比数列求和可证（总搬移次数 ≈ 2n）。

**副作用**：扩容会使**所有指向元素的指针/引用/迭代器失效**；这也是"**移动构造必须 `noexcept`**"的原因（否则为保证强异常安全，扩容只能用拷贝）。

```cpp
std::vector<int> v;
for (int i = 0; i < 10; ++i) { v.push_back(i); std::cout << v.capacity() << ' '; }
// libstdc++ / libc++（2x）： 1 2 4 8 16 ...
// MSVC STL（1.5x）：        1 2 3 4 6 9 13 ...
```

**优化手段**：`v.reserve(n)` 一次性预留，避免多次扩容与搬移；`v.shrink_to_fit()` 请求收缩容量（非强制）。

**为什么不用每次 +1？** 会退化成 **O(n²)**。**为什么不能无限大？** 内存浪费大、且失去"容量可复用"的工程收益。

---

### 28. 不同编译器的 `vector` 扩容策略是否相同？

**考察点**：标准未规定增长因子。

**答案：不相同。** 标准只要求均摊 O(1)，**未规定增长因子**，各实现自选：

| 实现 | 增长策略 | capacity 序列 |
| ---- | -------- | ------------- |
| **libstdc++（GCC）** | **2 倍** | 1, 2, 4, 8, 16, 32, ... |
| **libc++（Clang）** | **2 倍** | 同上 |
| **MSVC STL** | **1.5 倍** | 1, 2, 3, 4, 6, 9, 13, 19, ... |
| 其他实现 | 小块 2x、大块 1.5x 的混合策略 | 实现自定 |

**为什么 1.5 倍常被认为更好？** 1.5 倍序列在若干次扩容后，**新分配的内存块能容纳此前释放的全部块**，从而**复用**已释放的地址空间，减少"无法复用的内存空洞"；2 倍增长则扩容次数更少、速度更快，但更容易留下无法复用的空洞。

**实践结论**：

- **不要依赖具体增长因子**（跨编译器、跨版本行为不同）；
- 需要确定性行为或性能可预测时，**显式 `reserve`**；
- 涉及序列化/地址敏感的代码尤其要注意扩容导致的地址变化。

### 29. 迭代器何时失效？

**考察点**：不同底层结构在插入/删除时的失效规则。

| 容器 | 插入 | 删除 |
| ---- | ---- | ---- |
| `vector` / `string` | `size == capacity` 时**全部失效**；否则**插入点及之后**失效 | **删除点及之后**失效 |
| `deque` | 头/尾插入：**迭代器**失效，但已有元素的指针/引用可能仍有效（实现相关）；**中间插入：全部失效** | 头/尾删除：仅被删元素；**中间删除：全部失效** |
| `list` / `forward_list` | **不失效**（`end()` 除外） | **仅被删元素的迭代器失效** |
| `map` / `set` / `multimap` / `multiset` | **不失效** | **仅被删元素失效** |
| `unordered_map` / `unordered_set` | **rehash 时全部失效**，否则不失效 | 仅被删元素失效（若触发 rehash 则全部失效） |

**根本原因**：

- **连续存储**（`vector`/`deque`/`string`）：扩容会搬到新内存 → 全部失效；即便不扩容，插入/删除也会搬移后续元素 → 位置变了。
- **节点式存储**（`list`/`map`/`set`）：节点地址在元素生命周期内**固定不变** → 只有被删节点失效。
- **哈希表**：rehash 会重建桶数组、重排元素 → 全部失效。

**安全用法**：

```cpp
// ❌ 错误：erase 后 it 已失效，++it 是 UB
for (auto it = v.begin(); it != v.end(); ++it)
    if (*it % 2 == 0) v.erase(it);

// ✅ 正确：用 erase 的返回值接住下一个有效迭代器
for (auto it = v.begin(); it != v.end(); )
    it = (*it % 2 == 0) ? v.erase(it) : it + 1;

// ✅ C++20 更简洁
std::erase_if(v, [](int x) { return x % 2 == 0; });
```

> `reserve()` 只能**降低**失效概率，**不能保证**不失效（容量不足时仍会扩容）。

### 30. `vector` 插入元素如何影响迭代器？

**考察点**：插入点前后失效范围的区别。

**两种情形**（以 `v.insert(pos, x)` 为例，`push_back` 视为在 `end()` 处插入）：

1. **未触发扩容**（`size < capacity`）：**插入点及其之后**的所有迭代器、指针、引用**失效**（后续元素被整体后移，地址改变）；**插入点之前**的仍然有效。
   - `push_back`：只有 `end()` 语义失效 → **每次操作后都要重新获取 `end()`**。
2. **触发扩容**：申请新内存并搬移 → **全部迭代器、指针、引用失效**。

**返回值**：`insert` 返回指向新插入元素的迭代器；`erase` 返回**下一个**有效迭代器（需要连续删除时接住它）。

```cpp
std::vector<int> v{1, 2, 3};
v.reserve(10);

auto it = v.begin();          // 指向 1
v.push_back(4);               // 未扩容 → it 仍然有效
auto last = v.end() - 1;      // 每次都要重新取，不能缓存旧 end()

v.insert(v.begin(), 0);       // ❗ it（begin）及之后全部失效
it = v.begin();               // 重新获取

auto after = v.erase(v.begin());   // after 指向原 v[1]，即新的 begin()
```

> **实用原则**：任何可能改变 `size` / `capacity` 的操作之后，**重新获取迭代器**，或者干脆**用索引/`at()`** 访问。

### 31. `list` 插入、删除如何影响迭代器？

**考察点**：节点式存储的稳定性优势。

**要点**：

- **插入**（`insert` / `push_back` / `push_front` / `emplace*`）：**不会使任何已有迭代器失效**（节点原地新建，只需重连前后指针）。
- **删除**（`erase` / `pop_back` / `pop_front` / `clear`）：**只有指向被删除元素的迭代器失效**，指向其他元素的迭代器仍然有效。
- **`splice`**：把节点从一条链表"剪切"到另一条链表，**O(1)、不拷贝/不移动元素、不使任何迭代器失效**（list 的独门绝技，可用来实现"把元素从一个列表挪到另一个列表"）。
- **成员版 `sort` / `merge` / `reverse` / `unique`**：只重排节点、不移动元素，**不使迭代器失效**。注意 `std::sort` **不能**用于 `list`（要求随机访问迭代器），必须用 **`list::sort`**。

```cpp
std::list<int> l{1, 2, 3, 4};
auto it = std::next(l.begin());   // 指向 2

l.push_front(0);                  // it 仍有效，仍指向 2
l.erase(std::prev(it));           // 只有指向 1 的迭代器失效，it 有效
l.sort();                         // 只重排节点，it 仍指向 2
std::cout << *it;                 // 输出 2

std::list<int> other;
other.splice(other.begin(), l, it);   // 把 2 剪到 other，it 仍有效（现在属于 other）
```

> 对比记忆：**list 的迭代器稳定性来自"节点不搬家"**，代价是随机访问 O(n) 与缓存不友好。

### 32. `push_back` 与 `emplace_back` 有何区别？

**考察点**：原地构造 vs 临时对象 + 拷贝/移动。

| 维度 | `push_back` | `emplace_back` |
| ---- | ----------- | -------------- |
| 参数 | 一个**对象**（`T` 或 `T&&`） | **构造函数的参数包** `Args&&...` |
| 是否产生临时对象 | 传左值：拷贝；传右值：移动（无临时对象） | **无**（在尾部内存上原地构造） |
| 性能 | 传左值时多一次拷贝 | 通常更优；**传右值/已构造对象时两者等价** |
| 隐式转换 | 要求类型可**隐式转换** | 可直接调用 **`explicit`** 构造函数 |
| 返回类型 | `void` | C++17 起返回 `reference`（指向新元素） |

```cpp
std::vector<std::string> v;
v.push_back("hi");           // 构造临时 string + 移动（或直接构造）
v.emplace_back("hi");        // 直接在尾部构造 string（更优）
v.emplace_back(10, 'x');     // 直接调用 string(10, 'x')

struct P { int x, y; explicit P(int, int); };
std::vector<P> ps;
ps.emplace_back(1, 2);       // ✅ 调用 explicit 构造
// ps.push_back({1, 2});     // ❌ explicit 不能隐式转换（列表初始化也不允许）
// ps.push_back(1, 2);       // ❌ push_back 只接收一个参数
```

**易错点（`emplace_back` 的坑）**：

```cpp
std::vector<std::vector<int>> vv;
vv.push_back({3, 0});        // 得到 1 个元素 {3, 0}
vv.emplace_back(3, 0);       // ❗ 得到 3 个元素，每个是 {0}（调用了 vector(size, value)）
```

- `emplace_back` 会**无条件调用构造函数**，可能绕过 `explicit` 的意图、也可能匹配到你没想到的构造函数重载。
- **真正的性能关键往往不是 push/emplace 的选择，而是"是否触发扩容"** —— 先 `reserve` 的收益通常远大于二者之差。

### 33. 如何释放 `vector` 内存，而非仅清空元素？

**考察点**：`size` 与 `capacity` 的区别与收缩手段。

**要点**：

- `clear()` 只**析构元素**并把 `size` 置 0，**`capacity` 不变**，堆内存**不归还**。
- 释放内存的几种方式：

| 方法 | 代码 | 说明 |
| ---- | ---- | ---- |
| **swap 惯用法（最通用）** | `std::vector<T>().swap(v);` | 用空 vector 交换，临时对象析构时释放原缓冲区；**C++98 起都可用** |
| `shrink_to_fit()`（C++11） | `v.clear(); v.shrink_to_fit();` | **非强制性**请求，标准库可满足也可忽略（主流实现都会收缩） |
| 临时对象交换（C++03 收缩） | `std::vector<T>(v).swap(v);` | 拷贝一份再交换 |
| **移动赋值** | `v = std::vector<T>{};` | 旧缓冲区随移动赋值被释放 |

```cpp
std::vector<int> v(1000);
v.clear();                     // size=0，capacity 仍是 1000，内存没还
std::cout << v.capacity();     // 1000

std::vector<int>().swap(v);    // ✅ 真正释放
std::cout << v.capacity();     // 0

// 或
v = std::vector<int>{};        // 移动赋值，同样释放
```

**什么时候需要**：**长生命周期**的容器（单例、成员变量、全局缓存）在经历大批量数据后要归还内存。

**什么时候不需要**：容器即将销毁；或后续还会用到同量级容量（反复 swap 会导致频繁重新分配，**得不偿失**）。

## 五、Lambda 与现代 C++（34–37）

### 34. 什么是 Lambda 表达式？

**考察点**：闭包的本质 = 匿名函数对象。

**要点**：

- Lambda 是 C++11 引入的**匿名函数对象（闭包）**，语法：

  ```text
  [捕获列表](参数列表) mutable noexcept -> 返回类型 { 函数体 }
  ```

  其中 `mutable`、异常说明、返回类型可省略（返回类型可推导）。

- 编译器为**每个 lambda 表达式生成一个唯一的匿名闭包类型**，**捕获的变量成为该类型的数据成员**，`operator()` 是它的成员函数（默认是 `const` 成员函数）。
- 本质是**语法糖**，等价于手写一个带 `operator()` 的函数对象（functor）。因此**可内联、零额外开销**（区别于 `std::function` 的类型擦除）。
- **每个 lambda 都是不同类型**："长得一样"的两个 lambda 类型也不同，不能互相赋值；需要统一类型时转成 `std::function` 或用函数指针（**只有无捕获的 lambda 才能隐式转函数指针**）。

```cpp
int threshold = 10;
auto is_big = [threshold](int x) { return x > threshold; };

// 编译器大致生成：
struct __anon_lambda {
    int threshold;                                    // 捕获的变量成为成员
    bool operator()(int x) const { return x > threshold; }   // 默认 const
};
```

**典型用途**：STL 算法谓词（`sort` / `find_if` / `for_each`）、智能指针自定义删除器、`std::thread` / 异步任务、事件回调。

### 35. Lambda 有哪些捕获方式？

**考察点**：捕获列表的完整用法与生命周期陷阱。

| 写法 | 含义 | 说明 |
| ---- | ---- | ---- |
| `[]` | **不捕获** | 只能用全局/静态变量；无捕获 lambda 可转换为**函数指针** |
| `[=]` | **按值**捕获"用到的"变量 | 拷贝一份；lambda 内默认 **const**，需 `mutable` 才能改（改的是副本） |
| `[&]` | **按引用**捕获"用到的"变量 | 无拷贝开销；**有悬垂风险**（被引用对象生命周期） |
| `[x]` / `[&x]` | 显式按值 / 按引用捕获单个变量 | **推荐**：意图明确、可读性好 |
| `[=, &y]` / `[&, y]` | 混合捕获 | 默认按值 + `y` 按引用（反之亦然） |
| `[this]` | 捕获当前对象**指针** | 本质是 `[=]` 的一部分；对象析构后再调用 → UB |
| `[*this]`（C++17） | 按值捕获**整个对象的副本** | 适合异步场景，避免悬垂 |
| `[x = expr]`（C++14 **初始化捕获**） | 用表达式初始化捕获 | **移动捕获的唯一方式**：`[p = std::move(ptr)]` |

**关键要点与坑**：

- **捕获时机 = lambda 定义处**（不是调用处）：按值捕获立即拷贝；按引用捕获绑定到当时的对象。
- **按引用捕获的悬垂**：lambda 被存起来**延后执行**（存进容器、注册为异步回调、丢给 `std::thread`）而引用对象已出作用域 → UB。异步场景应使用**初始化捕获（move 进 lambda）**或 `[*this]`。
- **`[=]` 捕获的变量在 lambda 内是 const**（`operator()` 默认 const）；想修改需加 `mutable`（但改的是 lambda 自己的副本，不影响外部）。
- **成员函数中的 `[=]` 实际捕获的是 `this` 指针**，不是成员副本；C++20 起 `[=]` 对 `this` 的隐式捕获被**弃用**，要求显式写 `[this]` 或 `[*this]`。
- **静态变量 / 全局变量不捕获**，lambda 内直接访问（且非线程安全）。

```cpp
int a = 1, b = 2;
auto f1 = [a, &b] { return a + b; };                     // a 拷贝，b 引用
auto f2 = [p = std::make_unique<int>(5)] { return *p; }; // 初始化捕获（移动）
auto f3 = [a]() mutable { a += 1; return a; };           // mutable 才能改副本

// ⚠️ 危险：lambda 活得比 b 久
// std::function<void()> cb = [&b] { std::cout << b; };
```

### 36. `constexpr` 和 `const` 有何区别？

**考察点**：编译期常量表达式 vs 运行期只读。

| 维度 | `const` | `constexpr` |
| ---- | ------- | ----------- |
| 含义 | **运行期只读**（"我不会改它"） | **编译期常量表达式**（"编译期就能算出值"） |
| 初值必须编译期可算？ | 否（可运行期初始化） | **是**（修饰变量时） |
| 可用于数组长度 / `case` / 模板实参 / `static_assert` | **否**（除非同时是常量表达式） | **可以** |
| 是否隐含对方 | 不隐含 `constexpr` | 对变量**隐含 `const`** |
| 修饰函数 | `const` 成员函数：承诺不修改对象状态 | `constexpr` 函数：**可**在编译期求值（也可运行期求值）；C++14 起函数体可有循环/多语句 |
| 是否占内存 | 变量通常占内存 | 作为常量通常**直接内联，不占内存**（被 odr-use 时才会分配） |

```cpp
int n = 10;
const int a = n;            // ✅ 运行期只读
// constexpr int b = n;     // ❌ n 不是常量表达式
constexpr int c = 10;       // ✅ 编译期常量
int arr[c];                 // ✅

constexpr int fib(int n) { return n < 2 ? n : fib(n - 1) + fib(n - 2); }
static_assert(fib(10) == 55);   // 编译期求值
int x = fib(runtime_n);         // 也可运行期调用（不一定有编译期开销）
```

**延伸（C++20）**：

- **`consteval`**：**必须**在编译期求值（立即函数）。
- **`constinit`**：保证变量走**静态初始化**，用于规避"静态初始化顺序问题"（SIOF）。
- **`constexpr` 容器/字符串**：C++20 起 `std::string`、`std::vector` 等支持 `constexpr`，可在编译期构造。
- **`constexpr` 构造函数**：`constexpr` 对象必须由 `constexpr` 构造初始化。

> **一句话选择**：表达"**编译期常量**"用 `constexpr`；只表达"**只读**"用 `const`。`constexpr` 变量天然满足 `const`，反之不成立。

### 37. Lambda 与 `std::function` 有何区别？

**考察点**：类型擦除带来的灵活性与开销。

| 维度 | Lambda（闭包类型） | `std::function` |
| ---- | ----------------- | --------------- |
| 本质 | 编译器生成的**唯一匿名具体类型** | **类型擦除**的可调用对象包装器（模板类） |
| 类型 | 每个 lambda 一个类型，互不通用 | **统一类型**，可存任意签名兼容的可调用对象 |
| 互相赋值 / 放容器 | 不同类型不能互赋 | ✅ 可互相赋值、放容器、做参数 |
| 运行期开销 | **零开销**：可内联、无堆分配、间接调用可消除 | **间接调用**（虚函数式分派）；大于 SBO 缓冲时**可能堆分配** |
| 尺寸 | 取决于捕获（无捕获 = 1 字节） | 固定（通常 32 字节左右，含 SBO 缓冲区） |
| 可否存捕获 lambda | 它就是 | ✅ |
| 适用场景 | 局部使用、算法谓词、性能敏感路径 | 需要**统一类型 / 运行期多态**、回调注册表、成员变量存储 |

```cpp
std::vector<std::string> v{"a", "bb", "ccc"};

// ① 直接传 lambda：零开销，可内联
std::sort(v.begin(), v.end(), [](const auto& a, const auto& b) { return a.size() < b.size(); });

// ② 需要"统一类型"时用 std::function
std::function<bool(const std::string&)> pred;
int n = 2;
pred = [n](const std::string& s) { return s.size() > static_cast<size_t>(n); };
pred = [](const std::string& s) { return s.empty(); };   // 换一个不同 lambda 也没问题

// ③ 无捕获 lambda 可转函数指针（最轻量的"统一类型"，但不能携带状态）
bool (*fp)(int) = [](int x) { return x > 0; };
```

**关键结论**：

- **能用 lambda（或泛型 lambda / 模板参数）就不要用 `std::function`** —— `std::function` 有类型擦除的调用开销，且可能堆分配。
- 需要"**编译期多态**"传谓词时，把函数对象作为**模板参数**：`template <class F> void algo(F f)`（零开销）。
- 需要"**运行期多态 / 容器存储 / 回调表**"时，才用 `std::function`。
- `std::function` 内部通常有 **SBO（小对象优化）**：捕获很小的 lambda 不分配堆内存，捕获很大或捕获容器时才会堆分配。

## 六、编译链接与构建工程（38–42）

### 38. C++ 源码到可执行程序经过哪些阶段？

**考察点**：四大阶段与各阶段产物。

| 阶段 | 工具 | 输入 → 输出 | 做的事 |
| ---- | ---- | ----------- | ------ |
| **预处理** | `cpp` | `.cpp/.h` → `.i` | 展开 `#include`、宏替换、条件编译 `#if/#ifdef`、去注释、插入行号标记 |
| **编译** | `cc1plus`/`clang` | `.i` → `.s` | 词法 → 语法 → 语义分析 → AST → 中间表示（GIMPLE/LLVM IR）→ 优化 → **生成汇编** |
| **汇编** | `as` | `.s` → `.o` | 汇编翻译成机器码，生成**目标文件**（ELF：`.text`/`.data`/`.bss`/符号表/重定位表/未解析符号） |
| **链接** | `ld` | `.o` + 库 → 可执行文件 | **符号解析**（为每个未定义符号找到定义）+ **重定位**（填地址）+ 合并段 → ELF 可执行文件或 `.so` |

```bash
g++ -E main.cpp -o main.i     # 预处理
g++ -S main.i   -o main.s     # 编译 → 汇编
g++ -c main.s   -o main.o     # 汇编 → 目标文件（含未解析符号）
g++ main.o -o main            # 链接（默认动态链接 libstdc++）
g++ -v main.cpp               # 观察每一步的完整命令行
```

**要点补充**：

- 目标文件中每个函数/全局变量是一个**符号**：`T`（已定义，代码段）、`U`（**未定义，待链接解析**）、`W`（弱符号/内联函数）、`B`/`D`（BSS/数据段）。用 `nm` / `objdump -t` 查看。
- **链接的两大类型**：**静态链接**（把库代码复制进可执行文件）与**动态链接**（运行时由 `ld.so` 装载 `.so`，采用 **PLT/GOT 延迟绑定**）。
- 额外的优化阶段：**LTO**（链接期跨模块优化）、**`strip`**（剥离符号）、**PGO**（基于profile的优化）。

### 39. `undefined reference` 是哪个阶段的错误？

**考察点**：编译期"允许未解析符号"与链接期"必须找到定义"。

**答案：链接阶段的错误。**

```text
main.o: in function `main':
main.cpp:(.text+0x15): undefined reference to `print(int)'
collect2: error: ld returned 1 exit status
```

**原因**：编译阶段只要求**声明可见**，函数/变量可以**没有定义**（在目标文件里标记为 **`U`**）；到链接阶段，链接器必须为每个未定义符号找到**唯一**的定义，找不到就报 `undefined reference`。

**常见成因**：

| 成因 | 说明 |
| ---- | ---- |
| **只声明没定义** | 写了函数声明/类静态成员声明，但没写实现 |
| **忘记链接库** | 需要 `-lpthread`、`-lm`、`-lfoo`，或 CMake 里漏了 `target_link_libraries` |
| **库顺序不对** | 静态库对 `-lA -lB` 顺序敏感（**被依赖者放后面**）；可用 `--start-group`/`--whole-archive` |
| **名字修饰（mangling）不匹配** | C++ 调用 C 函数未加 **`extern "C"`** → 符号名不一致 |
| **模板定义不可见** | 模板定义写在 `.cpp` 且未显式实例化 → 实例化时找不到定义（通常表现为链接错误） |
| **内联/静态函数未定义** | `inline` 函数在各 TU 都不可见 |
| **头文件与库的签名/版本不一致** | 声明与实现的 ABI 不匹配 |

**与另外两类错误区分**：

- **编译错误**：语法、类型、标识符未声明（`error: 'x' was not declared in this scope`）。
- **运行时错误**：`undefined symbol` 出现在**动态库加载时**（启动或 `dlopen` 时找不到 `.so` 中的符号），属运行期/动态链接期，**不是**编译期的 `undefined reference`。

**排错工具**：

```bash
nm -C a.o | grep ' U '      # 查看未定义符号（-C 还原 C++ 名字）
ldd ./a.out                 # 查看运行时依赖的动态库
c++filt _ZN3Foo3barEv       # 还原被修饰的符号名
```

### 40. Debug 和 Release 有何区别？

**考察点**：优化等级、调试信息、断言宏、ABI 兼容性。

| 维度 | Debug | Release |
| ---- | ----- | ------- |
| 优化等级 | `-O0`（MSVC `/Od`） | `-O2` / `-O3`（MSVC `/O2`） |
| 调试信息 | `-g`（MSVC `/Zi`），含符号与行号 | 默认不含（**可单独加 `-g`**） |
| `assert` | **生效** | 被 **`-DNDEBUG`** 关闭 |
| 特征宏 | `_DEBUG` / `DEBUG` | `NDEBUG` |
| 运行速度 | 慢（可能慢数倍到几十倍） | 快 |
| 可调试性 | 可逐行断点、查看变量、完整栈回溯 | 变量被优化掉、内联/重排导致跳转错乱、难断点 |
| 体积 | 大（含调试段） | 小（可 `strip`） |
| 运行时检查 | 部分检查开启（如 MSVC `_ITERATOR_DEBUG_LEVEL`） | 关闭 |

**关键坑**：

- **Debug 与 Release 的库不能混用**（尤以 MSVC 为甚：CRT 版本、结构体布局、迭代器调试级别不同）→ 链接错误或运行时崩溃。第三方库必须与主程序配置**一致**。
- **"Release 才出现的 Bug"** 典型来源：
  - 依赖**未定义行为**（数组越界、使用未初始化变量、悬垂指针、有符号整数溢出）；
  - 依赖**求值顺序**或编译器优化重排；
  - 浮点精度差异；
  - **`assert(expr)` 里写了有副作用的代码**（Release 下副作用直接消失）。
- **正确做法**：Release 也**保留符号**便于线上崩溃分析 —— `-O2` 与 `-g` 可以共存；配合 `-fno-omit-frame-pointer` 得到可用的调用栈；用 `addr2line`/符号服务器还原堆栈。

### 41. `-O2`、`-O3` 会做哪些优化？

**考察点**：优化清单、代价与注意事项。

**-O2（最常用的发布级别）主要优化**：

- **常量传播 / 常量折叠**、常量条件消除；
- **死代码消除（DCE）**、无用变量与分支删除；
- **公共子表达式消除（CSE）**、冗余加载消除；
- **循环优化**：循环不变量外提（LICM）、循环展开、归纳变量优化、循环交换；
- **函数内联**（有限度）、**尾调用优化（TCO）**；
- **寄存器分配**与指令调度、**强度削弱**（乘法换移位）；
- **别名分析**驱动的指令重排。

**-O3 在 -O2 基础上额外**：

- **更激进的自动向量化（SIMD）**；
- 更激进的循环展开 / 分块 / 交换（`-ftree-loop-distribute-patterns` 等）；
- 更激进的内联（含部分过程间优化）、**函数克隆与特化**。

**代价与注意**：

- **代码膨胀**：内联/展开导致 i-cache 压力增大，**有时反而更慢**（需要实测）。
- **编译时间显著增加**。
- **调试困难**：变量被优化掉、行号与代码错位。
- **`-O2`/`-O3` 并不改变 IEEE 浮点语义**（除非显式 `-ffast-math`，它才允许重结合、忽略 NaN/Inf 假设）。
- 优化器会让你**依赖 UB 的代码"看起来能跑"**，换编译器/换版本就可能崩 —— 这是"Release 才崩"的常见根因。

**相关开关**：`-Os`（优化体积）、`-Ofast`（= -O3 + fast-math）、`-flto`（链接期优化，跨 TU 内联与去虚拟化）、`-march=native`（生成当前 CPU 的指令集）。

**实践建议**：默认 **`-O2 -g`**；只有在**实测**确有收益时才上 `-O3`。

### 42. 静态库和动态库各有哪些优缺点？

**考察点**：链接方式对体积、内存、部署、升级的影响。

| 维度 | 静态库（`.a` / Windows `.lib`） | 动态库（`.so` / Windows `.dll`） |
| ---- | ------------------------------ | ------------------------------- |
| 链接方式 | **编译期**把库代码**复制进**可执行文件 | **运行期**由动态链接器装载 |
| 可执行文件体积 | 大 | 小 |
| 内存占用 | 每个进程各一份 | **多进程共享同一份代码段**（省物理内存） |
| 部署 | 简单，无外部依赖 | 需随程序分发 `.so`/`.dll`，处理 `LD_LIBRARY_PATH`/`rpath` |
| 升级 | 需**重新链接**整个程序 | **替换库文件即可**（ABI 兼容前提下） |
| 启动速度 | 快 | 稍慢（装载 + 符号解析，可调优延迟绑定） |
| 插件 / 热更新 | 不支持 | **支持**（`dlopen`/`dlsym` 运行时加载） |
| 版本冲突 | 无 | 有（**DLL Hell**、符号冲突、soname 版本） |
| 编译调试 | 简单 | 稍复杂（符号可见性、导出表、`-fPIC` 要求） |
| 典型场景 | 工具链、单文件分发的 CLI、容器镜像内的独立程序 | 系统公共库、大型多模块系统、插件架构 |

**要点补充**：

- **静态库链接有顺序依赖**：`-lA -lB` 中 `A` 依赖 `B` 时，`B` 必须放在后面；复杂依赖用 `--start-group ... --end-group` 或 `--whole-archive` 解决。
- **动态库的优点本质是"共享 + 可独立升级"**，代价是引入**运行时依赖**与 **ABI 兼容**问题 —— **改了结构体布局、虚表、模板签名、内联函数就会不兼容**（需要重新编译使用方）。
- 动态库必须用 **`-fPIC`** 编译（位置无关代码）。
- 混合链接：`-static-libstdc++ -static-libgcc` 只静态链接 C++ 运行时（便于分发到不同 glibc 版本的环境）；`-static` 全静态（glibc 全静态链接有 NSS/dlopn 警告，需谨慎）。
- 符号可见性优化：`-fvisibility=hidden` + `__attribute__((visibility("default")))` 只导出必要符号，减小体积、加快装载、降低冲突。

## 七、其他高频考点（43–45）

### 43. 构造函数为何优先用初始化列表而非函数体赋值？

**考察点**：语义必要性 + 性能差异。

**① 语义必要性（不是优化，是"必须"）**

以下成员**只能在初始化列表中初始化**，函数体赋值根本无法完成：

- **`const` 成员**（只能初始化，不能赋值）；
- **引用成员**（必须绑定且不可改绑）；
- **无默认构造函数的类类型成员**（如 `std::mutex`、`std::atomic`、自定义类型）；
- **基类子对象**（需要调用带参基类构造）。

**② 性能差异**

| 写法 | 过程 | 代价 |
| ---- | ---- | ---- |
| **初始化列表** | 成员**直接构造**（一次构造） | 最优 |
| **函数体赋值** | 成员**先默认构造**（若无默认构造则直接编译错误）**再 `operator=`** | 多一次默认构造 + 一次赋值（对类类型可能多一次临时对象、资源分配与释放） |

```cpp
class A {
    const int id_;
    int& ref_;
    std::string name_;
    std::vector<int> v_;
public:
    A(int id, int& r, std::string n)
      : id_(id), ref_(r), name_(std::move(n)), v_(100, 0) {}   // ✅ 全部"直接初始化"
    // {
    //     id_ = id;        // ❌ const 不能赋值（编译错误）
    //     ref_ = r;        // ❌ 引用不能改绑（编译错误）
    //     name_ = n;       // ⚠️ 先默认构造空串，再 operator=，多一次操作
    //     v_.assign(100,0);// ⚠️ 同理
    // }
};
```

**③ 顺序陷阱（高频考点）**

- **实际初始化顺序按成员的声明顺序**，与初始化列表的书写顺序**无关**；写反会出现"用未初始化成员去初始化另一个成员"，`-Wreorder` 会给警告。
- 顺序：**虚基类 → 基类 → 成员（按声明顺序） → 构造函数体**；析构顺序恰好相反。

**④ 减少重复的现代写法**

- **类内默认成员初始化器（NSDMI）**：`int x_ = 0;`、`std::string name_ = "n/a";`；
- **委托构造（C++11）**：`A() : A(0) {}`；
- **默认参数**配合初始化列表。

**⑤ 例外**：若成员初始化需要 `try/catch` 或复杂循环，可把计算**抽成私有静态函数**在初始化列表中调用（保持"直接初始化"语义），而不是退化成函数体赋值。

### 44. `enum` 和 `enum class` 有何区别？

**考察点**：作用域、类型安全、底层类型、前向声明。

| 维度 | `enum`（无作用域枚举，C++98） | `enum class`（有作用域枚举，C++11） |
| ---- | ----------------------------- | ----------------------------------- |
| 作用域 | 枚举值**泄漏到外层作用域**，可直接使用，**易命名冲突** | 必须 `Color::Red`，**不污染外层作用域** |
| 隐式转换 | **隐式转换为整型**，可参与算术/比较 | **不隐式转换**，须 `static_cast<int>(x)` |
| 与其他枚举比较 | 允许（易错，不同类型混比无警告） | **编译错误**，类型安全 |
| 底层类型 | 由实现选择（大小实现相关）；可 `enum E : int` 指定 | 默认 `int`，可 `enum class E : uint8_t` 指定 |
| 前向声明 | **需要先固定底层类型**才能前置声明 | 默认底层类型已知，**可直接前向声明** |
| 同名枚举值 | 同一作用域内不能重名 | 不同 `enum class` 可用相同名字（作用域隔离） |

```cpp
enum Color { Red, Green };        // 传统
int c = Red;                      // ✅ 隐式转 int（类型不安全）
// enum Other { Red };            // ❌ 重定义（Red 已泄漏到外层作用域）

enum class Color2 { Red, Green }; // C++11
// int c2 = Color2::Red;          // ❌ 不隐式转换
int c2 = static_cast<int>(Color2::Red);   // ✅ 显式转换
Color2 c3 = Color2::Red;          // ✅ 必须带作用域

enum class Byte : unsigned char { v0, v1 };   // 指定底层类型
```

**相关内容**：

- 取底层类型：`std::underlying_type_t<Color2>`；
- C++20 起 `using enum Color2;` 可将枚举值引入当前作用域；
- C++17 的 `std::byte` 就是 `enum class byte : unsigned char` 的实践范例。

> **结论**：**新代码一律用 `enum class`**（类型安全 + 作用域隔离）；只有需要与 C API / 老代码隐式转 int 时才用传统 `enum`。

### 45. 进程和线程各自独占、共享哪些资源？

**考察点**：资源分配单位 vs 调度单位。

**定义**：**进程是资源分配的基本单位**（拥有独立地址空间）；**线程是 CPU 调度的基本单位**（同一进程内的多条执行流）。

| 资源 | 进程独有 | 线程独有 | 同进程内线程共享 |
| ---- | :------: | :------: | :--------------: |
| **虚拟地址空间（页表）** | ✅ | ❌ | — |
| **代码段（二进制指令）** | ✅ 独立映射 | ❌ | ✅ 共享同一份物理页 |
| **数据段 / 全局变量 / 静态变量** | ✅ 独立 | ❌ | ✅ |
| **堆（heap）** | ✅ 独立 | ❌ | ✅ |
| **栈（stack）** | 主线程栈 | ✅ **每线程独立栈** | ❌ |
| **寄存器上下文 / 程序计数器 PC** | — | ✅ | ❌ |
| **线程局部存储 TLS / `errno`** | — | ✅ | ❌ |
| **信号掩码 / 调度优先级 / 亲和性** | — | ✅ 可单独设置 | ❌ |
| **文件描述符表** | ✅（进程级持有） | ❌ | ✅ **同一张 fd 表** |
| **当前工作目录 / `umask`** | ✅ | — | ✅ |
| **用户 ID / 组 ID / 环境变量** | ✅ | — | ✅ |
| **信号处理函数（handler）** | ✅ 进程级 | — | ✅ |
| **PID / TID** | ✅ 独立 **PID** | 各有 **TID**（同 TGID） | ✅ 共享 PID（TGID） |

**关键差异与代价**：

- **创建/切换开销**：线程创建（`pthread_create`）与切换开销**小**（同地址空间，无需切换页表、不刷新 TLB）；进程创建（`fork`）开销大（页表复制 + **写时复制 COW**）。
- **隔离性 vs 通信成本**：线程共享地址空间 → **通信零成本（直接读内存）**，但**必须同步**（mutex/atomic/条件变量），否则数据竞争；进程隔离性好，但通信需管道、共享内存、socket 等 IPC。
- **故障影响**：**一个线程崩溃（如段错误）会导致整个进程退出**；进程崩溃只影响自身（隔离性强）。
- **同步原语**：线程用 mutex/条件变量/原子变量；进程间用文件锁、信号量、共享内存 + 同步。

**Linux 实现视角（面试加分）**：

- Linux 中**线程就是"共享部分资源的轻量级进程（LWP）"**，进程与线程都由 `task_struct` 表示。
- `fork` / `vfork` / `pthread_create` 底层都走 **`clone()` 系统调用**，通过传入不同的 flag 决定共享哪些资源：
  - `CLONE_VM`（共享地址空间）、`CLONE_FILES`（共享 fd 表）、`CLONE_FS`（共享文件系统信息）、`CLONE_SIGHAND`（共享信号处理）、`CLONE_THREAD`（同线程组，共享 PID/TGID）。
- `pthread_create` 本质上就是 `clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | ...)`。
- 因此"线程共享什么"在实现层就是"`clone` 时共享了哪些 flag" 的精确映射。

## 复习速记

| 主线 | 一句话结论 |
| ---- | ---------- |
| 指针 vs 引用 | 引用非空不可改绑，指针可空可改指；裸指针 = 非拥有可空，引用 = 非拥有非空 |
| RAII | 构造获取、析构释放，靠确定性析构与栈展开实现异常安全；析构须 `noexcept` |
| 移动语义 | 右值引用 + 资源窃取；`std::move` 只转类型不搬数据；移动后源对象"有效但未指定" |
| 五法则 | 拷贝/移动构造与赋值 + 析构，定义了其一通常要定义全部；移动操作必须 `noexcept` |
| 多态 | 动态 = 虚表 + vptr（运行期）；静态 = 重载/模板/CRTP/Concepts（编译期） |
| 隐藏 | 派生类同名即隐藏基类**全部**同名成员（只看名字不看参数），`using` 可恢复 |
| 虚析构 | 多态基类必须虚析构，否则 `delete basePtr` 是 UB |
| 容器 | 默认选 `vector`；`list` 胜在迭代器稳定，输在 cache 局部性 |
| 迭代器失效 | 连续存储看**插入/删除点及其后**（扩容则全部）；节点式只失效被删元素 |
| `emplace_back` | 原地构造，省一次拷贝/移动；但可能匹配到你没想到的构造重载 |
| 编译链接 | 预处理 → 编译 → 汇编 → 链接；`undefined reference` 是**链接期**错误 |
| Debug/Release | `-O0 -g` vs `-O2 -DNDEBUG`；两者库不可混用，"Release 才崩"多半是 UB |
