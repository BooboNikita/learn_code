# 深入学习

本书为你在图形编程领域的探索打下了一个坚实的基础。但它终究无法涵盖一切。接下来给出的是其他一些主题的概览：既然你已经对图形学大致的工作方式有了了解，这些主题就值得你去进一步研究。

## 调试

本书提供了可用于解决各类问题、实现各种效果的可用代码。但它没有讨论如何把一份不能工作的代码变成能工作的代码。也就是调试。

调试 OpenGL 代码非常困难。图形代码里有 bug 时，最常见的结果是一块完全帮不上忙的空白屏幕。如果问题局限在某个着色器或用于渲染某个物体的状态上，结果就是一个黑色的物体或一堆垃圾。让问题更严重的是，OpenGL 有大量的全局状态。本书经常采用「绑定对象、对它做些事情、再解绑」的写法，原因之一就是减少状态依赖。这样可以确保每个物体都由特定的程序、特定的纹理集合、特定的 VAO 等来渲染。这样做可能稍慢一些，但对简单的应用来说，先让它跑起来更重要。

调试着色器的问题更严重：GLSL 着色器上没有断点，也没有可以查看的变量。片元着色器提供了类似 `printf` 式的调试手段：总能把一些值写到帧缓冲里，然后看到点东西。顶点着色器或其他着色器阶段则必须先把数据传给另一个阶段，才能看到结果。而且即便看到了，那还是插值之后的版本。

正因为调试如此困难，调试的总体策略与其说是找出 bug，不如说是防止 bug。因此，调试最重要的策略是：永远从能工作的代码开始。开发要从一个确实能跑起来的东西开始，哪怕它画出来的东西还不是你最终想要的。一旦有了能工作的代码，你就可以改它，让它渲染你需要的内容。

第二个要点是，尽量减少可能引发问题的代码与数据量。这意味着在一个能工作的应用中做小改动，并立刻测试它们是否有效。如果无效，那问题必然出在这些小改动上。如果你做大改动，那么需要排查的代码与数据量就会大得多。需要调试的代码越多，有效调试就越困难。

与上一条配套的做法是使用分布式版本控制系统，并经常提交代码，最好是每做一个小改动就提交一次。这样你既能回退掉不能工作的改动，也能看到上一个可用版本与现在这个不能工作的版本之间的实际差异。它能让你免受误敲键盘之类问题的困扰。

下一步是尽可能使用调试工具，在你的目标平台上存在这类工具的地方使用它们。OpenGL 本身在这方面也能帮上忙。OpenGL 规范定义了各函数在输入不合法时应当如何处理。具体来说，它们会把错误放入 OpenGL 错误队列。每次调用 OpenGL 函数之后，你可能都要检查一下队列里是否新增了错误。代码如下：

```cpp
for(GLenum currError = glGetError(); currError != GL_NO_ERROR; currError = glGetError())
{
  //Do something with `currError`.
}
```

把这段代码放在每次函数调用之后会非常繁琐。但由于所有错误都存放在一个队列里，它们并不与引发错误的那个具体函数相关联。如果不是频繁调用 `glGetError`，就很难知道某个特定的错误究竟来自哪里。因此，OpenGL 有一个专门用于辅助调试的扩展：ARB_debug_output。这个扩展只有在创建 OpenGL 上下文时带上特定的调试标志才会启用。本书所用的框架会在调试构建中自动使用这个扩展。

调试输出扩展允许用户注册一个函数，一旦发生错误就会调用它。在错误不那么严重的情况下也可以调用它，这取决于 OpenGL 的实现。当配置为同步错误消息时，回调函数会在引发错误的那个函数返回之前被调用。因此你可以在回调函数中设置断点，准确地看出是哪个函数引发了错误。

设置这个回调的过程有些复杂。Unofficial OpenGL SDK 在其 GL Utilities 子库中提供了一个用于正确配置调试输出的注册函数。此外，本书代码所用的框架也提供了类似的功能，位于 `framework/framework.cpp`。

捕获 OpenGL 错误还有其他办法。工具 [RenderDoc](https://renderdoc.org/) 能够钩住 OpenGL，无需修改任何代码就能跟踪每一次 OpenGL 函数调用。随后它可以回放 `glDraw*` 调用，同时让你检查渲染结果以及传入的参数。这对调试非常有用，因为它能告诉你更多关于哪些因素可能引发了特定的错误或画面瑕疵的信息。它还会在每次函数调用之后自动检查错误，省去了手动检查的麻烦。任何错误都会连同产生它们的函数一起记录到日志中。

除 OpenGL 之外，它也支持 Vulkan 和 D3D API，因此你可以把它当作解决渲染问题的默认首选工具。

## 值得研究的主题

本书应当为理解图形开发打下了坚实的基础。但还有许多同样对渲染很重要的主题没有在本书中覆盖。下面是一个值得你去研究的主题列表，并对基本概念做简要介绍。

这份列表并不是要全面游览所有有趣的图形效果，它只是为你应当花些时间研究的少数几个概念做一次引入。可能还有别的主题不在这份列表中，但同样值得你投入时间。

**顶点权重**

我们的所有网格都只应用了相当简单的线性变换（透视投影除外）。然而，人物或类人角色的网格需要能够根据动画发生形变。上臂与前臂的变换是不同的，但它们都会以某种方式影响肘部的顶点。

处理这个问题的系统称为顶点权重或蒙皮（注意："skinning"这个词也被用于把纹理映射到物体上，做网络搜索时要留意这一点）。一个角色由一个变换层次结构构成；每个变换称为一根骨骼。顶点被赋予针对特定骨骼的权重。有意思的地方在于，一个顶点可以对多根骨骼有权重。这意味着顶点的最终位置由两个（或更多）变换的加权组合决定。

顶点着色器通常通过把一个矩阵数组作为一致性缓冲对象（uniform block）来做到这一点。每个矩阵就是一根骨骼。每个顶点包含一个 `vec4`，其中含骨骼矩阵数组中最多 4 个索引，以及另一个 `vec4`，其中包含对应骨骼要使用的权重。顶点分别与这四个矩阵相乘，结果再取平均。

法线以及凹凸映射所需的切线空间基向量会让这个过程更加复杂。而一种称为对偶四元数蒙皮的技术会让它更复杂。这种技术主要是为了避免某些骨骼相互旋转时产生的问题。当手腕骨骼相对于前臂旋转 180 度时，它能防止顶点向内塌陷。

**BRDF**

双向反射分布函数（Bidirectional Reflectance Distribution Function，BRDF）指的是一类特殊的函数。它是一个关于两个方向的函数：指向入射光的方向和指向观察者的方向，两者都是相对于表面法线指定的。最后这一点使得 BRDF 与表面法线无关，因为法线只是方程中的一个隐含参数。BRDF 的输出是来自光源的光中沿视线方向被反射的百分比。因此，BRDF 的输出乘以入射光强，就得到朝向观察者的反射光强。

从各方面来看，这听上去就是一个光照方程。事实也确实如此。本书中每一个光照方程都可以写成 BRDF 的形式。BRDF 这类方程有意思的地方之一在于，你实际上可以把一个实物拿进实验室，做一系列测试，然后从中生成一张 BRDF 表。这张 BRDF 表通常表示为一张纹理，着色器随后可以直接用它来表现真实世界中的表面在光照条件下实际如何表现。这能比我们在本书中使用的光照模型给出准确得多的结果。

**可缩放的 Alpha 测试**

我们已经看到 alpha 测试如何通过 `discard` 工作：如果一个片元的 alpha 低于某个阈值，它就会被丢弃。然而，在放大提供该 alpha 的纹理时，被丢弃部分与未被丢弃部分的边界上会出现不理想的阶梯效应。如果对纹理做正确的预处理，就可以避免这些瑕疵。

Valve software 的 Chris Green 写过一篇论文，题为 *Improved Alpha-Tested Magnification for Vector Textures and Special Effects*。论文描述了一种方法：取 alpha 的高分辨率版本，并把它转换成距离场。由于距离在图像这样的空间域中插值得好得多，使用基于距离的剔除而不是基于边缘的剔除，即使图像被大幅放大，也能得到平滑得多的结果。

深度场还可以用来做其他效果，比如在物体周围描边或投射阴影。而且它最妙的地方在于，这是一项实现起来非常廉价的技术。它需要一些前期预处理，但最终得到的东西相当强大，而且对性能非常友好。

**屏幕空间环境光遮蔽**

基于光栅化的渲染有许多困难问题，其中之一就是处理互相反射。也就是说，一个物体反射出去的光又打到另一个物体上。我们此前用单一的环境光来近似处理这一点。这确实是个有用的手段，但仍然是种 hack。

屏幕空间环境光遮蔽（Screen-Space Ambient Occlusion，SSAO）这个术语，指的是对上述本身就很 hack 的概念所作的一种 hack 式改造。其思路是这样的：如果一个物体有一个内凹的角，那么这个内凹角周围像素的互相反射量就会低于整体的互相反射水平。这是一个普遍成立的陈述。SSAO 所做的就是在屏幕空间中找出所有这样的角，并按比例降低它们的环境光强度。

在屏幕空间中做这件事需要访问每个像素的屏幕空间深度。因此它与延迟渲染技术结合得非常好。实际上，它可以直接融入延迟渲染的环境光照过程，不过如何让它跑得足够快是最大的挑战。但它的效果足够好，值得为之付出努力。

**光散射**

光穿过大气时，会被大气自身吸收和反射。毕竟这就是天空呈蓝色的原因：大气吸收了来自太阳的部分光，使阳光带上蓝色。云也是同一回事：打在构成云的水汽上的光会被四处反射和散射。薄云看起来是白的，因为仍有大量光能够穿透。厚云看起来暗，是因为它们散射和吸收了太多光，穿过去的很少。

这些都是大气光散射效应。在实时场景中最常见的是雾。从气象学角度看，雾其实就是一层低空的云。图形学中常见的地面雾近似做法，是改变从表面反射到观察者眼中的光强。光传播得越远，被吸收和反射得就越多，逐渐转化为雾的颜色。因此，离观察者极远的物体会与雾本身难以区分。雾的厚度取决于光在变成纯粹雾之前需要传播的距离。

雾也可以是体积化的，局限在空间中的某个特定区域。这常用来制造充满蒸汽、烟雾或其他颗粒气溶胶的房间效果。体积雾的实现比基于距离的雾复杂得多。如果还有物体需要在雾区中移动，问题就更复杂了。

雾系统处理的是从表面反射到观察者眼中的光。广义的光散射系统处理的则是光源发出并在雾中散射的光。想想雾中的车灯：你能看到光束在雾本身上的反射。那完全是另一回事了，通用实现非常困难。特定实现——有时称为 "God rays"，用于表现阴暗房间中强烈阳光照在尘埃颗粒上的效果——可以提供某种形式的支持。但它们通常必须针对每种具体情况做特化处理，而不是一种可以直接套用的通用技术。

**非真实感渲染**

把非真实感渲染（Non-Photorealistic Rendering，NPR）当作一件事来谈，就好比把"非大象生物学"当作一件事来谈。照片级真实感或许占据了大部分研究精力，但在现代硬件上，非真实感的可能性同样非常广阔。

这些技术往往超出了纯粹渲染的范畴，从纹理如何创建、存储什么，到夸张的模型，再到各种其他东西。一旦你离开近似真实的光照模型这个舒适区，一切规则就都不再适用。

单就渲染部分而言，最知名的 NPR 技术大概是卡通渲染，也就是卡通着色（cel shading）。真实光照的思路是把一个曲面物体照得看起来是弯的。而卡通渲染的思路往往是把曲面物体照得看起来是*平的*。或者至少，让它近似于卡通动画的多种风格中的某一种，有些风格比其他的更平。这一般意味着光只有少数几个强度档位：开、也许稍微弱一点的开、关。这会在模型中形成锐利的高光边缘，从而在不需要完整强度梯度的情况下表现出曲率感。

与卡通渲染搭配的通常是某种形式的轮廓渲染。要以美观的方式实现它要难一些。艺术家在绘制卡通动画时，可以用各种方式进行微调以取得最佳效果，而计算机必须使用算法，对每种情况来说它更可能是一个折中方案而非完美方案。某种情况下好看的轮廓，换一种情况可能就不行。因此，测试各种描边技术对于做出令人信服的效果至关重要。

其他 NPR 技术还包括绘制看起来像铅笔素描的物体，这需要更多的纹理工作而非渲染系统工作。有些人想出办法，让本来可以照片级真实渲染的画面看起来像某种油画，或者在某些情况下像漫画书里那种光亮的色彩。还有诸如此类。NPR 的唯一限制就是图形程序员的想象力，以及那位程序员足够聪明、能找到实现它的方法。
